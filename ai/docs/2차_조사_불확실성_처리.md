# 2차 조사 웹검색 불확실성·상충 근거 처리 설계

작성일: 2026-10-01  
상태: 제안

## 1. 목적

2차 조사는 1차 조사에서 변화가 확인되지 않은 가게를 웹에서 다시 조사해 전화번호·주소·상호명·영업 상태의
변화 후보를 찾는다. 현재 구현은 Vertex AI의 Gemini와 Google Search Grounding을 한 번 호출해 관측값을
수집하고, Python 규칙으로 DB 값과 비교한다.

프로토타입에서는 같은 가게를 다시 조사했을 때 검색 결과와 최종 판정이 달라지는 현상이 확인됐다. 이 문서는
이를 단순히 "환각"으로 묶지 않고 발생 단계를 구분하며, 재검색 결과를 안전하게 누적하고 상충 근거를 사용자에게
노출하기 위한 설계 원칙을 정리한다.

이 문서의 범위는 다음과 같다.

- Google Search Grounding 호출의 변동성을 관측하는 방법
- 제한된 다단계 재검색 흐름
- 서로 다른 값이 발견됐을 때의 충돌 표현과 해소 규칙
- 자동 변경 제안과 사람 검토의 경계
- 기존 단일 호출 방식과 비교할 평가 지표

## 2. 현재 구조

현재 2차 조사는 애플리케이션 관점에서 LLM 한 번을 호출하는 파이프라인이다.

```text
InvestigationTarget
  → Gemini + Google Search Grounding 1회
  → 관측값 파싱
  → Grounding 출처 연결
  → 카카오맵 확인
  → Python 규칙 분류
  → StoreFinding
```

`google_search` 도구를 활성화하면 Gemini 내부에서는 검색 필요성을 판단하고, 하나 이상의 검색어를 만들고,
Google 검색 결과를 종합할 수 있다. 그러나 애플리케이션은 중간 검색 단계에 개입하지 않는다. 검색이 빗나갔을 때
우리 코드가 결과를 보고 검색어를 수정하는 도구 루프도 아직 없다.

현재 구현에서 유지해야 할 원칙은 다음과 같다.

- 모델은 웹에서 본 값을 근거와 함께 수집한다.
- 모델이 적은 URL은 사용하지 않는다.
- `grounding_chunks`와 `grounding_supports`로 응답 구간과 실제 검색 출처를 연결한다.
- DB 값 비교, 정규화, 변경 분류는 Python 규칙이 담당한다.
- 출처가 연결되지 않은 관측은 변경 근거로 사용하지 않는다.

## 3. 문제를 세 단계로 구분한다

같은 입력의 결과가 바뀌었다고 해서 모두 환각은 아니다. 어느 단계가 달라졌는지 먼저 구분해야 한다.

| 구분 | 증상 | 주요 원인 |
|---|---|---|
| 검색 변동성 | 실행마다 검색어·출처가 달라진다 | Gemini의 검색어 선택, Google 순위·검색 결과 변화 |
| 추출 변동성 | 출처는 같은데 모델이 뽑은 값이 달라진다 | 생성 비결정성, 문맥 해석 차이, 형식 이탈 |
| 분류 변동성 | 관측값은 같은데 최종 분류가 달라진다 | 정규화·비교 규칙의 비결정성 또는 버그 |

출처가 뒷받침하지 않는 값을 모델이 생성했다면 환각으로 본다. 반면 실행마다 서로 다른 유효 출처가 검색되어
값이 달라진 것은 검색 변동성이다. 두 문제는 대응 방법이 다르다.

## 4. 모든 조사 시도에 관측 정보를 남긴다

원인을 구분하려면 최종 `StoreFinding`만 저장해서는 안 된다. 개발·평가 환경에서는 적어도 다음 정보를 조사
시도별로 저장한다.

```text
ResearchRun
├─ target: 조사 당시 가게 이름·주소·전화번호
├─ model: 정확한 모델 이름
├─ promptVersion
├─ attempt: 1, 2, 3
├─ purpose: INITIAL | FILL_GAP | RESOLVE_CONFLICT
├─ webSearchQueries
├─ groundingChunks
├─ groundingSupports
├─ rawResponse
├─ parsedObservations
├─ parseErrors
└─ elapsedMs
```

현재 코드는 `grounding_chunks`와 `grounding_supports`를 읽지만 `web_search_queries`는 보존하지 않는다. 검색
변동성을 확인하려면 이 필드를 먼저 수집해야 한다.

같은 대상의 반복 호출을 비교하는 기준은 다음과 같다.

```text
검색어 또는 출처가 다름
  → 검색 단계 변동

검색어와 출처가 같고 관측값만 다름
  → 추출 단계 변동

관측값까지 같고 최종 판정만 다름
  → 분류 단계 결함
```

## 5. 핵심 설계 원칙

### 5.1 재검색은 기존 결과를 교체하지 않는다

재검색 결과는 이전 결과를 덮어쓰지 않고 증거 저장소에 추가한다.

```text
1차 검색 관측
  + 2차 검색 관측
  + 충돌 해소 검색 관측
  → 정규화
  → 값별 후보 그룹
  → 출처 중복 제거
  → 최종 해소 상태 결정
```

마지막 호출 결과만 사용하면 호출 순서에 따라 최종 판정이 달라진다. 모든 시도의 근거를 누적하면 검색 순서의
영향을 줄이고, 담당자에게 왜 충돌했는지 설명할 수 있다.

### 5.2 검색 실패는 변화 없음이 아니다

이번 호출에서 정보를 찾지 못했다는 사실은 가게 정보가 그대로라는 증거가 아니다.

- `NO_CHANGE`: 현재 값과 같은 정보를 근거와 함께 확인했다.
- `INSUFFICIENT`: 확인할 만한 근거를 찾지 못했다.
- `FAILED`: 호출 오류, 파싱 오류 또는 Grounding 누락으로 조사를 완료하지 못했다.

`INSUFFICIENT`와 `FAILED`를 `NO_CHANGE`로 합치면 웹 흔적이 적은 가게가 조사 완료로 잘못 처리될 수 있다.

### 5.3 LLM은 조사하고 코드는 판정한다

LLM이 담당할 일:

- 검색 목적과 검색어 선택
- 동명이점·다른 지점 가능성 확인
- 근거 문장에서 관측값 추출
- 부족한 항목과 충돌 후보 식별

결정적 코드가 담당할 일:

- 값 정규화
- DB 값 비교
- 독립 출처 집계
- 충돌 상태 결정
- 자동 변경 제안 여부 결정
- 최종 API 응답 생성

## 6. 제한형 조사 에이전트

처음부터 자유도가 높은 에이전트를 만들지 않는다. 최대 호출 횟수와 행동 종류를 제한한 상태 기계로 시작한다.

```text
INITIAL_SEARCH
    ↓
관측·출처 정규화
    ↓
┌─ 충분하고 충돌 없음 ─────────────→ COMPLETE
│
├─ 필요한 항목의 근거가 없음 ─────→ FILL_GAP_SEARCH ──┐
│                                                     │
└─ 유효한 값이 둘 이상임 ──────────→ CONFLICT_SEARCH ──┘
                                                      ↓
                                                결과 다시 평가
                                                      ↓
                                   RESOLVED | CONFLICT | INSUFFICIENT
```

권장 초기 한도:

- 최초 검색 1회
- 부족한 항목 또는 충돌 해소를 위한 추가 검색 최대 1회
- 동일 검색어 재사용 금지
- 전체 LLM 호출 횟수 최대 2회
- 전체 제한 시간은 기존 백엔드 타임아웃 안에서 설정

효과가 측정으로 확인된 경우에만 최대 3회로 늘린다.

### 6.1 추가 검색은 목적을 좁힌다

나쁜 예:

```text
이 가게를 다시 조사해라.
```

좋은 예:

```text
성심당 본점의 현재 전화번호에 대한 근거가 없었다.
대전 중구 은행동의 같은 지점인지 확인할 수 있는 전화번호 출처만 찾아라.
```

충돌 해소 검색 예:

```text
같은 지점의 전화번호 후보로 053-111-1111과 053-222-2222가 발견됐다.
두 후보 중 현재 값을 확인할 수 있는 공식 또는 최근 출처를 찾아라.
새 후보를 추측하지 말고 확인할 수 없으면 없다고 답하라.
```

## 7. 상충 근거를 일급 결과로 표현한다

서로 다른 값에 유효한 출처가 연결됐다면 하나를 억지로 선택하지 않는다.

```text
RESOLVED
  하나의 후보를 변경 제안으로 사용할 근거가 충분함

CONFLICT
  둘 이상의 후보에 유효한 근거가 있고 우열을 결정할 수 없음

INSUFFICIENT
  유효한 후보 또는 출처가 부족함

FAILED
  호출·파싱·Grounding 문제로 조사를 완료하지 못함
```

권장 결과 형태:

```json
{
  "field": "phone",
  "resolution": "CONFLICT",
  "candidates": [
    {
      "value": "053-111-1111",
      "normalizedValue": "0531111111",
      "sourceCount": 1,
      "sources": [
        {
          "domain": "official.example.com",
          "url": "https://official.example.com/store",
          "observedAt": "2026-09-20"
        }
      ]
    },
    {
      "value": "053-222-2222",
      "normalizedValue": "0532222222",
      "sourceCount": 2,
      "sources": [
        {"domain": "directory.example", "url": "https://directory.example/place"},
        {"domain": "blog.example", "url": "https://blog.example/review"}
      ]
    }
  ],
  "proposedValue": null
}
```

`CONFLICT`일 때는 다음처럼 처리한다.

- `proposedChanges`에 임의의 후보를 넣지 않는다.
- 담당자가 확인할 수 있도록 모든 후보와 대표 근거를 반환한다.
- 기존 API가 `PRIORITY_CHECK`와 `NO_CHANGE`만 지원한다면 `PRIORITY_CHECK`로 보내되, 충돌 신호와
  `proposedChanges` 없음으로 구분한다.
- 조사 완료 여부를 나타내는 `researchStatus`를 분류와 별도로 추가하는 방안을 검토한다.

## 8. 충돌 해소 규칙

### 8.1 먼저 동일 대상을 확인한다

값의 우열을 비교하기 전에 모든 근거가 같은 가게와 같은 지점을 가리키는지 확인한다.

- 가게 이름만 같고 주소가 다르면 별도 대상으로 본다.
- 쇼핑몰·시장·대학교·병원 등 시설 안 가게는 부모 시설 정보가 섞였는지 확인한다.
- 본점과 지점, 이전 전후 주소, 대표번호와 지점번호를 구분한다.
- 동일 대상을 확인할 수 없는 관측은 후보 점수에 포함하지 않는다.

### 8.2 단순 출처 개수만으로 선택하지 않는다

다음 상황에서 단순 다수결은 잘못된 후보를 선택할 수 있다.

```text
후보 A: 공식 홈페이지 1곳
후보 B: 오래된 블로그와 업체 목록 2곳
```

후보 평가는 적어도 다음 요소를 함께 본다.

1. 대상 일치도: 같은 가게·같은 지점인지
2. 출처 성격: 공공·공식·당사자 출처인지
3. 최신성: 게시일 또는 관측일이 있는지
4. 독립성: 다른 도메인이 같은 원본을 복제한 것은 아닌지
5. 지지 출처 수: 독립적인 출처가 몇 곳인지
6. 반대 근거: 신뢰할 수 있는 다른 후보가 남아 있는지

초기 구현에서는 불완전한 숫자 점수를 만들기보다 보수적인 규칙을 사용한다.

- 공식·공공 출처에서 현재 값을 확인하고 강한 반대 근거가 없으면 `RESOLVED`
- 독립적인 최근 출처 둘 이상이 같은 값을 지지하고 강한 반대 근거가 없으면 `RESOLVED`
- 신뢰할 만한 후보가 둘 이상 남으면 출처 수 차이가 있더라도 `CONFLICT`
- 날짜와 대상 일치 여부를 확인할 수 없으면 `INSUFFICIENT` 또는 `CONFLICT`

필드마다 신뢰할 출처가 다르므로 하나의 전역 출처 점수를 모든 필드에 적용하지 않는다.

## 9. Grounding 사용 시 주의점

### 9.1 메타데이터만 출처로 사용한다

모델이 본문에 직접 적은 URL은 저장하지 않는다. `grounding_chunks`와 `grounding_supports`로 연결된 출처만
사용한다. 한 관측 줄에 support가 연결되지 않았다면 출처 없는 관측으로 유지하고 판정에서 제외한다.

### 9.2 Grounding이 켜졌다고 모든 문장이 근거 기반인 것은 아니다

응답 전체에 검색 결과가 붙어 있어도 개별 관측 줄에는 support가 없을 수 있다. `grounding_chunks`가 하나 이상
있다는 사실만으로 모든 관측을 신뢰하지 않는다.

### 9.3 생성 설정만으로 재현성을 보장할 수 없다

temperature를 낮추면 문장 생성의 변동은 줄일 수 있지만 다음 요소는 남는다.

- Gemini가 선택하는 검색어
- Google 검색 순위와 검색 결과
- 선택되는 Grounding 청크
- 출처를 종합하는 방식

따라서 temperature 조정은 보조 수단이며, 증거 누적과 충돌 표현을 대신할 수 없다.

### 9.4 모델과 프롬프트 버전을 고정한다

평가와 운영 기록에 정확한 모델 이름과 `RESEARCH_PROMPT_VERSION`을 남긴다. 모델 또는 프롬프트가 바뀌면
이전 실행과 같은 조건으로 취급하지 않는다.

## 10. 평가 방법

기존 단일 호출과 제한형 에이전트를 동일한 대상 집합에서 비교한다. 각 대상은 여러 번 반복 호출해 평균 정확도뿐
아니라 안정성을 측정한다.

### 10.1 필수 지표

| 지표 | 의미 |
|---|---|
| 분류 뒤집힘률 | 같은 대상을 반복했을 때 최종 분류가 달라지는 비율 |
| 후보값 안정률 | 반복 실행에서 동일한 정규화 값이 유지되는 비율 |
| 출처 안정률 | 반복 실행의 출처 도메인 집합 유사도 |
| 근거 연결률 | 전체 관측 중 Grounding support가 연결된 관측 비율 |
| 잘못된 변경 제안률 | 실제 값과 다른 값을 `proposedChanges`로 제안한 비율 |
| 충돌 탐지율 | 상충 근거가 있을 때 `CONFLICT`로 남긴 비율 |
| 미해결률 | `INSUFFICIENT` 또는 `FAILED`로 끝난 비율 |
| 평균 호출 수 | 가게 하나당 LLM·검색 호출 횟수 |
| 평균 지연·비용 | 안정성 개선에 드는 운영 비용 |

### 10.2 우선순위

이 서비스에서는 잘못된 자동 제안을 줄이는 것이 응답률을 높이는 것보다 우선이다.

```text
1. 잘못된 변경 제안률 감소
2. 분류 뒤집힘률 감소
3. 근거 연결률과 충돌 탐지율 증가
4. 미해결률 감소
5. 비용과 지연 최적화
```

재검색으로 발견률이 높아져도 잘못된 변경 제안이나 뒤집힘률이 함께 증가하면 채택하지 않는다.

## 11. 단계별 적용안

### 단계 0 — 관측성 추가

동작은 바꾸지 않고 다음 정보를 저장한다.

- `web_search_queries`
- 전체 Grounding 청크와 support
- 호출별 원문과 파싱 결과
- 호출 시간, 오류, 모델·프롬프트 버전

목표는 현재 변동성이 검색·추출·분류 중 어디에서 발생하는지 수치로 확인하는 것이다.

### 단계 1 — 충돌 모델 도입

- 동일 필드의 관측을 정규화 값별 후보로 묶는다.
- `RESOLVED`, `CONFLICT`, `INSUFFICIENT`, `FAILED`를 구분한다.
- 충돌 상태에서는 자동 변경 제안을 만들지 않는다.
- 기존 단일 호출에서도 동작하도록 먼저 적용한다.

### 단계 2 — 목적이 제한된 추가 검색 1회

> **재검색(근거 0건이면 "검색어를 넓혀 다시 찾아라" 지시를 붙여 한 번 더)은 시도했지만 채택하지 않았다(2026-10-05).
> 간이 DB 60곳을 재검색 켜고 2번·끄고 2번 돌린 결과 근거를 찾은 가게는 23·24곳 → 30·28곳으로 늘었지만 수정안은
> 19·18건 → 16·20건으로 늘지 않았고, 같은 설정끼리 판정 뒤집힘은 18% → 24%, 시간은 15초 → 24초였다. 재검색에서만 나온
> 제안에 시설 오인(수성포차에 호텔 대표번호·"호텔 수성")이 섞였다. 모델은 첫 호출에서 이미 "폐업"·"전화번호"·동 이름
> 변형으로 5~20번 검색하고 있어(`web_search_queries`) 지시가 같은 검색을 되풀이했다. 검색어 기록은 남겼다.** 아래 원안(필드·충돌 단위로 목적을 좁힌 조사)은 아직 시도하지 않았다.

- 근거가 없는 필드 또는 충돌한 필드만 추가 조사한다.
- 이전 관측을 버리지 않고 합친다.
- 최대 호출 횟수와 전체 시간 제한을 둔다.
- 기존 방식과 반복 안정성을 비교한다.

### 단계 3 — 검색 도구 확장 여부 결정

Google Grounding 재검색으로도 특정 유형의 가게를 반복해서 찾지 못하거나 검색 결과를 통제할 필요가 있을 때만
Brave 등 명시적 검색 API를 폴백 또는 비교 실험으로 추가한다. 다단계 에이전트를 만든다고 여러 검색 도구가
반드시 필요한 것은 아니다.

## 12. 결정해야 할 항목

- `CONFLICT`를 기존 `PRIORITY_CHECK`에 포함할지 별도 분류로 추가할지
- `INSUFFICIENT` 조사 결과가 `lastCheckedAt` 갱신 대상인지
- 필드별 공식·신뢰 출처의 정의
- 공식 출처 1곳과 비공식 출처 여러 곳이 충돌할 때의 정책
- 추가 검색 최대 횟수와 백엔드 전체 타임아웃
- 운영 환경에서 원문 응답과 검색 쿼리를 얼마 동안 보관할지
- 담당자 화면에서 후보와 상충 근거를 어떤 형태로 보여줄지

## 13. 요약

현재 문제는 LLM 환각 하나가 아니라 검색·추출·분류 세 단계의 변동성 문제다. 해결의 중심은 호출 횟수를 늘리는
것이 아니라 다음 네 가지다.

1. 검색어·출처·원문·관측을 호출별로 기록한다.
2. 재검색 결과를 교체하지 않고 누적한다.
3. 상충 근거를 `CONFLICT`로 보존하고 임의의 값을 제안하지 않는다.
4. 최대 한 번의 목적성 있는 추가 검색부터 시작해 안정성과 비용을 측정한다.

이 원칙이 먼저 적용되어야 다단계 검색 에이전트를 추가해도 불확실성을 키우지 않고 관리할 수 있다.
