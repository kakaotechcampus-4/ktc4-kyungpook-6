# 2차 조사 — 가게 정보 불일치 찾기

PROMPT-88·115·145 · 갱신 2026-10-14 · 백엔드와 주고받는 형식은 [`백엔드_연동.md`](백엔드_연동.md)

## 목적

1차 조사(국세청 대조)에서 변화가 없던 가게를 지도·웹으로 다시 확인해, DB 와 다른 **주소·전화·상호**를 수정안으로
올린다. 담당자가 직접 찾아 대조하던 수고를 덜어 주는 게 목적이고, 반영은 담당자가 승인한다.
**모델은 조사만, 판단은 규칙이** 한다(모델 확신도는 쓰지 않음 — 멘토 결정).

## 흐름

```
가게 1곳
  ① 지도 대조 — 네이버 지역 검색·카카오, LLM 없음        [NAVER_LOCAL_ENABLED · KAKAO_COMPARE_ENABLED]
       └ 지도만으로 확정되면 ③으로
  ② 미확정이면  에이전트가 이어서 조사(혼합 방식)          [AGENT_ENABLED]
                 도구: web_search(항목, 목적) · finish
               아니면 웹검색 1회(Gemini + 구글 그라운딩)
  ③ 규칙 판정 → 응답(task·signal 형식)
```

- **의도한 동작은 스위치를 모두 켠 것**이다. 스위치는 약관 우려 때문에 기본으로 꺼 둔다.
  끄면 **웹검색 → 카카오맵 "근처에 있다/없다" 확인 → 규칙 판정**(기존 동작)
- 파일: 흐름 `web.py` · 지도 `map_lookup.py` · 웹검색 `web_research.py` · 에이전트 `agent.py` · 판정 `classify.py`

## 단계 요약

**① 지도 대조** — 지도에 등록된 상호·주소·전화를 가져온다. 상호가 비슷하고 같은 지역인 후보만 같은 가게로 본다
(주소만 같으면 같은 건물의 다른 업체라 제외). DB 값이 전부 확인되면 확정.
**지도 값은 카카오·네이버 모두 약관상 저장 불가**(아래 약관) → 판정에만 쓰고, 지도에만 다른 값이면 수정안 없이
"카카오맵/네이버 지도에 등록된 값 — DB 값과 다름 + 링크"만 남긴다. 네이버 링크는 네이버 값이 아니라 DB 상호·주소로 만든 검색
링크다. 지도에만 다른 값은 확정이 아니라 에이전트가 웹에서 저장 가능한 같은 값을 찾으러 간다.

**② 웹검색** — DB 값을 주고 `항목 | 값 | 근거 | 날짜` 로 받는다. 출처는 모델이 적은 URL 이 아니라 그라운딩 결과로
잇는다. 형식이 깨지면 1번 더, 429 면 기다렸다 다시. 모델이 쓴 검색어를 기록한다.

**② 에이전트(혼합 방식)** — 지도로 확정 안 된 가게(못 찾음·일부만 확인·지도에만 다른 값)만 받아, 무엇을 더 찾을지
고른다(`web_search(항목, 목적)` 최대 2번 · `finish`, 도구 최대 4번). 수정안에 담을 값은
웹검색에서만 나온다 — 지도는 "다름" 신호와 링크만. **가게당 시간 예산**(`INVESTIGATION_TIME_BUDGET_SECONDS`, 기본 75초 = 지금 백엔드 `ai.read-timeout-ms`) 안에서만 웹검색을 새로 시작한다 — 남은 시간이 40초 이상일 때만. 넘으면 그때까지 모은 관측으로 판정한다(백엔드가 타임아웃으로 버리면 찾은 것까지 잃는다). 지도 값은 판단 모델에 넘기지 않고 관계(일치·다름·못 찾음)만 준다.
판단 모델은 기본 Vertex Gemini, `AGENT_MODEL` 이면 카테캠 프록시(gpt-6-luna, Responses API). 웹검색은 늘 Vertex 그라운딩.

**③ 규칙 판정**
- 빼는 관측: 출처 없음, 가게 번호가 아닌 전화(15xx 등), 번지 없는 잘린 주소, `lastCheckedAt`(선택 입력)보다 확실히 이전 근거
- 같은 값: 전화는 표준 표기로, 주소는 도로명+건물번호로, 상호는 괄호·지점명 앞 지역어를 빼고 비교.
  한쪽이 다른 쪽의 앞부분 + 업종·지점 꼬리면 같음, 그 밖의 포함 관계(`최과장` ↔ `최과장회닾밥`)는 **판단 보류**
- 값 고르기: 출처 많은 값 → 같으면 최근 글. DB 값을 확인해 주는 최근 근거보다 오래된 다른 값은 무시
- 상태를 모를 때 웹의 "영업 중"은 변화로 보지 않는다(폐업 뒤에도 남는 영업시간 문장)

**응답** — `classification`(우선확인/변화없음) · `proposedChanges` · `signals[]`(변화당 1행, 근거 끝에 "(출처 N곳)") ·
`failure`(실패 문장 하나, 성공이면 null). 추가확인(확인 90일 경과)은 백엔드가 정한다.

## 측정 (값 불일치 벤치마크)

인허가 영업 60곳을 확인된 DB 처럼 만들고 한 항목만 일부러 틀리게 넣어(전화 한 자리·건물번호·상호 오타) 측정
(`eval/mismatch_bench.py`, 오류 34곳).

| 방식 | 잡음 | 값까지 담은 수정안 | 가게당 LLM | 시간 | 판정 흔들림 |
|---|---|---|---|---|---|
| 웹검색만 (기본) | 10 | 9 | 1+ | 20초 | 13~18% |
| **고정 순서** (지도 대조 켬) | **22** | 11 | **0.5** | **7초** | **2%** |

| 에이전트 단독 | 20~22 | 12~13 | 4.1~4.2 | 25초 | – |

같은 벤치마크에서 Vertex 오류로 빠진 곳을 빼고 양쪽 다 끝난 오류 31곳으로 짝지어 비교:

| 방식 | 잡음 | 값까지 맞게 고침 | 가게당 LLM | 시간 |
|---|---|---|---|---|
| 고정 순서 (f3) | 22 | 3 | 0.7 | 13초 |
| 혼합 (h3) | 21 | **10** | 3.7 | 52초 |

- 지도 값을 못 담으니 고정 순서는 "지도와 다름 + 링크"만 남고 값이 3곳뿐이다. 혼합은 지도에만 다른 항목을 에이전트가
  골라 웹에서 같은 값을 찾아 **7곳을 되찾았다**(영화반점 상호, 안심농장 전화, 양지찜 주소 등) — 고정 순서로는 못 하는 일
- 혼합이 놓친 1곳(수성포차)은 Vertex 서버 오류로 웹검색 두 번이 다 실패한 것이다
- 판단 모델 비교(세 방식 모두 끝난 51곳, 오류 29곳): 고정 잡음 21·값 3·틀린 값 1 / 혼합 Gemini 20·9·4 / **혼합 gpt-6-luna
  24·13·7**, LLM 3.3회·49초. luna 가 더 잡고 더 고치지만 건드리지 않은 항목에 낸 틀린 값도 많다(인허가 옛 전화번호일 수
  있어 근거를 열어 봐야 한다). 1회씩이라 흔들림은 아직 모른다
- **블로그 도구(`check_blog`, 지금은 뺐다)를 더하면**(b2, luna 판단, l1 과 공통 45곳·오류 23곳): 잡음 18 → 17, 값 9 → 9, 대조군 신호
  10 → 9 로 **더 잡은 것이 없다**. 평균 44 → 69초, LLM 3.2 → 4.4회, 75초 넘는 가게 11 → 21곳. 블로그를 부른 18곳 중
  시간 예산으로 건너뜀 3 · Vertex 오류 5 · 못 찾음 9 · 찾음 1(이미 지도로 잡힌 상호 오타). 주 목표(주소·전화·상호
  불일치)에는 기여가 없고, 폐업 신호는 이 벤치마크(영업 가게에 값만 틀리게 넣음)로는 잴 수 없다
- **가게당 시간 예산(75초)을 넣으면**(l2, luna 판단, l1 과 공통 50곳·오류 28곳): 75초 넘는 가게 14 → 3곳, 중앙 38 → 28초,
  상위 10% 108 → 70초. 예산 없이 다 기다리면 잡음 22·값 11 → 20·8 로 조금 줄지만, **지금 백엔드(75초에 끊음)에서 실제로
  받는 결과로 치면 잡음 13·값 5 → 18·7 로 늘어난다** — 넘긴 가게는 백엔드가 버려 찾은 것까지 잃기 때문이다.
  9곳에서 시간 예산으로 두 번째 검색을 건너뛰었다
- 같은 설정 2회(l2·l3, 공통 50곳): 잡음 19 · 19, 값 7 · 5, 75초 초과 3 · 5. 판정(우선확인/변화없음)이 뒤집힌 가게 4곳(8%),
  수정안·신호가 달라진 가게 12곳 — 잡는 수는 안정적이고, 값을 웹에서 되찾는 부분이 실행마다 흔들린다
- 넘어간 가게 분류(h1): 지도에서 전부 못 찾음 19 · 상호 다름 8(7곳이 실제 오타) · 그 밖(전화 못 찾음·지도에만 다른 값) —
  넘기는 조건을 좁힐 여지는 작다

방식별 로직 — 쓰는 도구(지도 대조·웹검색)와 판정(규칙)은 같고, **다음에 무엇을 할지 누가 정하느냐**가 다르다.
- **웹검색만**: 모든 가게에 웹검색 1회를 돌리고 판정
- **고정 순서**: 코드가 정한 순서. 지도 대조(카카오맵 + 네이버) → 지도만으로 확정(DB 값 전부 확인 또는 다른 값 발견)되면 끝,
  발견되지 않은 건에 대해서 웹검색 1회를 더하고 판정
- **혼합**: 지도 대조까지는 고정 순서와 같다. 확정되지 않은 가게(못 찾음·일부만 확인·지도에만 다른 값)만 에이전트가
  지도 결과(관계만)를 받아 웹에서 무엇을 더 찾을지(항목·목적, 최대 2번) 스스로 정한 뒤 판정
- **에이전트 단독**: 처음부터 LLM 이 도구를 고름 : 지도 대조, 웹에서 무엇을 찾을지, 언제 끝낼지.
  쉬운 가게에도 판단 호출을 써서 LLM 이 가장 많다

- 지도 대조가 탐지를 두 배로 늘리고 결과를 안정시킨다. 전화는 약하다(9곳 중 3곳)
- 첫 표 기준으로 혼합은 잡는 수가 같고 값까지 담은 수정안이 2곳 많지만, 60곳 중 45곳이 에이전트로 넘어가 LLM 이 6배.
  지도 값을 저장하지 않게 바꾼 뒤로는 값을 되찾는 몫이 커져 혼합이 고정 순서보다 낫다(위 두 번째 표)
- 대조군 오탐(24곳 중 5곳)은 셋 다 비슷하고, 일부는 정답(인허가 옛 번호) 쪽 문제. 표본이 작다

**넣지 않은 것**
- 근거 0건이면 재검색: 근거는 늘지만 수정안은 그대로, 판정 흔들림만 증가(모델이 이미 첫 호출에 5~20개 검색어를 씀)
- **네이버 블로그 조사**(PROMPT-145): 멘토 제안(PR #81)대로 브라우저 에이전트가 블로그 글을 읽고 값은 버린 채 판단 라벨과
  링크만 남기는 방식으로 만들어 측정했지만 넣지 않았다. 주 목표(주소·전화·가게명 불일치)에 기여가 없고(b2, 위) 가게당
  +25초라 시간 예산 75초에서는 사실상 돌지 않는다. 남길 이유였던 폐업 신호는 5곳 시험에서 실행마다 흔들렸다(하누탕 폐업
  글: 1회차 못 찾음, 2회차 찾음). 값을 꺼내 수정안에 쓰는 것은 약관상 처음부터 불가. 앞선 실험(`eval/naver_browse.py`)에서
  날짜 규칙·잘린 주소 규칙이 나왔다
- 폐업은 웹으로 거의 못 잡는다(간이 DB 폐업 30곳 중 신호 1곳) — 주 목표가 아니다

## 외부 출처와 약관

- **카카오 로컬**: 실시간 비교 후 폐기·장소 링크 저장만 허용, 값 저장·LLM 전송 불가
- **네이버 지역 검색**(NAVER API HUB): 원문 확인(「NAVER API 서비스 이용약관 – NAVER API HUB」 2026-09-20 시행,
  [상품 페이지](https://www.ncloud.com/product/applicationService/naverApiHub)의 약관 PDF. 개발자센터판과 검색 특약 문구 같음).
  - 검색 특약 1.1 "네이버 검색결과를 **제공하기 위한 목적으로만**", 1.2 가공 없이 노출·원본 링크
  - 1.3 데이터(가공·파생물 포함) 복사·저장·캐싱 금지, **AI 에 입력**·학습·평가 금지
  - 일반조건 7.3③ "네이버 지역정보를 수집하여 **별도 데이터베이스로 관리**하며 이용하는 행위" 금지
  - → 그래서 **카카오와 같은 방식**으로 쓴다: 값은 판정에만 쓰고 버림(`storable=False`), 수정안·에이전트 입력·링크에 네이버 값을
    넣지 않음(1.3·7.3③ 해소). **목적 제한(1.1)은 남는다** — 감수할지 팀 결정. 바꾸기 전 벤치마크를 다시 채점하면
    잡는 수는 같고 값까지 담은 수정안이 11 → 3(고정 순서)으로 줄어, 그 몫을 에이전트가 웹에서 되찾는다
- **네이버 블로그 자동 수집**: 이용약관이 자동화 수집을 금지하고, robots.txt 가 검색 페이지(`m.search.naver.com`)를 막고
  AI·RAG 봇을 금지한다(개별 글 `m.blog.naver.com/{id}/{logNo}` 는 허용). 링크만 넘기는 방식이면 감수하기로 했지만
  (멘토 제안·팀 답변, PR #81) 측정 결과 기여가 없어 운영에는 넣지 않았다(위 "넣지 않은 것")
- **네이버 플레이스**: 첫 요청에 "과도한 접근" 차단 — 쓰지 않는다
- **카테캠 프록시**: 그라운딩을 못 써 에이전트 판단에만 사용

## 정하지 않은 것 (팀 결정)

- 엇갈리는 근거를 지금처럼 하나 골라 제안할지, 후보를 모두 보여 주고 수정안을 비울지
- 결과를 **수정 필요 / 직접 확인 필요 / 확인됨**으로 나눠 보일지 — 지금은 "확인됨"과 "못 찾음"이 둘 다 변화없음
- 판단 보류(잘린 상호 등)를 어떻게 보일지

2. 판단 모델 정하기 — luna 가 더 잡고 더 고치지만 틀린 값도 많다(위). luna·Gemini 를 반복 측정해 흔들림까지 비교
3. 오탐·전화 사례 열어 보기(luna 의 틀린 값 7곳 포함), 벤치마크 데이터 확대(전화 사례·실제 같은 오류)
4. 같은 가게 확인(시설 오인 — 수성포차 ↔ 호텔수성)
5. 카카오맵, 네이버 API 사용을 어떻게 둘지 — 네이버 지역 검색은 약관 원문상 목적 제한(1.1)이 남는다(위)
6. 백엔드 타임아웃(`ai.read-timeout-ms` 75초)과 시간 예산을 같이 정하기 — 올리면 넘긴 가게를 덜 잃지만 Job 이 길어진다

넘기는 조건 좁히기·판단 로그 보기는 h1 분류(위)로 마쳤다 — 넘어간 가게 대부분이 지도에서 못 찾았거나 실제 오타라 좁힐 여지가 작다.
