# 2차 조사 — 가게 정보 불일치 찾기

PROMPT-88·115·145·154 · 갱신 2026-10-16 · 백엔드와 주고받는 형식은 [`백엔드_연동.md`](백엔드_연동.md)

## 목적

1차 조사(국세청 대조)에서 변화가 없던 가게를 지도·웹으로 다시 확인해, DB 와 다른 **주소·전화·가게명**을 수정안으로
올린다. 담당자가 직접 찾아 대조하던 수고를 덜어 주는 게 목적이고, 반영은 담당자가 승인한다.
**모델은 조사만, 판단은 규칙이** 한다(모델 확신도는 쓰지 않음 — 멘토 결정).

**전제 — 실제로 바뀐 가게는 극소수다.** 그래서 많이 잡는 것보다 ① 안 바뀐 가게를 바뀌었다고 올리지 않는 것,
② 대다수인 변화없음 가게를 담당자가 빨리 넘기게 해 주는 것이 중요하다. 벤치마크는 60곳 중 36곳에 오류를 넣은 것이라
이 전제와 거꾸로다 — 거짓 신호는 "DB 가 맞는 가게"로 따로 잰다(아래 측정).

## 흐름

```
가게 1곳
 ① 지도 대조 (LLM 없음)                         [NAVER_LOCAL_ENABLED · KAKAO_COMPARE_ENABLED]
    네이버 "가게명 + 구" · 카카오 DB 좌표 150m 안
    카카오 근처에 없으면 → 반경 없이 다시 찾아 전화번호가 같은 가게 = 이사
 ② DB 값(가게명·주소·전화)이 전부 지도와 같으면 끝
 ③ 아니면 에이전트가 이어서 웹검색 (LLM)         [AGENT_ENABLED · AGENT_MODEL]
    지도에서 "다름"·"못 찾음"인 항목만, 최대 2번, 가게당 75초 안
 ④ 규칙 판정 → 우선확인 / 변화없음
 ⑤ 변화없음이면 항목마다 확인 근거를 붙인다 (일치 / 찾지 못함)
```

- **의도한 동작은 스위치를 모두 켠 것**이다. 끄면 "웹검색 1회 → 카카오맵 근처에 있다/없다 → 규칙 판정"(옛 동작).
- dev 배포는 저장소 변수 `AI_NAVER_LOCAL_ENABLED`·`AI_KAKAO_COMPARE_ENABLED`·`AI_AGENT_ENABLED` 로 켠다(`deploy-dev.yml`).
  비우면 꺼진다.
- 파일: 흐름 `web.py` · 지도 `map_lookup.py` · 웹검색 `web_research.py` · 에이전트 `agent.py` · 판정 `classify.py`

## 단계

**① 지도 대조** — 지도에 등록된 가게명·주소·전화를 가져온다.

같은 가게로 보는 조건(`same_store`):
- 가게명이 비슷하다(한쪽이 다른 쪽을 품거나 글자 유사도 0.6 이상, "&" ↔ "앤" 같음). 두 글자 이하 상호는 정확히 같거나,
  괄호 속 지점명까지 같거나("행컵(계명대점)" ↔ "행컵 계명대점"), 카카오 후보가 20m 안이면 앞부분 포함도 인정("은정" ↔
  "은정식당"). "네네치킨앤봉구스밥버거"처럼 두 상호를 이은 이름은 한쪽과 같고 30m 안이면 인정. 거리 덕분에만 인정한
  후보의 가게명은 "가게명 다름" 근거로 쓰지 않는다(원래 다르게 적혀 있는 것이라)
- 시·도와 구·군이 같다
- **읍·면·동이나 큰길 이름 중 하나가 같다** — 시·도+구·군만 보면 넓은 군에서 다른 읍의 같은 이름 가게를 잡았다
  (화원읍 상하이반점 ↔ 가창면 상하이반점). 큰길은 "비슬로525길" → "비슬로"처럼 번호 길을 뗀 이름이다
- 주소만 같은 후보는 고르지 않는다(같은 건물의 어린이집을 잡았다)

**이사**(`moved_store`): 지도의 가게명·주소만으로는 "우리 가게가 이사함"과 "다른 동네에 원래 있던 같은 이름 가게"가
똑같이 보인다. 그래서 카카오에서 근처(150m)에 없을 때만 반경 없이 가게명으로 다시 찾고, **전화번호가 DB 와 같은**
후보만 이사한 우리 가게로 본다(시·도만 같으면 된다). 전국 대표번호(15xx 등)는 비교하지 않는다. 네이버는 전화번호를
주지 않아(검색 API 의 `telephone` 이 늘 빈 값, 실호출 확인) 이사 판단에 쓰지 않는다.

**지도 값은 카카오·네이버 모두 약관상 저장 불가**(아래 약관) → 판정에만 쓰고(`storable=False`), 지도에만 다른 값이면
수정안 없이 근거 문구와 링크만 남긴다(④ 문구 표). 네이버 링크는 네이버 값이 아니라 DB 가게명·주소로 만든
검색 링크다. 지도에만 다른 값은 끝이 아니라, 에이전트가 웹에서 저장할 수 있는 같은 값을 찾으러 간다.

**③ 에이전트** — 지도로 끝나지 않은 가게(지도와 다름·일부만 확인·못 찾음)만 받아, 무엇을 더 찾을지 고른다
(`web_search(항목, 목적)` 최대 2번 · `finish`). 지도 값은 판단 모델에 넘기지 않고 관계(일치·다름·못 찾음)만 준다.
수정안에 담을 값은 웹검색에서만 나온다. 웹검색은 Vertex Gemini + 구글 그라운딩으로 `항목 | 값 | 근거 | 날짜` 를 받고,
출처는 모델이 적은 URL 이 아니라 그라운딩 결과로 잇는다.
**가게당 시간 예산**(`INVESTIGATION_TIME_BUDGET_SECONDS`, 기본 75초 = 백엔드 `ai.read-timeout-ms`) — 남은 시간이
40초 미만이면 새 웹검색을 시작하지 않고 모은 근거로 판정한다(백엔드가 끊으면 찾은 것까지 잃는다).
판단 모델은 기본 Vertex Gemini, `AGENT_MODEL` 이면 카테캠 프록시(gpt-6-luna, Responses API).

**④ 규칙 판정**
- 빼는 근거: 출처 없음, 가게 번호가 아닌 전화(15xx 등), 번지 없는 잘린 주소, `lastCheckedAt` 보다 확실히 이전 근거
- 같은 값: 전화는 표준 표기로, 주소는 도로명+건물번호로, 가게명은 괄호·지점명 앞 지역어를 빼고 비교.
  한쪽이 다른 쪽의 앞부분 + 업종·지점 꼬리면 같음, 그 밖의 포함 관계(`최과장` ↔ `최과장회덮밥`)는 판단 보류
- 값 고르기: 출처 많은 값 → 같으면 최근 글. DB 값을 확인해 주는 최근 근거보다 오래된 다른 값은 버린다(옛 번호·옛
  표기로 생기는 거짓 신호를 막는다). 출처끼리 엇갈리면 근거 문구에 "(웹 2곳은 DB 와 같음)" 처럼 표시(아래 문구 표)
- 영업 상태를 모를 때 웹의 "영업 중"은 변화로 보지 않는다(폐업 뒤에도 남는 영업시간 문장)
- 근거 문구는 코드가 정한 틀로만 쓴다(`_change_text`). 웹검색 모델의 근거 문장은 넣지 않는다 — 영어 주소가 섞이고 실행마다
  달라졌고, 찾은 값이 문장 속에 묻혔다. 원문은 출처 링크에 있다

  | 경우 | 문구 |
  |---|---|
  | 웹에서 값을 찾음 | `주소: DB "상인서로 48" → 웹 3곳 "대구 달서구 상인서로 46" (최근 글 2026-09-12)` |
  | 지도에서만 다름 | `가게명: 카카오맵과 다름 — 링크에서 확인` (지도 값은 약관상 적지 않는다) |
  | 이사 | `주소: 같은 전화번호의 가게가 다른 주소에 있음(카카오맵) — 링크에서 확인` |
  | 엇갈림 | 뒤에 `(웹 2곳은 DB 와 같음)` · `(웹 3곳은 다른 값)` — 성격별로 묶어 한 번만 |

  출처는 웹이면 도메인 수, 지도면 이름만 적는다. 영업 상태는 "영업 중·휴업·폐업·확인 안 됨"으로 적는다

**⑤ 확인 근거**(`with_confirmations`) — 변화없음 결과에만, 조사를 다 마친 뒤 붙인다(`SIGNAL_NONE`, 분류는 그대로).
지도에서 전부 확인된 가게와 아무것도 못 찾은 가게가 똑같이 "변화없음"이라 담당자가 구분하지 못했다.

| 경우 | 근거 행 |
|---|---|
| 항목을 확인함 | "주소: DB 값과 일치 — 카카오맵" + 출처 링크 (가게명·주소·전화 중 DB 에 값이 있는 항목마다) |
| 항목을 못 찾음 | "전화번호: 확인할 근거를 찾지 못함" |
| 아무 근거도 없음 | `status` 한 행 "지도·웹에서 이 가게를 찾지 못함 — 영업 여부를 직접 확인하세요" |

조사 중간(지도로 끝낼지 판단 등)에는 붙이지 않는다 — 그 판단은 Signal 이 있으면 변화로 본다.

## 측정

**값 불일치 벤치마크**(`eval/mismatch_bench.py`) — 인허가 영업 60곳을 확인된 DB 처럼 만들고 한 항목만 일부러 틀리게
넣었다(전화 한 자리·건물번호·가게명 오타, 오류 약 34곳 + 대조군).

| 방식 | 잡음 | 값까지 고침 | 가게당 LLM | 시간 |
|---|---|---|---|---|
| 웹검색만 (스위치 끔) | 10 | 9 | 1+ | 20초 |
| 고정 순서 (지도 먼저, 안 되면 웹 1회) | 22 | 3 | 0.7 | 13초 |
| **혼합 (지도 먼저, 안 되면 에이전트)** | 21 | **10** | 3.7 | 52초 |

- 아래 두 줄은 지도 값을 저장하지 않게 바꾼 뒤(2026-10-13, 짝지은 오류 31곳, Gemini 판단). 고정 순서는 "지도와 다름 +
  링크"만 남아 값이 3곳이고, 혼합은 에이전트가 웹에서 같은 값을 찾아 7곳을 되찾았다
- **에이전트 판단 vs 규칙**(2026-10-16, 같은 최신 코드, 각 1회, 다섯 조건 모두 성공한 50곳·오류 29) — 지도 대조·웹검색·
  판정은 같고 "다음에 무엇을 검색할지"만 바꿨다(`--mode hybrid_rule` · `hybrid_rule_anchored` · `hybrid`)

  | 다음 행동을 정한 쪽 | 잡음 | 값까지 고침 | 틀린 값 | 평균 | 웹검색 |
  |---|---|---|---|---|---|
  | 규칙 | 22 | 8 | 0 | 14초 | 45번 |
  | 규칙 + 검색 목적에 주소·전화를 닻으로 | 22 | 8 | 0 | 12초 | 43번 |
  | gpt-6-luna | 22 | 11 | 0 | 23초 | 60번 |
  | gemini-4-argon | 22 | 10 | 0 | 25초 | 50번 |
  | claude-sonnet-5 | 22 | 10 | 0 | 32초 | 58번 |

  잡는 수는 지도가 정해 같다. 값까지 고치는 건 모델이 규칙보다 2~3곳 많고(규칙 8·8, 모델 10·10·11), 모델끼리는 차이가 없다.
  목적 문장을 모델처럼 써도 규칙은 그대로라, 차이는 첫 검색 결과를 보고 다른 항목을 한 번 더 찾는 판단에서 나온 것으로
  보인다(웹검색 횟수가 더 많다). 틀린 값·대조군 오탐은 늘지 않았고 대가는 가게당 10~18초. 각 1회라 반복 측정이 남았다
- 예전 판단 모델 비교(51곳·오류 29, 네이버 값을 담던 코드): 혼합 Gemini 잡음 20·값 9·틀린 값 4 / luna 24·13·7
- 시간 예산 75초(l2): 75초 넘는 가게 14 → 3곳. 백엔드가 75초에 끊을 때 실제로 받는 결과로 잡음 13·값 5 → 18·7
- 흔들림(같은 설정 2회): 잡음은 19·19 로 같고 값은 7·5, 판정이 뒤집힌 가게 8% — 웹에서 값을 되찾는 부분이 흔들린다
- **전화가 약하다**: 전화 오류 7~9곳 중 잡음 3~4, 값까지 1~2. 잡은 곳은 전부 카카오 덕이다 — 카카오에 등록된 가게면
  놓치지 않았고(3/3), 아니면 웹으로 거의 못 잡는다
- 웹검색 오류로 가게가 통째 실패: 6회 실행에서 40건(실행마다 60곳 중 4~11). 25건은 지도·웹 모두 흔적이 없는 가게,
  10건은 429(의도한 실패), 지도 결과를 살릴 수 있던 건 5건

**DB 가 맞는 가게에서 지도가 내는 거짓 "다름"**(일부러 틀리게 넣기 전 값 60곳, 빈 전화 채움 제외)

| | 다름 | 지도에서 전부 못 찾음 |
|---|---|---|
| 동네 조건 넣기 전 | 11곳 | 17곳 |
| 동네 조건 넣은 뒤 | 8곳 | 18곳 |
| **+ 이름 규칙(지점명·바로 옆·&)** | **11곳** | **14곳** |

오류를 잡는 수(전화 3/9·주소 9~10/15·가게명 7/12)는 세 단계 모두 같다. 이름 규칙으로 더 찾게 된 가게 중 3곳은 전화가
DB(인허가)와 달라 "다름"이 늘었다. 남은 11곳: 전화 다름 8(인허가 옛 번호일 수 있음, 1곳은 0502 안심번호) · 서류상 이름
vs 간판 이름 2 · 같은 길 다른 번지 1 — 진짜 변화인지 비교 기준이 오래된 건지 이 자료로는 가릴 수 없다.

**이사 흉내** — 전화번호가 있는 34곳의 DB 주소·좌표를 다른 구의 다른 가게 것으로 바꿔 넣었다. 카카오에 등록돼 있고
번호가 같은 10곳 중 **7곳을 이사로 잡았고 모두 진짜 주소**를 가리켰다. DB 가 맞는 60곳·인허가 폐업 30곳에서 이사로
잘못 잡은 곳은 0. 나머지 24곳은 카카오에 없거나(18) 번호가 다르거나 없었다(6).

**지도에서 전부 못 찾는 비율** — 영업 중 60곳 중 18곳(30%), **인허가 폐업 30곳 중 29곳(97%)**. 폐업 가게는 거의 다
지도에서 사라진다. 다만 영업 중 가게도 30%(이름 규칙 뒤 23%) 가 여기 와서, 우선확인으로 올리면 거짓 신호가 넘친다 →
⑤ 확인 근거의 "찾지 못함"으로만 표시한다.

**카카오 장소 ID 다시 찾기**(멘토 제안의 전제 확인) — 지도 대조로 고른 카카오 장소의 ID 를 저장했다고 치고, 이름 없이 DB
좌표 150m 안 음식점·카페 카테고리 검색(공식 API, 분류당 최대 45곳)만으로 그 ID 가 다시 나오는지 봤다. 영업 중 60곳 중
**37곳에서 ID 를 얻었고 37곳 모두 다시 찾았다**(가까운 순 12번째 안). 100m 로 좁히면 3곳을 놓쳤다 — DB 좌표가 실제
위치에서 100~144m 떨어진 가게다. 이름으로 찾지 않으니 가게명이 바뀌어도 따라간다.

**카카오만 쓰면**(네이버 지역 검색을 끄면, 지도 대조만 비교) — 일부러 넣은 오류는 주소만 10 → 8/15 로 줄고 전화·가게명은
같다. DB 가 맞는 60곳에서 거짓 "다름"(11)·인허가 폐업 30곳의 못 찾음(29)도 같다. 대신 지도에서 확인 못 하는 가게가
14 → 23곳으로 는다. 공식 API 로 찾은 가게는 카카오 37 · 네이버 28(둘 다 19, 네이버만 9, 카카오만 18, 둘 다 없음 14) —
실제 등록은 네이버가 많을 수 있지만, 네이버 지역 검색 API 는 결과를 5개까지만 주고 검색어에 민감하다(류센소 동성로점 0건).
네이버를 끄면 남은 약관 쟁점(목적 제한 1.1)이 사라진다.

## 넣지 않은 것

- **근거 0건이면 재검색**: 근거는 늘지만 수정안은 그대로, 흔들림만 늘었다
- **네이버 블로그 조사 에이전트**(멘토 제안, PR #81): 블로그 글을 읽고 판단 라벨과 링크만 남기게 만들어 쟀지만 주 목표에
  기여가 없었다(잡음 18 → 17, 값 9 → 9, 가게당 +25초). 폐업 신호는 실행마다 흔들렸다. 코드는 로컬 보관 브랜치에만 있다
- **확인할 항목의 DB 값을 웹검색에서 가리기 + 형식 오류 재시도**(각 2회): 틀린 값이 든 검색어는 45% → 26·39% 로
  줄었지만 잡음·값까지 고침이 같았다(그런 가게는 웹에 정보 자체가 적다). 가게명을 가리면 같은 건물의 다른 가게를 잡았다
- **웹검색이 실패해도 지도 결과 유지**: 살릴 수 있는 가게가 6회에 5곳이고, 웹 확인을 못 한 가게가 변화없음으로 나간다
- **네이버 검색 화면의 전화번호**: 60곳 중 32곳을 찾았지만 절반(16)이 0507 안심번호라 비교할 수 있는 건 약 11곳.
  검색 화면 자동 수집은 robots.txt 가 막는다. 검색어에 동 이름을 붙이면 장소 정보가 안 나온다
- **비즈노·국세청으로 주소 확인**: 둘 다 응답에 주소가 없다(비즈노는 상호·번호·상태·폐업일뿐, 대표자명 검색은 유료)
- **인허가 자료로 이사 찾기**: 2024년 이후 대구 폐업 9,245건 중 6개월 안에 다른 주소에서 같은 이름으로 신고된 588건은
  행사 임시 매장·체인점 지점이었다. 같은 주소에서 같은 이름으로 다시 신고한 528건(6%)은 주인만 바뀐 서류상 폐업으로
  보인다 — 서류상 폐업만 믿으면 영업 중인 가게를 폐업으로 올린다
- **웹으로 폐업 잡기**: 간이 DB 폐업 30곳 중 신호 1곳

## 보류 (효과는 확인, 팀 결정 필요)

- **블로그 장소 카드로 최근 영업 흔적 확인** — 블로그 글에 붙은 네이버 장소 카드(`.se-placesMap`)의 가게명·도로명이 DB 와
  같고 90일 안에 쓴 글이면 "최근 방문 리뷰 + 링크". LLM 없이 가게당 9초. 영업 중 60곳 중 15곳에서 찾고, 인허가 폐업
  30곳에는 0곳(본문 글자로 맞추면 흔한 이름·길안내 언급으로 오탐이 났다). 분류를 바꾸지 않는 근거라 쓰려면
  "담당자 확인일(`lastCheckedAt`)과 별도 날짜"를 둘지 팀이 정해야 한다 — 확인일은 담당자가 직접 확인한 시각이고
  국세청 확인도 건드리지 않는다

- **카카오 장소 ID 추적**(멘토 제안, 2026-10-15) — 이름으로 매번 검색하지 말고, 한 번 찾은 지도 장소 ID 를 저장해 두고
  그 장소가 아직 있는지만 본다. 카카오 담당자는 장소 ID·링크 저장을 허용한다고 답했다(값은 불가, 아래 약관).
  - 처음 한 번: 지도 대조로 카카오 장소를 고르고 담당자가 확인 → ID 저장. 지금 규칙으로 60곳 중 37곳(62%). 못 고른
    23곳 중 상당수는 카카오 미등록이거나 DB 좌표가 어긋난 가게. 애매한 후보는 담당자가 고른다 — 카카오 값은 LLM 에
    보낼 수 없어 이 매칭을 에이전트(LLM)에 맡길 수 없다
  - 그 뒤: DB 좌표 150m 안 카테고리 검색으로 ID 확인. 있으면 값 비교(지금과 같음), **없으면 "지도에서 사라짐"** —
    이름 검색의 "못 찾음"(영업 중 23~30%)과 달리 영업 중 가게에서 거짓으로 나온 적이 없다(37/37)
  - 모르는 것: 카카오가 문 닫은 가게를 실제로 지우는지. ID 를 저장해 두고 시간이 지나야 확인된다
  - 필요한 것: 백엔드에 장소 ID(또는 링크) 칸, AI 요청에 그 값을 실어 주기
  - 네이버: 장소 페이지는 자동 접근을 막는다(12곳 모두 차단). 문 닫은 가게 8곳의 옛 블로그 장소 카드에서 꺼낸 네이버 장소
    ID 는 7곳이 검색 결과에서 사라졌고, 남은 1곳(카페동이 2호점)은 같은 ID 가 다른 이름("수성1가점")으로 살아 있었다 —
    인허가로만 폐업인 가게로 보인다

## 정하지 않은 것 (팀 결정)

- ⑤ 확인 근거(`SIGNAL_NONE`)를 백엔드·프론트가 변화로 다루는 곳이 없는지, 변화없음 카드에 근거가 여러 줄 붙어도 되는지
