# 2차 조사 — 웹검색으로 가게 정보 불일치 찾기

PROMPT-88 · 갱신 2026-09-30

> 반복 검색의 변동성, 제한형 재검색, 상충 근거 처리 방안은
> [`2차_조사_불확실성_처리.md`](2차_조사_불확실성_처리.md)를 참고한다.

## 무엇을 하나

1차 조사(백엔드, 매일 새벽 국세청 대조)에서 **변화가 잡히지 않은 가게**를 웹에서 다시 확인해, 우리 DB 값과
다른 것을 찾아 **수정안**으로 올린다. 가게 정보는 담당자가 승인해야 바뀐다.

- 주 목표는 **주소 · 전화번호 · 상호명의 값 불일치**다. 영업 상태(폐업)도 보지만 웹검색으로는 거의 못 잡는다
- 표기 차이(`대구` ↔ `대구광역시`, `053-111-2222` ↔ `053)111-2222`)는 같은 값으로 본다
- 대상은 **백엔드가 골라 보낸다** — `statusMismatch`(1차에서 우선확인)·`dataProblem`(번호부터 찾을 가게)이
  아닌 가게. AI 는 받은 가게를 다시 거르지 않는다

```
담당자 가게 선택 → 백엔드: 1차 결과로 나눔 → 2차 대상만 가게 하나씩 POST /investigations
AI (가게 하나):  (지도 대조) → ① 관측 수집 → ② 카카오맵 확인 → ③ 규칙 분류 → StoreFinding
```

지도 대조를 켜면(`NAVER_LOCAL_ENABLED`·`KAKAO_COMPARE_ENABLED`, 기본은 꺼짐) **지도를 먼저 보고**, 지도만으로
변화가 잡히거나 DB 값이 전부 확인되면 ① 웹검색을 건너뛴다(아래 "지도 대조와 에이전트").

| 단계 | 파일 | LLM |
|---|---|---|
| 흐름·재시도 | `src/investigation/web.py` | – |
| 지도 대조 | `src/investigation/map_lookup.py` | 없음 |
| ① 관측 수집 | `src/investigation/web_research.py` | Gemini 1회 + 구글 검색 그라운딩 |
| ② 카카오맵 확인 | `src/investigation/kakao_map.py` | 없음 |
| ③ 규칙 분류 | `src/investigation/classify.py` | 없음 |
| 입출력 형식 | `src/investigation/models.py` | – |

**모델은 "웹에서 본 값을 근거와 함께 적어 오기"만 하고, 판단은 규칙이 한다.** 모델의 확신도로 가르지
않는다(멘토 결정). 순서도 코드가 정한다 — LLM 이 도구를 고르는 에이전트(`agent.py`)는 만들어 쟀지만 채택하지
않았다(아래).

## ① 관측 수집

1. 가게 이름·주소·전화(DB 값)를 주고 네 항목(`status`·`phone`·`address`·`name`)을 한 줄에 하나씩
   `항목 | 값 | 근거 문장 | 날짜` 로 적게 한다. "바뀌었는지 판단하지 말고 본 것만"
2. 줄을 읽는다. 약속을 어긴 줄·빈 표시(`없음`, `(모름)`)는 그 줄만 뺀다. 상태는 OPEN/SUSPENDED/CLOSED,
   한글은 뜻이 하나로 정해지는 말만(`폐업`→CLOSED, `임시 휴업`→SUSPENDED; `영업 종료`·`휴무`는 안 받음)
3. **출처는 모델이 적은 URL 을 쓰지 않는다.** 구글이 붙여 주는 `grounding_supports`(응답의 어느 **UTF-8 바이트
   구간**이 어느 검색 결과에 근거하나)로 줄마다 검색 결과를 잇고, 리다이렉트 주소는 원래 URL 로 푼다
4. 재시도(`web.py`): 형식 이탈·출처 0개면 1번 더, 429 면 5초·15초 기다렸다 다시. 그래도 안 되면 그 가게는 실패
5. 모델이 쓴 검색어(`web_search_queries`)를 결과(`ResearchResult.queries`)에 남긴다. 판정에는 쓰지 않고, 결과가 흔들릴 때
   검색이 달라진 것인지 추출이 달라진 것인지 가리는 데 쓴다. 측정 시트(`mock_round`)의 `검색어` 칸에 기록된다

## ② 카카오맵 확인

`KAKAO_REST_API_KEY` 가 있으면 DB 좌표(없으면 DB 주소 → 좌표) 반경 150m 안에서 상호로 찾는다(법인 표기·괄호를
뺀 이름, 한쪽이 다른 쪽을 품으면 같음).

| 결과 | 쓰임 |
|---|---|
| `FOUND` + `placeUrl` | 영업 방증. 폐업·이전·상호 변화에 "지도에는 원래대로 있음 — 다른 가게 정보일 수 있음" 표시 |
| `NOT_FOUND` | **폐업 근거가 아니다** (영업 가게의 절반 가까이도 못 찾는다) |
| `NO_COORDINATES` · `UNAVAILABLE` | 아무것도 하지 않는다. 조사를 막지 않는다 |

분류는 바꾸지 않는다. 카카오 응답에서 남기는 건 상태와 `placeUrl` 뿐이고 모델에 넘기지 않는다 — 카카오맵
담당자 답변(데브톡, 2026-09): 실시간 비교 후 폐기·장소 URL 저장은 허용, 장소명·가공 데이터 저장과 외부 LLM
전송은 불허. 지금은 쓸 만한지 재는 단계라 정식으로 쓰기 전에 다시 확인한다.

## ③ 규칙 분류

**판정에서 빼는 관측**

- 출처가 이어지지 않은 관측 — 사람이 검증할 수 없다
- 가게 번호가 될 수 없는 전화 — 15xx·16xx·18xx 대표번호, 080, 자릿수가 틀리거나 끝자리가 넘치는 번호
- DB 가 도로명 주소일 때의 지번 주소 관측 — 같은 곳인지 가릴 수 없다
- 번지까지 없는 주소 — `수성구 범어동 3층` 처럼 검색 요약에서 잘린 주소다(도로명+건물번호, 또는 동·리+번지가 있어야 한다)
- **담당자 확인일(`lastCheckedAt`)보다 확실히 이전에 쓰인 근거** — 그 뒤에 사람이 본 DB 값이 더 믿을 만하다. 연·월만 아는
  날짜는 그 기간의 끝으로 보고, 날짜를 모르는 근거는 남긴다(그라운딩 근거의 2/3 가 날짜가 없다). 확인일이 안 오면 거르지 않는다

**같은 값인가** (`comparison_key`)

| 항목 | 비교 | 같다고 보는 예 |
|---|---|---|
| 전화 | 문장에서 번호 하나를 뽑아 `053-111-2222` 표준 표기로(DB 번호도 같은 규칙) | `+82 53-111-2222`, `(053) 111-2222`, `053-111-2222 (예약)` |
| 주소 | 도로명 + 건물번호. 도로명 속에 끼어든 "광역시"는 되돌림 | `대구광역시 중구 동성로 12, 1층` = `대구 중구 동성로12`, `동대구광역시로 590` = `동대구로 590` |
| 상호 | 괄호 병기·지점명 앞 지역어 제거. 한쪽이 다른 쪽의 **앞부분이고 남는 부분이 업종·지점 표기**면 같음. 그 밖에 한쪽이 다른 쪽을 품기만 하면 **판단 보류**(확인 근거로도 변화로도 안 셈) | `삼송빵집` = `삼송빵집 본점`, `크라운호프대구수성못점` = `크라운 호프 수성못점`, `최과장` ↔ `최과장회닾밥` 은 보류 |
| 상태 | 값 그대로 | |

**변화인가**

- DB 와 다른 값이 있으면 변화다. DB 값이 비어 있으면 찾은 값이 곧 변화다(빈칸 채우기)
- 예외: **DB 상태가 UNKNOWN·없음일 때 웹의 OPEN 은 변화가 아니다.** OPEN 근거는 대부분 목록 사이트의
  "영업시간" 문장이라 폐업 뒤에도 남는다. CLOSED·SUSPENDED 는 변화다
- 다른 값이 여럿이면 **서로 다른 도메인이 가장 많은 값**을, 같으면 **가장 최근 글의 값**을 제안한다. 표기는 가장 흔하고 짧은 것
- **DB 값이 맞다는 가장 최근 근거보다 확실히 오래된 다른 값은 올리지 않는다** — 예전 번호·옛 표기·오타가 최신 확인을
  이기지 않게 한다. 날짜를 모르는 다른 값은 낡았다고 보지 않는다
- 날짜는 모델이 적은 것을 `YYYY-MM-DD`·`YYYY-MM`·`YYYY` 로 고쳐 쓴다. 날짜가 아닌 말("맛집검색", 실측)은 버린다

**결과**

| | 담는 것 |
|---|---|
| `Signal` (변화 하나당 1행) | `signalType=SIGNAL_HIGH`, `confidence=null`, `field`(어느 수정안 항목인가), 대표 근거(`evidenceText`·`evidenceUrl`). 근거 끝에 "(출처 N곳)"(그 값을 가리킨 도메인 수), 출처끼리 엇갈리면 "(다른 값을 가리키는 출처도 있음)" |
| `classification` | 변화가 있으면 `PRIORITY_CHECK`(우선확인), 없으면 `NO_CHANGE`(변화없음) |
| `proposedChanges` | 변화마다 새 값. 예: `{"phone": "053-964-0022"}` |

응답은 백엔드 `Task`·`Signal` 칸 그대로다(`백엔드_연동.md`). 규칙이 쓰는 `observed`·`sourceCount`·`mapCheck`
(② 의 결과)는 AI 안에만 있고 응답에서는 뺀다 — 백엔드에 칸이 없다.

- **신호에 등급을 두지 않는다** — 담당자가 승인하므로 출처 1곳짜리도 올리고, 판단 재료로 출처 수를 근거 문구에 적는다
- DB 값을 확인한 근거·지도 확인·"근거 없음"은 이상 징후가 아니라 **Signal 로 만들지 않는다.** 변화가 없으면 0행
- **추가확인은 AI 가 돌려주지 않는다.** 팀 합의로 분류는 이렇다

| 분류 | 정의 | 정하는 곳 |
|---|---|---|
| 우선확인 | 1차에서 국세청 변화 + 2차에서 변화 | 백엔드(1차) · AI(2차) |
| 추가확인 | 변화없는 매장 중 직접 확인한 지 90일 이상 | 백엔드 (`Store.lastCheckedAt`) |
| 변화없음 | 그 밖 | |

## 이상해 보이는 규칙이 왜 있나

대부분 실제 호출이나 경계값 검증에서 틀린 결과가 나와서 생겼다. 규칙마다 회귀 테스트가 있다.

| 규칙 | 없었을 때 |
|---|---|
| 출처를 모델 URL 대신 그라운딩으로 | 모델이 적은 URL 15개 중 13개가 검색 결과에 없는 주소 |
| 응답을 JSON 대신 줄 형식으로 | JSON 이면 그라운딩이 9번 중 1번만 붙어 전부 "출처 없음" → 조용히 변화없음 |
| 바이트 오프셋으로 출처 잇기 | 문자 기준으로는 0/40 이 맞음 — 출처가 엉뚱한 줄에 붙음 |
| 상태 UNKNOWN + OPEN 은 변화 아님 | 우선확인이 "영업시간 적힌 가게"로 가득, 폐업 가게를 "영업 중"으로 제안 |
| 전화번호 표준화·자릿수 검사 | 영화관 대표번호 제안, 잘린 `0507-5256-540` 제안, `053-111-2222 (2층)` 이 `053-1112-2222` 로 |
| 도로명 붙여 쓰기, 지번 비교 안 함 | `대종로 480번길` ↔ `대종로480번길` 이 "이전", 지번 한 건 때문에 엇갈림 |
| 상호 괄호 병기 제거·포함 관계 | `성심당(聖心堂)`, `삼송빵집 본점` 이 "상호 변경" |
| 상호 포함 관계는 앞부분+업종·지점 꼬리만 같음, 나머지는 보류 | 웹의 잘린 이름 `최과장` 이 DB 의 오타 `최과장회닾밥` 을 "확인"해 오류를 놓침(불일치 벤치마크) |
| 지점명 앞 지역어 제거, 도로명 속 "광역시" 되돌림 | `크라운 호프 수성못점` 을 "상호 변경", 모델이 적은 `동대구광역시로` 를 "이전"으로 제안(불일치 벤치마크) |
| 지도에서 찾으면 어긋나는 변화에 표시 | 케이블카 안 식당에 케이블카 주소를 "이전"으로 제안 |
| 날짜: 같은 출처 수면 최신 값, 최신 확인보다 오래된 값 무시, 확인일 이전 근거 제외 | 블로그(도메인 하나)에서 2019 번호가 2020 번호를 이김, 2026-09 글은 DB 상호인데 2026-07 오타가 "상호 변경", 2022 글의 깨진 주소를 "이전"으로 제안(네이버 실험) |
| 번지 없는 주소 제외 | `수성구 범어동 3층`(잘린 요약)을 "이전"으로 제안(네이버 실험) |

## 지도 대조와 에이전트

**지도 대조**(`map_lookup.py`) — 지도에 지금 등록된 상호·주소·전화를 관측으로 가져온다. 담당자가 지도에서 가게를
찾아 대조하던 일이다. LLM 을 쓰지 않는다.

| 출처 | 가져오는 것 | 저장 |
|---|---|---|
| 네이버 지역 검색 API (NAVER API HUB) | 상호·도로명 주소(전화는 빈 값) | 수정안에 값을 담는다 — API 약관 원문 확인 전 |
| 카카오 로컬 키워드 검색 (DB 좌표 150m) | 상호·도로명 주소·전화 | **담지 않는다** — 실시간 비교 후 폐기만 허용. 카카오만 다른 값을 가리키면 Signal(근거 "카카오맵에 등록된 값 — DB 값과 다름, 링크에서 확인")만 남고 수정안에는 오르지 않는다 |

같은 가게 고르기: 상호가 비슷하고(포함 관계 또는 글자 유사도 0.6 이상, 두 글자 이하는 정확히 같음) 시·도와
구·군이 같은 후보만. 주소만 같은 후보는 고르지 않는다(같은 건물의 다른 업체를 잡았다).

**고정 순서**(`web.py`) — 지도 대조 → `coverage()` 가 changed·confirmed 면 끝, unresolved(못 찾음·일부만 확인)면
웹검색을 더한다. 카카오는 한 경로만 부른다 — 값 대조가 켜져 있으면 ② 카카오맵 확인("근처에 있다/없다")은 하지 않는다.

**혼합 방식**(`AGENT_ENABLED`, 기본 꺼짐) — 지도로 확정되면 규칙으로 끝내고, 확정되지 않은 가게(못 찾음·일부만
확인·카카오에만 다른 값)만 에이전트가 지도 결과를 받아 이어서 조사한다(`continue_from` — 웹에서 무엇을 더 찾을지 판단).
카카오에만 다른 값은 웹에서 실제 값을 확인하면 수정안에 값을 담을 수 있다.

**에이전트 단독**(`agent.py` 의 `investigate`) — LLM 이 `check_maps` · `web_search(항목 또는 all, 목적)` · `finish` 를 골라
부른다(도구 4번, 웹검색 2번 상한). 카카오 값은 판단 모델에 넘기지 않고 "일치·다름·못 찾음"만 알린다. 판단 모델은
기본 Vertex Gemini, `AGENT_MODEL` 을 주면 OpenAI 호환 Responses API(카테캠 프록시 gpt-6-luna)다. 웹검색은 늘
Vertex 그라운딩이다.

**값 불일치 벤치마크**(`eval/mismatch_bench.py`) — 인허가 영업 60곳을 확인된 DB 처럼 만들고 한 항목만 일부러
틀리게 넣었다(전화 한 자리, 건물번호 +2, 상호 모음 오타). 같은 58곳(오류 34곳) 결과:

| | 잡음 | 값까지 담은 수정안 | 대조군 깨끗(24) | LLM 호출(가게당) | 시간 |
|---|---|---|---|---|---|
| 웹검색만(원래) | 10 | 9 | – | 1+ | 20초 |
| **고정 순서** | **22** | 11 | 19 | **0.5** | **7초** |
| 에이전트 · Gemini 판단 | 20 | 13 | 19 | 4.2 | 27초 |
| 에이전트 · gpt-6-luna 판단 | 22 | 12 | 19 | 4.1 | 25초 |
| 혼합 · gpt-6-luna 판단 (2회) | 23 / 20 | 14 / 12 | 19 | 2.7 | 19초 |

- 지도 근거가 대부분을 잡는다(주소는 네이버, 상호는 카카오). 전화는 약하다(9곳 중 3곳)
- 에이전트 단독은 고정 순서보다 더 잡지 못하고 LLM 호출이 8배다
- **혼합**은 잡은 수가 고정 순서와 사실상 같고(평균 21.5 대 22), 값까지 담은 수정안이 평균 2곳 많다(카카오에만
  다른 값을 웹으로 확인). 대신 60곳 중 45곳이 에이전트로 넘어가 LLM 이 고정 순서의 6배다 — 카카오 상호 표기가 조금씩
  달라 "카카오에만 다른 값"이 자주 생긴다. 다음은 에이전트로 넘기는 조건을 좁히는 것(남은 것 2)
- **판정 흔들림**(같은 설정 2회): 고정 순서 판정 뒤집힘 2%·오류 탐지 변화 0곳, 혼합 3%·3곳. 웹검색만 쓰던 때(13~18%)보다
  지도 대조가 결과를 크게 안정시킨다
- 표본이 작다(항목별 9~15곳)

## 측정

`gemini-2.5-flash`, 가게당 5~40초. 실데이터가 아직 DB 에 없어 **간이 DB** 로 잰다.

**간이 DB** (`eval/mock_db.py`) — 대구 일반음식점 인허가(LOCALDATA)에서 폐업 30곳(폐업 1~18개월 전)·영업 30곳을
뽑아, `nts-checks` 응답 행 모양(`store` 칸 + 국세청 칸)으로 만든 것. 결함은 선한영향력가게 명단을 따라 넣었다 —
`phone=null`, `internalStatus=UNKNOWN`, 10% 는 지번 주소. 즉 **처음 적재한 직후**의 모습이다.

| | 폐업 30 | 영업 30 |
|---|---|---|
| 우선확인 | 4 | 12 |
| 폐업·휴업 변화 | 1 | 1 |
| 카카오맵에서 찾음 | 0 | 16 |

- 우선확인은 거의 전부 **출처 1곳짜리 전화번호 채우기**다(Signal 19행 중 18행이 출처 1곳). 인허가 번호가 있는 11건 중 7건 일치
- **폐업은 웹검색으로 거의 못 잡는다** — 폐업 30곳 중 23곳은 구글 검색 결과 자체가 0개. 근거 출처에 네이버 블로그는
  0건이고, 프롬프트로 네이버를 찾게 해도(40회) 0건이었다. 네이버 검색 API 는 2026-09-07 개정 약관(목적 제한·AI
  입력 금지, 기사 기준)과 부딪혀 쓰지 않는다
- **카카오맵에 있으면 영업 중이 16/16** 맞았다. 없다고 폐업은 아니다(못 찾은 44곳 중 14곳이 영업)
- 같은 60곳을 두 번 돌리면 **8곳(13%) 판정이 뒤집힌다** — 변화없음은 "이번에 못 찾음"일 수 있다
- 주 목표(값 불일치)는 위 "값 불일치 벤치마크"로 잰다

## 돌려 보기

```bash
uv run --with pyproj python -m eval.mock_db --n 30      # 간이 DB (좌표 변환에 pyproj)
uv run python -m eval.mock_round run --tag v1           # Vertex·카카오 호출, 관측 원본까지 시트에 저장
uv run python -m eval.mock_round reclassify --tag v1 --out v2   # 규칙만 고쳤을 때 — Vertex 없이 다시 분류
uv run python -m eval.mock_round map --tag v1 --out v2          # 카카오맵 확인만 새로
uv run python -m eval.mock_round grade --tag v2

uv run --with pyproj python -m eval.mismatch_bench build --n 60   # 값 불일치 벤치마크
uv run python -m eval.mismatch_bench run --tag f1 --mode fixed     # web · fixed · agent
uv run python -m eval.mismatch_bench grade --tag f1
```

결과 시트·인허가 파일·간이 DB 는 `eval/fixtures/`(커밋 금지)에 둔다. 단위 테스트(`tests/investigation/`)는 전부
가짜 응답으로 돈다.

## 남은 것

1. **지도 대조 운영 투입** — 스위치로 넣었다(기본 꺼짐). 네이버 검색 API 약관 원문 확인, 카카오 "신호만" 결과를
   담당자 화면에 어떻게 보일지(백엔드·프론트)가 남았다. 전화 확인 보강, 벤치마크 확대(전화 사례가 9곳뿐)
2. **에이전트** — 단독은 채택 기준 미달. 혼합 방식(`AGENT_ENABLED`)은 값까지 담은 수정안이 늘지만 LLM 6배라, 에이전트로
   넘기는 조건을 좁혀(예: 카카오 상호 표기만 다른 경우는 넘기지 않음) 다시 잰다. 이전의 재검색(근거 0건이면 "검색어를 넓혀 다시 찾아라" 지시를 붙여 한 번 더)은 **시도했지만 채택하지 않았다**(2026-10-05).
   간이 DB 60곳을 재검색 켜고 2번·끄고 2번 돌린 결과 근거를 찾은 가게는 23·24곳 → 30·28곳으로 늘었지만 수정안은
   19·18건 → 16·20건으로 늘지 않았고, 같은 설정끼리 판정 뒤집힘은 18% → 24%, 시간은 15초 → 24초였다. 재검색에서만 나온
   제안에 시설 오인(수성포차에 호텔 대표번호·"호텔 수성")이 섞였다. 모델은 첫 호출에서 이미 "폐업"·"전화번호"·동 이름
   변형으로 5~20번 검색하고 있어(`web_search_queries`) 지시가 같은 검색을 되풀이했다. 검색어 기록은 남겼다.
   다음은 가게 전체가 아니라 **항목·목적을 좁힌 재조사**(불확실성 문서 §6.1)나 같은 가게인지 확인(§8.1)이다.
   카카오맵 확인은 약관상 에이전트 밖에 둔다
3. **상호 규칙** — 앞부분+업종·지점 꼬리만 같음으로 좁혔다(나머지 포함 관계는 판단 보류). `안다미로` ↔ `밥안다미로`
   는 이제 보류라 변화로 잡히지도 않는다 — 보류를 담당자에게 어떻게 보여 줄지는 "확인됨/못 찾음" 응답 형식과 함께 정한다
4. **한계로 둔 것** — 웹에 흔적이 없는 가게, 시설 안 가게(부모 시설을 조사함), 모델이 해석을 섞음("운영 여부 확인
   안 됨"을 SUSPENDED 로), 그라운딩 근거 대부분은 날짜가 없어 날짜 규칙이 닿지 않음, 호출마다 결과가 흔들림
5. **백엔드·프론트 연동** — 조사 시작·AI 호출·결과 저장·조회가 비어 있다. 요청할 것은
   [`백엔드_연동.md`](백엔드_연동.md)
