# 2차 조사 — 가게 정보 불일치 찾기

PROMPT-88·115 · 갱신 2026-10-08 · 백엔드와 주고받는 형식은 [`백엔드_연동.md`](백엔드_연동.md)

## 목적

1차 조사(국세청 대조)에서 변화가 없던 가게를 지도·웹으로 다시 확인해, DB 와 다른 **주소·전화·상호**를 수정안으로
올린다. 담당자가 직접 찾아 대조하던 수고를 덜어 주는 게 목적이고, 반영은 담당자가 승인한다.
**모델은 조사만, 판단은 규칙이** 한다(모델 확신도는 쓰지 않음 — 멘토 결정).

## 흐름

```
가게 1곳
  ① 지도 대조 — 네이버 지역 검색·카카오, LLM 없음        [NAVER_LOCAL_ENABLED · KAKAO_COMPARE_ENABLED]
       └ 지도만으로 확정되면 ③으로
  ② 미확정이면  에이전트가 이어서 조사(혼합 방식)          [AGENT_ENABLED]
               아니면 웹검색 1회(Gemini + 구글 그라운딩)
  ③ 규칙 판정 → 응답(task·signal 형식)
```

- 스위치는 모두 기본 꺼짐. 끄면 **웹검색 → 카카오맵 "근처에 있다/없다" 확인 → 규칙 판정**(기존 동작)
- 파일: 흐름 `web.py` · 지도 `map_lookup.py` · 웹검색 `web_research.py` · 에이전트 `agent.py` · 판정 `classify.py`

## 단계 요약

**① 지도 대조** — 지도에 등록된 상호·주소·전화를 가져온다. 상호가 비슷하고 같은 지역인 후보만 같은 가게로 본다
(주소만 같으면 같은 건물의 다른 업체라 제외). DB 값이 전부 확인되거나 다른 값이 나오면 확정.
카카오 값은 약관상 저장 불가 → 판정에만 쓰고, 카카오만 다른 값이면 수정안 없이 "카카오맵과 다름 + 링크"만 남긴다.

**② 웹검색** — DB 값을 주고 `항목 | 값 | 근거 | 날짜` 로 받는다. 출처는 모델이 적은 URL 이 아니라 그라운딩 결과로
잇는다. 형식이 깨지면 1번 더, 429 면 기다렸다 다시. 모델이 쓴 검색어를 기록한다.

**② 에이전트(혼합 방식)** — 지도로 확정 안 된 가게(못 찾음·일부만 확인·카카오에만 다른 값)만 받아, 웹에서 무엇을 더
찾을지 고른다(`web_search(항목, 목적)`·`finish`, 웹검색 최대 2번). 카카오 값은 판단 모델에 넘기지 않는다.
판단 모델은 기본 Vertex Gemini, `AGENT_MODEL` 이면 카테캠 프록시(gpt-6-luna, Responses API). 웹검색은 늘 Vertex 그라운딩.

**③ 규칙 판정**
- 빼는 관측: 출처 없음, 가게 번호가 아닌 전화(15xx 등), 번지 없는 잘린 주소, `lastCheckedAt`(선택 입력)보다 확실히 이전 근거
- 같은 값: 전화는 표준 표기로, 주소는 도로명+건물번호로, 상호는 괄호·지점명 앞 지역어를 빼고 비교.
  한쪽이 다른 쪽의 앞부분 + 업종·지점 꼬리면 같음, 그 밖의 포함 관계(`최과장` ↔ `최과장회닾밥`)는 **판단 보류**
- 값 고르기: 출처 많은 값 → 같으면 최근 글. DB 값을 확인해 주는 최근 근거보다 오래된 다른 값은 무시
- 상태를 모를 때 웹의 "영업 중"은 변화로 보지 않는다(폐업 뒤에도 남는 영업시간 문장)

**응답** — `classification`(우선확인/변화없음) · `proposedChanges` · `signals[]`(변화당 1행, 근거 끝에 "(출처 N곳)") ·
`failure{code, message}`. 추가확인(확인 90일 경과)은 백엔드가 정한다.

## 측정 (값 불일치 벤치마크)

인허가 영업 60곳을 확인된 DB 처럼 만들고 한 항목만 일부러 틀리게 넣어(전화 한 자리·건물번호·상호 오타) 측정
(`eval/mismatch_bench.py`, 오류 34곳).

| 방식 | 잡음 | 값까지 담은 수정안 | 가게당 LLM | 시간 | 판정 흔들림 |
|---|---|---|---|---|---|
| 웹검색만 (기본) | 10 | 9 | 1+ | 20초 | 13~18% |
| **고정 순서** (지도 대조 켬) | **22** | 11 | **0.5** | **7초** | **2%** |
| 혼합 (gpt-6-luna 판단) | 21.5 | **13** | 2.7 | 19초 | 3% |
| 에이전트 단독 | 20~22 | 12~13 | 4.1~4.2 | 25초 | – |

방식별 로직 — 쓰는 도구(지도 대조·웹검색)와 판정(규칙)은 같고, **다음에 무엇을 할지 누가 정하느냐**가 다르다.
- **웹검색만**: 모든 가게에 웹검색 1회를 돌리고 판정
- **고정 순서**: 코드가 정한 순서. 지도 대조(카카오맵 + 네이버) → 지도만으로 확정(DB 값 전부 확인 또는 다른 값 발견)되면 끝,
  발견되지 않은 건에 대해서 웹검색 1회를 더하고 판정
- **혼합**: 지도 대조까지는 고정 순서와 같다. 확정되지 않은 가게(못 찾음·일부만 확인·카카오에만 다른 값)만 에이전트가
  지도 결과를 받아 웹에서 무엇을 더 찾을지(항목·목적, 최대 2번) 스스로 정한 뒤 판정
- **에이전트 단독**: 처음부터 LLM 이 도구를 고름 : 지도 대조, 웹에서 무엇을 찾을지, 언제 끝낼지.
  쉬운 가게에도 판단 호출을 써서 LLM 이 가장 많다

- 지도 대조가 탐지를 두 배로 늘리고 결과를 안정시킨다. 전화는 약하다(9곳 중 3곳)
- 혼합은 잡는 수가 같고 값까지 담은 수정안이 2곳 많지만, 60곳 중 45곳이 에이전트로 넘어가 LLM 이 6배
- 대조군 오탐(24곳 중 5곳)은 셋 다 비슷하고, 일부는 정답(인허가 옛 번호) 쪽 문제. 표본이 작다

**넣지 않은 것**
- 근거 0건이면 재검색: 근거는 늘지만 수정안은 그대로, 판정 흔들림만 증가(모델이 이미 첫 호출에 5~20개 검색어를 씀)
- 네이버 블로그 직접 보기: 폐업 신호는 잡았지만 약관 위반이라 실험만. 여기서 날짜 규칙·잘린 주소 규칙이 나왔다
- 폐업은 웹으로 거의 못 잡는다(간이 DB 폐업 30곳 중 신호 1곳) — 주 목표가 아니다

## 외부 출처와 약관

- **카카오 로컬**: 실시간 비교 후 폐기·장소 링크 저장만 허용, 값 저장·LLM 전송 불가
- **네이버 지역 검색**(NAVER API HUB): 검색 API 약관(목적 제한·AI 입력·저장 금지)은 기사 기준, **원문 미확인**
- **네이버 블로그·플레이스 자동 수집**: 이용약관이 금지, robots.txt 차단, 플레이스는 첫 요청에 차단하는 상태.
- **카테캠 프록시**: 그라운딩을 못 써 에이전트 판단에만 사용

## 정하지 않은 것 (팀 결정)

- 엇갈리는 근거를 지금처럼 하나 골라 제안할지, 후보를 모두 보여 주고 수정안을 비울지
- 결과를 **수정 필요 / 직접 확인 필요 / 확인됨**으로 나눠 보일지 — 지금은 "확인됨"과 "못 찾음"이 둘 다 변화없음
- 판단 보류(잘린 상호 등)를 어떻게 보일지

## 남은 것

1. 혼합 방식에서 에이전트로 넘기는 조건 좁히기(카카오 상호 표기만 다른 경우 제외 등)
2. 에이전트 판단 로그 보기 — 45곳이 넘어간 원인이 넘기는 조건인지, 가게당 판단 횟수인지
3. 판단 모델 비교 — 혼합 방식을 여러 모델 판단으로 측정(지금은 gpt-6-luna 만)
4. 오탐·전화 사례 열어 보기, 벤치마크 데이터 확대(전화 사례·실제 같은 오류)
5. 같은 가게 확인(시설 오인 — 수성포차 ↔ 호텔수성)
6. 카카오맵, 네이버 API 사용을 어떻게 둘지
