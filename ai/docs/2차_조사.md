# 2차 조사 — 가게 정보 불일치 찾기

PROMPT-88·115·145·154 · 갱신 2026-10-27 · 백엔드와 주고받는 형식은 [`백엔드_연동.md`](백엔드_연동.md)

## 목적

1차 조사(국세청 대조)에서 변화가 없던 가게를 지도·웹으로 다시 확인해, DB 와 다른 **주소·전화·가게명**을 수정안으로
올린다. 담당자가 직접 찾아 대조하던 수고를 덜어 주는 게 목적이고, 반영은 담당자가 승인한다.
**모델은 조사만, 판단은 규칙이** 

**전제 — 실제로 바뀐 가게는 극소수다.** 그래서 많이 잡는 것보다 ① 안 바뀐 가게를 바뀌었다고 올리지 않는 것,
② 대다수인 변화없음 가게를 담당자가 빨리 넘기게 해 주는 것이 중요하다. 벤치마크는 60곳 중 36곳에 오류를 넣은 것이라
이 전제와 거꾸로다 — 거짓 신호는 "DB 가 맞는 가게"로 따로 잰다(아래 측정).

## 흐름

```
가게 1곳
 ① 지도 대조                        [NAVER_LOCAL_ENABLED · KAKAO_COMPARE_ENABLED]
    네이버 "가게명 + 구" · 카카오 DB 좌표 150m 안
    카카오 근처에 없으면 → 반경 없이 다시 찾아 전화번호가 같은 가게 = 이사
 ② DB 값(가게명·주소·전화)이 전부 지도와 같으면 끝
 ③ 아니면 에이전트가 이어서 웹검색 [AGENT_ENABLED · AGENT_MODEL]
    지도에서 "다름"·"못 찾음"인 항목만, 최대 2번, 가게당 75초 안
 ④ 규칙 판정 → 우선확인 / 변화없음
 ⑤ 변화없음이면 항목마다 확인 근거를 붙인다 (일치 / 찾지 못함)
```

- **의도한 동작은 스위치를 모두 켠 것**이다. 끄면 "웹검색 1회 → 카카오맵 근처에 있다/없다 → 규칙 판정"(옛 동작).
- dev 배포는 저장소 변수 `AI_NAVER_LOCAL_ENABLED`·`AI_KAKAO_COMPARE_ENABLED`·`AI_AGENT_ENABLED` 로 켠다(`deploy-dev.yml`).
  비우면 꺼진다.
- 파일: 흐름 `web.py` · 지도 `map_lookup.py` · 웹검색 `web_research.py` · 에이전트 `agent.py` · 판정 `classify.py`

## 단계

**① 지도 대조** — 지도에 등록된 가게명·주소·전화를 가져온다. 같은 가게로 보는 조건(`same_store`):
- 가게명이 비슷하다(한쪽이 다른 쪽을 품거나 글자 유사도 0.6 이상, "&" ↔ "앤" 같음). 두 글자 이하 상호는 정확히 같거나,
  괄호 속 지점명까지 같거나("행컵(계명대점)" ↔ "행컵 계명대점"), 카카오 후보가 20m 안이면 앞부분 포함도 인정("은정" ↔
  "은정식당"). 두 상호를 이은 이름("네네치킨앤봉구스밥버거")은 한쪽과 같고 30m 안이면 인정. 거리 덕분에만 인정한
  후보의 가게명은 "가게명 다름" 근거로 쓰지 않는다
- 시·도와 구·군, 그리고 **읍·면·동이나 큰길 이름 중 하나**가 같다 — 구·군만 보면 넓은 군에서 다른 읍의 같은 이름
  가게를 잡았다(화원읍 상하이반점 ↔ 가창면 상하이반점). 큰길은 "비슬로525길" → "비슬로"
- 주소만 같은 후보는 고르지 않는다(같은 건물의 어린이집을 잡았다)
- 알려진 한계: 같은 길에 비슷한 이름의 다른 가게가 있으면 같은 가게로 본다("대구왕갈비본점" ↔ 같은 길 "왕갈비본점")

**이사**(`moved_store`) — 지도만으로는 "우리 가게가 이사함"과 "다른 동네의 같은 이름 가게"가 똑같이 보인다. 카카오
근처(150m)에 없을 때만 반경 없이 다시 찾아, **전화번호가 DB 와 같은** 후보를 이사한 우리 가게로 본다(시·도만 같으면
된다, 15xx 대표번호 제외). 네이버는 전화번호를 주지 않아(`telephone` 이 늘 빈 값) 쓰지 않는다.

지도 값은 약관상 저장할 수 없어(아래 약관) 판정에만 쓴다(`storable=False`). 지도에만 다른 값이면 수정안 없이 근거
문구와 링크만 남기고(④ 문구 표), 에이전트가 웹에서 저장할 수 있는 같은 값을 찾으러 간다. 네이버 링크는 DB 가게명·주소로
만든 검색 링크다.

**③ 에이전트** — 지도로 끝나지 않은 가게(지도와 다름·일부만 확인·못 찾음)만 받아, 무엇을 더 찾을지 고른다
(`web_search(항목, 목적)` 최대 2번 · `finish`). 지도 값은 판단 모델에 넘기지 않고 관계(일치·다름·못 찾음)만 준다.
수정안에 담을 값은 웹검색에서만 나온다. 웹검색은 `항목 | 값 | 근거 | 날짜` 를 받고, 출처는 모델이 적은 URL 이 아니라
검색 결과로 잇는다. 제공자는 `WEB_SEARCH_PROVIDER` 로 고른다:
  - `vertex`(기본) — Vertex Gemini + 구글 그라운딩. 출처는 그라운딩 support 로 잇는다
  - `claude` — Claude 웹검색 도구(`web_search_20250305`, `claude-opus-5-5`, 호출당 검색 3번까지). 출처는 근거 구간에 붙는
    인용(`citations`)으로 잇는다. 최신판 `web_search_20260209` 는 결과를 코드 실행으로 걸러 써서 답에 인용이 붙지 않아
    (2026-10-27 실측) 쓰지 않는다. `ANTHROPIC_API_KEY` 가 있어야 하고, 판단을 Gemini 로 하면 GCP 도 그대로 필요하다
- **가게당 시간 예산**(`INVESTIGATION_TIME_BUDGET_SECONDS`, 기본 75초 = 백엔드 `ai.read-timeout-ms`) — 남은 시간이
  40초 미만이면 새 웹검색을 시작하지 않고 모은 근거로 판정한다(백엔드가 끊으면 찾은 것까지 잃는다)
- 판단 모델은 기본 Vertex Gemini, `AGENT_MODEL`·`AGENT_BASE_URL`·`AGENT_API_KEY` 를 주면 카테캠 프록시(Responses API)

**④ 규칙 판정**
- 빼는 근거: 출처 없음, 가게 번호가 아닌 전화(15xx 등), 번지 없는 잘린 주소, `lastCheckedAt` 보다 확실히 이전 근거
- 찾은 번호가 안심번호(050x)면 DB 와 같은 번호일 때만 확인 근거로 쓴다 — 플랫폼이 가게로 넘겨 주는 번호라 다르다고
  바뀐 게 아니고, DB 가 비어 있어도 채울 번호가 아니다. 반대로 DB 가 안심번호인데 진짜 번호를 찾으면 바꾸자고 한다
  (안심번호는 다시 발급하면 바뀐다)
- 같은 값: 전화는 표준 표기로, 주소는 도로명+건물번호로, 가게명은 괄호·지점명 앞 지역어를 빼고 비교.
  한쪽이 다른 쪽의 앞부분 + 업종·지점 꼬리면 같음, 그 밖의 포함 관계(`최과장` ↔ `최과장회덮밥`)는 판단 보류.
  DB 상호의 일부만 적은 값 — 지점명만(본사 매장 목록 `대구신암신천점`)이나 괄호 병기만(`E1(이원)` 의 `이원`) — 도 판단 보류
- 값 고르기: 출처 많은 값 → 같으면 최근 글. DB 값을 확인해 주는 최근 근거보다 오래된 다른 값은 버린다(옛 번호·옛
  표기로 생기는 거짓 신호를 막는다)
- 영업 상태를 모를 때 웹의 "영업 중"은 변화로 보지 않는다(폐업 뒤에도 남는 영업시간 문장)
- 근거 문구는 코드가 정한 틀로만 쓴다(`_change_text`). 웹검색 모델의 근거 문장은 넣지 않는다 — 영어 주소가 섞이고
  실행마다 달라졌고, 찾은 값이 문장 속에 묻혔다. 원문은 출처 링크에 있다

  | 경우 | 문구 |
  |---|---|
  | 웹에서 값을 찾음 | `주소: DB "상인서로 48" → 웹 3곳 "대구 달서구 상인서로 46" (최근 글 2026-09-12)` |
  | 지도에서만 다름 | `가게명: 카카오맵과 다름 — 링크에서 확인` (지도 값은 약관상 적지 않는다) |
  | 이사 | `주소: 같은 전화번호의 가게가 다른 주소에 있음(카카오맵) — 링크에서 확인` |
  | 엇갈림 | 뒤에 `(웹 2곳은 DB 와 같음)` · `(웹 3곳은 다른 값)` — 성격별로 묶어 한 번만 |

  출처는 웹이면 도메인 수, 지도면 이름만 적는다. 영업 상태는 "영업 중·휴업·폐업·확인 안 됨"으로 적는다

**⑤ 확인 근거**(`with_confirmations`) — 변화없음 결과에만, 조사를 다 마친 뒤 붙인다(`SIGNAL_NONE`, 분류는 그대로).
이게 없으면 지도에서 전부 확인된 가게와 아무것도 못 찾은 가게가 똑같이 "변화없음"이다.

| 경우 | 근거 행 |
|---|---|
| 항목을 확인함 | "주소: DB 값과 일치 — 카카오맵" + 출처 링크 (가게명·주소·전화 중 DB 에 값이 있는 항목마다) |
| 항목을 못 찾음 | "전화번호: 확인할 근거를 찾지 못함" |
| 아무 근거도 없음 | `status` 한 행 "지도·웹에서 이 가게를 찾지 못함 — 영업 여부를 직접 확인하세요" |

조사 중간(지도로 끝낼지 판단 등)에는 붙이지 않는다 — 그 판단은 Signal 이 있으면 변화로 본다.

## 측정

**Claude 웹검색(2026-10-27, 로컬 DB 실제 가게 5곳, 각 1회)** — 가게당 8~16초(Vertex 실측 10~20초와 비슷), 검색 1~3번,
출처 URL 은 리다이렉트 없이 원래 주소로 온다. 5곳 중 2곳에서 변화 신호(전화·주소 각 웹 1곳 근거), 3곳은 찾은 것 없음.
같은 60곳 `mismatch_bench --mode web`(지도 없이 웹검색만, 각 1회, `WEB_SEARCH_PROVIDER` 로 전환):

| | Vertex (Gemini Flash) | Claude Opus 5.5 | Claude Haiku 5.5 |
|---|---|---|---|
| 확인된 값으로 고침 (전화 9·주소 15·상호 12) | 2·8·7 = 17 | 2·8·7 = 17 | 3·6·7 = 16 |
| 대조군 24곳 중 제안 없음 | 18 | 16 | 20 |
| 건드리지 않은 항목의 다른 값 | 상태 6 · 전화 4 · 상호 2 | 상호 9 · 전화 6 · 주소 2 | 상호 3 · 전화 4 · 주소 1 |
| 평균 시간 | 17초 | 12초 | 15초 |
| 비용(추정, 가게당) | 재지 않음 | 약 $0.08 | 약 $0.025 (대부분 검색 요금) |

Haiku 는 상호 판단 보류 규칙(아래)을 넣은 뒤 돌렸다 — 같은 규칙이면 Opus 상호 9 → 5. Claude Sonnet 5.5 는 근거 문장을
옮겨 적되 인용을 붙이지 않아(2026-10-27 실측, 생각 설정을 바꿔도 같음) 모든 관측이 출처 없음으로 실패해 쓸 수 없다.

고친 수는 같지만 **잡은 가게가 다르다**(주소 8곳 중 겹치는 곳 5). 거짓 신호의 성격도 다르다 — Vertex 는 영업 상태
(폐업·휴업)를, Claude 는 지점명만 떼어 온 가게명(`대구신암신천점`·`이원`)을 낸다. 1회씩이라 실행마다 흔들리는 폭은 모른다.
지점명·괄호 병기만 적은 가게명을 판단 보류로 바꾼 뒤 같은 관측으로 다시 판정하면 Claude 가게명 거짓 신호 9 → 5, 고친 수는 그대로다.

**값 불일치 벤치마크**(`eval/mismatch_bench.py`) — 인허가 영업 60곳을 확인된 DB 처럼 만들고 한 항목만 일부러 틀리게
넣었다(전화 한 자리·건물번호·가게명 오타, 오류 약 34곳 + 대조군). 지도를 먼저 보는 이유: 웹검색만으로는 10곳, 지도를
먼저 보면 22곳을 잡았다(2026-10-06).

**다음 행동을 누가 정하나**(2026-10-16, 같은 코드, 각 1회, 다섯 조건 모두 성공한 50곳·오류 29) — 지도 대조·웹검색·
판정은 같고 "다음에 무엇을 검색할지"만 바꿨다(`--mode hybrid_rule` · `hybrid_rule_anchored` · `hybrid`)

| 다음 행동을 정한 쪽 | 잡음 | 값까지 고침 | 틀린 값 | 평균 | 웹검색 |
|---|---|---|---|---|---|
| 규칙 | 22 | 8 | 0 | 14초 | 45번 |
| 규칙 + 검색 목적에 주소·전화를 닻으로 | 22 | 8 | 0 | 12초 | 43번 |
| gpt-6-luna | 22 | 11 | 0 | 23초 | 60번 |
| gemini-4-argon | 22 | 10 | 0 | 25초 | 50번 |
| claude-sonnet-5 | 22 | 10 | 0 | 32초 | 58번 |

잡는 수는 지도가 정해 같다. 값까지 고치는 건 모델이 규칙보다 2~3곳 많고 모델끼리는 차이가 없다 — 첫 검색 결과를 보고
다른 항목을 한 번 더 찾는 판단에서 나온 것으로 보인다(웹검색이 더 많다). 틀린 값·대조군 오탐은 늘지 않았고 대가는
가게당 10~18초. 각 1회라 반복 측정이 남았다.

- 흔들림(같은 설정 2회): 잡음은 같고 값은 7·5, 판정이 뒤집힌 가게 8% — 웹에서 값을 되찾는 부분이 흔들린다
- 시간 예산 75초: 75초 넘는 가게 14 → 3곳
- **전화가 약하다**: 전화 오류 7~9곳 중 잡음 3~4. 잡은 곳은 전부 카카오 덕이고, 카카오에 없으면 웹으로 거의 못 잡는다
- 웹검색 오류로 가게가 통째 실패: 6회 실행에서 40건. 25건은 지도·웹 모두 흔적이 없는 가게, 10건은 429

**DB 가 맞는 가게에서 지도가 내는 거짓 "다름"**(일부러 틀리게 넣기 전 값 60곳, 빈 전화 채움 제외)

| | 다름 | 지도에서 전부 못 찾음 |
|---|---|---|
| 동네 조건 넣기 전 | 11곳 | 17곳 |
| 동네 조건 넣은 뒤 | 8곳 | 18곳 |
| + 이름 규칙(지점명·바로 옆·&) | 11곳 | 14곳 |
| **+ 안심번호 제외**(카카오만) | **10곳** | 23곳(카카오만) |

오류를 잡는 수는 세 단계 모두 같다. 이름 규칙으로 더 찾게 된 가게 중 3곳은 전화가 DB(인허가)와 달라 "다름"이 늘었다.
안심번호를 빼자 1곳(0502)이 줄고, DB 전화가 빈 3곳은 안심번호로 채우자는 제안 없이 카카오에서 끝났다. 남은 10곳: 전화 다름 7(인허가 옛 번호일 수 있음) · 서류상 이름 vs 간판 이름 2 · 같은 길 다른 번지 1 — 진짜 변화인지
비교 기준이 오래된 건지 이 자료로는 가릴 수 없다.

**이사 흉내** — 전화번호가 있는 34곳의 DB 주소·좌표를 다른 구의 다른 가게 것으로 바꿔 넣었다. 카카오에 등록돼 있고
번호가 같은 10곳 중 **7곳을 이사로 잡았고 모두 진짜 주소**를 가리켰다. DB 가 맞는 60곳·인허가 폐업 30곳에서 이사로
잘못 잡은 곳은 0.

**지도에서 전부 못 찾는 비율** — 영업 중 23~30%, **인허가 폐업 30곳 중 29곳(97%)**. 영업 중 가게도 많이 오므로
우선확인으로 올리지 않고 ⑤ 확인 근거의 "찾지 못함"으로만 표시한다.

**카카오만 쓰면**(네이버 지역 검색 끔) — 일부러 넣은 오류는 주소만 10 → 8/15 로 줄고, 거짓 "다름"(11)·폐업 못 찾음(29)은
같다. 대신 지도에서 확인 못 하는 가게가 14 → 23곳으로 는다(공식 API 로 찾은 가게: 카카오 37 · 네이버 28, 네이버만 9).
네이버를 끄면 남은 약관 쟁점(목적 제한)이 사라진다.

## 보류 (효과는 확인, 팀 결정 필요)

- **블로그 장소 카드로 최근 영업 흔적 확인** — 블로그 글의 네이버 장소 카드 가게명·도로명이 DB 와 같고 90일 안 글이면
  "최근 방문 리뷰 + 링크". LLM 없이 가게당 9초, 영업 중 60곳 중 15곳, 폐업 30곳에는 0곳. 분류를 바꾸지 않는 근거라
  "담당자 확인일(`lastCheckedAt`)과 별도 날짜"를 둘지 팀이 정해야 한다
- **카카오 장소 ID 추적**(멘토 제안, 2026-10-15) — 매번 이름으로 찾지 말고, 한 번 찾은 카카오 장소 ID 를 저장해 두고
  그 장소가 아직 있는지만 본다
  - 처음 한 번: 지도 대조로 고르고 담당자가 확인 → ID 저장. 지금 규칙으로 60곳 중 37곳. 카카오 값은 LLM 에 보낼 수 없어
    이 매칭은 규칙 + 담당자 몫이다
  - 그 뒤: DB 좌표 150m 안 카테고리 검색으로 ID 확인 — 37곳 모두 다시 찾았고(100m 면 3곳 놓침), 없으면 "지도에서 사라짐".
    이름 검색의 "못 찾음"과 달리 영업 중 가게에서 거짓으로 나온 적이 없다
  - 모르는 것: 카카오가 문 닫은 가게를 실제로 지우는지
  - 필요한 것: 백엔드에 장소 ID(또는 링크) 칸, AI 요청에 그 값을 실어 주기
  - 네이버는 장소 페이지 자동 접근이 막혀(12곳 모두 차단) 추적할 수 없다

## 외부 출처와 약관

- **카카오 로컬** — 실시간 비교 후 폐기, 장소 ID·링크 저장만 된다. 이름·주소·전화 저장과 LLM 전송은 안 된다.
  담당자가 고른 후보의 값도 "API 결과 기반"이라 저장할 수 없다(2026-10-16 원문 확인)
  - [운영정책](https://developers.kakao.com/terms/ko/site-policies) 제5조 20호(목적 외 캐시 금지)·30호(얻은 데이터를 승낙
    없이 복사·변경·제공 금지), 제8조(위반 시 삭제 요구). [플랫폼 서비스 약관](https://developers.kakao.com/terms/ko/site-terms)
    제11조 ③ 도 같다. AI 전용 조항은 없다
  - [DevTalk FAQ](https://devtalk.kakao.com/t/faq-api/125610): "API는 실시간으로 호출하여 사용하는 것만 가능", "결과
    데이터를 별도로 저장하여 사용하는 것은 허용하지 않습니다"
  - 장소 ID 저장은 약관이 아니라 담당자 답변에만 근거가 있다 — [151727](https://devtalk.kakao.com/t/id/151727)
    "장소ID 및 URL은 저장 및 활용은 가능합니다", [150784](https://devtalk.kakao.com/t/topic/150784) 리뷰 매핑용 ID 저장
    허용. 답변 계정에 직원 표시가 없어, 도입 전에 우리 용도로 직접 문의해 답을 남겨 두는 게 안전하다. 우리 문의 답변
    (2026-08~09, LLM 전송 불가)은 링크를 남겨 두지 않았다
- **네이버 지역 검색**(NAVER API HUB, 2026-09-20 시행 약관) — 검색 특약 1.1 "검색결과를 **제공하기 위한 목적으로만**",
  1.3 저장·캐싱·**AI 입력** 금지, 일반조건 7.3③ "**별도 데이터베이스로 관리**" 금지. 카카오와 같은 방식으로 쓴다
  (판정에만, 수정안·에이전트 입력에 네이버 값 없음). **목적 제한(1.1)은 남는다**
- **네이버 블로그·검색 화면·플레이스** — 자동 수집 금지(약관·robots.txt), 플레이스는 첫 요청에 차단. 운영에는 쓰지 않는다
- **카테캠 프록시** — 그라운딩을 못 써 에이전트 판단에만 쓴다
- **Claude 웹검색 도구** — 가게 이름·DB 주소·전화(우리 DB 값)만 보낸다. 지도 값은 보내지 않는다(위 카카오·네이버와 같은 원칙)

## 정하지 않은 것 (팀 결정)

- ⑤ 확인 근거(`SIGNAL_NONE`)를 백엔드·프론트가 변화로 다루는 곳이 없는지, 변화없음 카드에 근거가 여러 줄 붙어도 되는지
- 추가확인 목록에서 "찾지 못함" 가게를 위로 올릴지(폐업이 여기 몰린다)
- 엇갈리는 근거를 지금처럼 하나 골라 제안할지, 후보를 모두 보여 주고 수정안을 비울지(값이 갈린 항목은 실행마다 0~2개)
- 블로그 최근 리뷰 날짜를 둘 칸, 네이버 지역 검색의 목적 제한을 감수할지
- 카카오 장소 ID 를 백엔드에 둘지(멘토 제안) — 두면 "지도에서 사라짐"을 폐업 의심으로 쓸 수 있다
