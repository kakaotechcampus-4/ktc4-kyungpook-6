# 2차 조사 — 웹검색으로 가게 정보 불일치 찾기

PROMPT-88 · 갱신 2026-09-30

## 무엇을 하나

1차 조사(백엔드, 매일 새벽 국세청 대조)에서 **변화가 잡히지 않은 가게**를 웹에서 다시 확인해, 우리 DB 값과
다른 것을 찾아 **수정안**으로 올린다. 가게 정보는 담당자가 승인해야 바뀐다.

- 주 목표는 **주소 · 전화번호 · 상호명의 값 불일치**다. 영업 상태(폐업)도 보지만 웹검색으로는 거의 못 잡는다
- 표기 차이(`대구` ↔ `대구광역시`, `053-111-2222` ↔ `053)111-2222`)는 같은 값으로 본다
- 대상은 **백엔드가 골라 보낸다** — `statusMismatch`(1차에서 우선확인)·`dataProblem`(번호부터 찾을 가게)이
  아닌 가게. AI 는 받은 가게를 다시 거르지 않는다

```
담당자 가게 선택 → 백엔드: 1차 결과로 나눔 → 2차 대상만 가게 하나씩 POST /investigations
AI (가게 하나):  ① 관측 수집 → ② 카카오맵 확인 → ③ 규칙 분류 → StoreFinding
```

| 단계 | 파일 | LLM |
|---|---|---|
| 흐름·재시도 | `src/investigation/web.py` | – |
| ① 관측 수집 | `src/investigation/web_research.py` | Gemini 1회 + 구글 검색 그라운딩 |
| ② 카카오맵 확인 | `src/investigation/kakao_map.py` | 없음 |
| ③ 규칙 분류 | `src/investigation/classify.py` | 없음 |
| 입출력 형식 | `src/investigation/models.py` | – |

**모델은 "웹에서 본 값을 근거와 함께 적어 오기"만 하고, 판단은 규칙이 한다.** 모델의 확신도로 가르지
않는다(멘토 결정). 아직 도구 루프(에이전트)는 없다 — LLM 1회짜리 파이프라인이다.

## ① 관측 수집

1. 가게 이름·주소·전화(DB 값)를 주고 네 항목(`status`·`phone`·`address`·`name`)을 한 줄에 하나씩
   `항목 | 값 | 근거 문장 | 날짜` 로 적게 한다. "바뀌었는지 판단하지 말고 본 것만"
2. 줄을 읽는다. 약속을 어긴 줄·빈 표시(`없음`, `(모름)`)는 그 줄만 뺀다. 상태는 OPEN/SUSPENDED/CLOSED,
   한글은 뜻이 하나로 정해지는 말만(`폐업`→CLOSED, `임시 휴업`→SUSPENDED; `영업 종료`·`휴무`는 안 받음)
3. **출처는 모델이 적은 URL 을 쓰지 않는다.** 구글이 붙여 주는 `grounding_supports`(응답의 어느 **UTF-8 바이트
   구간**이 어느 검색 결과에 근거하나)로 줄마다 검색 결과를 잇고, 리다이렉트 주소는 원래 URL 로 푼다
4. 재시도(`web.py`): 형식 이탈·출처 0개면 1번 더, 429 면 5초·15초 기다렸다 다시. 그래도 안 되면 그 가게는 실패

## ② 카카오맵 확인

`KAKAO_REST_API_KEY` 가 있으면 DB 좌표(없으면 DB 주소 → 좌표) 반경 150m 안에서 상호로 찾는다(법인 표기·괄호를
뺀 이름, 한쪽이 다른 쪽을 품으면 같음).

| 결과 | 쓰임 |
|---|---|
| `FOUND` + `placeUrl` | 영업 방증. 폐업·이전·상호 변화에 "지도에는 원래대로 있음 — 다른 가게 정보일 수 있음" 표시 |
| `NOT_FOUND` | **폐업 근거가 아니다** (영업 가게의 절반 가까이도 못 찾는다) |
| `NO_COORDINATES` · `UNAVAILABLE` | 아무것도 하지 않는다. 조사를 막지 않는다 |

분류는 바꾸지 않는다. 카카오 응답에서 남기는 건 상태와 `placeUrl` 뿐이고 모델에 넘기지 않는다 — 카카오맵
담당자 답변(데브톡, 2026-09): 실시간 비교 후 폐기·장소 URL 저장은 허용, 장소명·가공 데이터 저장과 외부 LLM
전송은 불허. 지금은 쓸 만한지 재는 단계라 정식으로 쓰기 전에 다시 확인한다.

## ③ 규칙 분류

**판정에서 빼는 관측**

- 출처가 이어지지 않은 관측 — 사람이 검증할 수 없다
- 가게 번호가 될 수 없는 전화 — 15xx·16xx·18xx 대표번호, 080, 자릿수가 틀리거나 끝자리가 넘치는 번호
- DB 가 도로명 주소일 때의 지번 주소 관측 — 같은 곳인지 가릴 수 없다

**같은 값인가** (`comparison_key`)

| 항목 | 비교 | 같다고 보는 예 |
|---|---|---|
| 전화 | 문장에서 번호 하나를 뽑아 `053-111-2222` 표준 표기로(DB 번호도 같은 규칙) | `+82 53-111-2222`, `(053) 111-2222`, `053-111-2222 (예약)` |
| 주소 | 도로명 + 건물번호 | `대구광역시 중구 동성로 12, 1층` = `대구 중구 동성로12` |
| 상호 | 괄호 병기 제거, 한쪽이 다른 쪽을 품으면 같음 | `삼송빵집` = `삼송빵집 본점` |
| 상태 | 값 그대로 | |

**변화인가**

- DB 와 다른 값이 있으면 변화다. DB 값이 비어 있으면 찾은 값이 곧 변화다(빈칸 채우기)
- 예외: **DB 상태가 UNKNOWN·없음일 때 웹의 OPEN 은 변화가 아니다.** OPEN 근거는 대부분 목록 사이트의
  "영업시간" 문장이라 폐업 뒤에도 남는다. CLOSED·SUSPENDED 는 변화다
- 다른 값이 여럿이면 **서로 다른 도메인이 가장 많은 값**을 제안한다. 표기는 가장 흔하고 짧은 것

**결과**

| | 담는 것 |
|---|---|
| `Signal` (변화 하나당 1행) | `signalType=SIGNAL_HIGH`, `confidence=null`, `field`(어느 수정안 항목인가), 대표 근거(`evidenceText`·`evidenceUrl`). 근거 끝에 "(출처 N곳)"(그 값을 가리킨 도메인 수), 출처끼리 엇갈리면 "(다른 값을 가리키는 출처도 있음)" |
| `classification` | 변화가 있으면 `PRIORITY_CHECK`(우선확인), 없으면 `NO_CHANGE`(변화없음) |
| `proposedChanges` | 변화마다 새 값. 예: `{"phone": "053-964-0022"}` |

응답은 백엔드 `Task`·`Signal` 칸 그대로다(`백엔드_연동.md`). 규칙이 쓰는 `observed`·`sourceCount`·`mapCheck`
(② 의 결과)는 AI 안에만 있고 응답에서는 뺀다 — 백엔드에 칸이 없다.

- **신호에 등급을 두지 않는다** — 담당자가 승인하므로 출처 1곳짜리도 올리고, 판단 재료로 출처 수를 근거 문구에 적는다
- DB 값을 확인한 근거·지도 확인·"근거 없음"은 이상 징후가 아니라 **Signal 로 만들지 않는다.** 변화가 없으면 0행
- **추가확인은 AI 가 돌려주지 않는다.** 팀 합의로 분류는 이렇다

| 분류 | 정의 | 정하는 곳 |
|---|---|---|
| 우선확인 | 1차에서 국세청 변화 + 2차에서 변화 | 백엔드(1차) · AI(2차) |
| 추가확인 | 변화없는 매장 중 직접 확인한 지 90일 이상 | 백엔드 (`Store.lastCheckedAt`) |
| 변화없음 | 그 밖 | |

## 이상해 보이는 규칙이 왜 있나

대부분 실제 호출이나 경계값 검증에서 틀린 결과가 나와서 생겼다. 규칙마다 회귀 테스트가 있다.

| 규칙 | 없었을 때 |
|---|---|
| 출처를 모델 URL 대신 그라운딩으로 | 모델이 적은 URL 15개 중 13개가 검색 결과에 없는 주소 |
| 응답을 JSON 대신 줄 형식으로 | JSON 이면 그라운딩이 9번 중 1번만 붙어 전부 "출처 없음" → 조용히 변화없음 |
| 바이트 오프셋으로 출처 잇기 | 문자 기준으로는 0/40 이 맞음 — 출처가 엉뚱한 줄에 붙음 |
| 상태 UNKNOWN + OPEN 은 변화 아님 | 우선확인이 "영업시간 적힌 가게"로 가득, 폐업 가게를 "영업 중"으로 제안 |
| 전화번호 표준화·자릿수 검사 | 영화관 대표번호 제안, 잘린 `0507-5256-540` 제안, `053-111-2222 (2층)` 이 `053-1112-2222` 로 |
| 도로명 붙여 쓰기, 지번 비교 안 함 | `대종로 480번길` ↔ `대종로480번길` 이 "이전", 지번 한 건 때문에 엇갈림 |
| 상호 괄호 병기 제거·포함 관계 | `성심당(聖心堂)`, `삼송빵집 본점` 이 "상호 변경" |
| 지도에서 찾으면 어긋나는 변화에 표시 | 케이블카 안 식당에 케이블카 주소를 "이전"으로 제안 |

## 측정

`gemini-2.5-flash`, 가게당 5~40초. 실데이터가 아직 DB 에 없어 **간이 DB** 로 잰다.

**간이 DB** (`eval/mock_db.py`) — 대구 일반음식점 인허가(LOCALDATA)에서 폐업 30곳(폐업 1~18개월 전)·영업 30곳을
뽑아, `nts-checks` 응답 행 모양(`store` 칸 + 국세청 칸)으로 만든 것. 결함은 선한영향력가게 명단을 따라 넣었다 —
`phone=null`, `internalStatus=UNKNOWN`, 10% 는 지번 주소. 즉 **처음 적재한 직후**의 모습이다.

| | 폐업 30 | 영업 30 |
|---|---|---|
| 우선확인 | 4 | 12 |
| 폐업·휴업 변화 | 1 | 1 |
| 카카오맵에서 찾음 | 0 | 16 |

- 우선확인은 거의 전부 **출처 1곳짜리 전화번호 채우기**다(Signal 19행 중 18행이 출처 1곳). 인허가 번호가 있는 11건 중 7건 일치
- **폐업은 웹검색으로 거의 못 잡는다** — 폐업 30곳 중 23곳은 구글 검색 결과 자체가 0개. 근거 출처에 네이버 블로그는
  0건이고, 프롬프트로 네이버를 찾게 해도(40회) 0건이었다. 네이버 검색 API 는 2026-09-07 개정 약관(목적 제한·AI
  입력 금지, 기사 기준)과 부딪혀 쓰지 않는다
- **카카오맵에 있으면 영업 중이 16/16** 맞았다. 없다고 폐업은 아니다(못 찾은 44곳 중 14곳이 영업)
- 같은 60곳을 두 번 돌리면 **8곳(13%) 판정이 뒤집힌다** — 변화없음은 "이번에 못 찾음"일 수 있다
- **주 목표(값 불일치)로는 아직 재지 않았다** — 간이 DB 에 확인된 값이 없어서다(아래 남은 것 1)

## 돌려 보기

```bash
uv run --with pyproj python -m eval.mock_db --n 30      # 간이 DB (좌표 변환에 pyproj)
uv run python -m eval.mock_round run --tag v1           # Vertex·카카오 호출, 관측 원본까지 시트에 저장
uv run python -m eval.mock_round reclassify --tag v1 --out v2   # 규칙만 고쳤을 때 — Vertex 없이 다시 분류
uv run python -m eval.mock_round map --tag v1 --out v2          # 카카오맵 확인만 새로
uv run python -m eval.mock_round grade --tag v2
```

결과 시트·인허가 파일·간이 DB 는 `eval/fixtures/`(커밋 금지)에 둔다. 단위 테스트(`tests/investigation/`)는 전부
가짜 응답으로 돈다.

## 남은 것

1. **값 불일치 측정** — 간이 DB 에 "확인된 값" 버전(상태 OPEN·전화 채움)을 두고 일부 가게의 번호·주소·상호를
   일부러 틀리게 넣어, 그걸 잡는지 잰다. 주 목표를 재는 유일한 방법이다
2. **에이전트로 바꾸기** — 검색이 빗나가면(근거 0건, 시설 정보만 나옴) 이름을 바꿔 다시 찾게 한다. 1 로 전후를
   비교해 나아지지 않으면 지금 파이프라인으로 둔다. 카카오맵 확인은 약관상 에이전트 밖에 둔다
3. **상호 규칙** — "한쪽이 다른 쪽을 품으면 같음"은 `안다미로` → `밥안다미로` 같은 값 차이를 놓친다. "한쪽이
   다른 쪽의 **앞부분**일 때만 같음"으로 좁히는 안 검토 중(지점·업종 표기는 뒤에 붙는다)
4. **한계로 둔 것** — 웹에 흔적이 없는 가게, 시설 안 가게(부모 시설을 조사함), 모델이 해석을 섞음("운영 여부 확인
   안 됨"을 SUSPENDED 로), 관측 날짜를 판정에 쓰지 않음, 호출마다 결과가 흔들림
5. **백엔드·프론트 연동** — 조사 시작·AI 호출·결과 저장·조회가 비어 있다. 요청할 것은
   [`백엔드_연동.md`](백엔드_연동.md)
