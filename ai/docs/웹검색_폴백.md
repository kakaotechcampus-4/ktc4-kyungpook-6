# 웹검색 폴백 — 현황과 계획

티켓 PROMPT-49 · 2026-09-15

## 범위

**사업자등록번호를 채워 넣는 기능**의 웹검색 폴백 구간만 다룬다.

```
Store.사업자등록번호 있음 ──→ 국세청 API ──→ 휴폐업 상태 조회 ✓

비었음 / 오류 / 갱신 필요
   └→ ① 상호명으로 비즈노 조회 → 번호 획득
        └→ ① 실패 시 ② 웹검색 폴백        ← 여기
```

**최종 산출물은 사업자등록번호다.** 등록상호명은 목적이 아니라 비즈노 조회를 뚫기 위한
수단이다(간판 `성심당`으로는 안 나오고 등록명 `로쏘`로 물어야 나옴).

## 결과

fixture 23건 중 **모수 21건**(E유형 2건은 정답지 오염이라 제외) · `gemini-2.5-flash` Vertex 직결 그라운딩

| 방식 | 번호 도달률 | 오염률 |
|---|---|---|
| ① "정답 이름 하나를 맞혀라" (폐기) | 0/23 완전일치 | — |
| ② 원본 상호명을 비즈노에 직접 | 0/21 = 0.0% | 4.8% |
| ③ **후보 생성 + 비즈노 검증** | **4/21 = 19.0%** | 4.8% |
| 오라클 — 정답 이름을 안다고 가정 | 18/21 = 85.7% | 0 |

**0% → 19.0%.** 상한(85.7%)의 22% 지점이다.

> 이 fixture는 이름 불일치만 골라 만든 **최난도 세트**다(상호명 = 등록상호명인 건이 0건).
> `19.0%`를 "전체에서 19%"로 읽으면 안 된다. 실제 분포는 원본 목록이 있어야 알 수 있다.

**"①로 대부분 뚫리면 폴백 구간은 좁아진다"던 가정은 틀렸다 — ①이 0%다.** 비즈노 상호명
검색은 국세청 등록상호명에 매칭하므로 `벨라로사`로 검색해 등록명 `주식회사 우리요리`가
나올 길이 원리적으로 없다. 동시에 오라클 85.7%는 **전제가 성립한다**는 뜻이다 —
이름만 알아내면 번호는 나온다.

## 설계 — 정답이 아니라 후보를 받는다

```
웹검색 → 이름 후보 여러 개 + 근거·주소·사업자번호
       → 주소가 다른 지역이면 기각 / 번호가 있으면 역조회 / 아니면 이름 검색
       → 비즈노 결과를 모아 등급 판정
       → 제안값 + 근거로 담당자 큐에
```

**비즈노가 검증자다.** 모델은 정확할 필요 없이 **유용하게 틀리기만 하면** 된다 — 후보 안에
정답이 하나 있으면 성공이다. LLM self-report confidence를 신뢰할 필요가 사라진다
(멘토 결정사항인 "외부 검증"이 구조로 들어간다).

이전 방식은 `{official_name, confidence}` 하나를 요구했고 **완전일치 0/23**이었다.
그중 **그럴듯한 오답 9건이 confidence 0.90~1.00을 달고 있었다**(입력을 그대로 되돌려주거나,
실재하는 다른 법인을 찾아옴). `confidence` 필드를 없앤 이유다.

### 반드시 지킬 두 가지

1. **폴백 결과를 자동으로 DB에 쓰지 않는다.** `제안값 + 근거 + 미확인`으로 담당자 큐에 올린다.
   이 조건이 있으면 적중률이 낮아도 순이익이다 — 틀려도 사람이 거른다
2. **근거 없는 답은 버린다.** 검색 스니펫에 근거가 없으면 후보에서 제외한다.
   지어냄 5건이 통과하던 경로가 닫힌다

### 통한 것 셋

- **후보를 여러 개 받는 것 자체** — `여주휴게소(강릉방향)`는 후보 8개 중 하나가 정답이었다
- **근거에서 사업자등록번호 줍기** — 간판과 등록명이 글자 하나 안 겹치는 건을 번호로 뚫었다
- **근거의 주소로 다른 지점 기각** — 11개를 걸렀다. 비즈노에 없는 주소가 웹검색 근거에는 있다

### 막힌 이유 — 모델은 본사를 찾고, 등록은 지점 사업자다

| 상호명 | 모델이 찾은 것 | 국세청 등록명 |
|---|---|---|
| 세븐일레븐 우정조암점 | `(주)코리아세븐` | `미니스톱 우정조암점` |
| CU 의정부호원가든점 | `BGF리테일` | `씨유 의정부호원가든점` |

**모델이 틀린 게 아니다** — 실제 운영사다. 개별 지점의 사업자 정보가 웹에 없다.

## 아직 못 하는 것 — 동일성 판정

비즈노가 확인해주는 건 **"이 이름이 실재하는 사업자인가"**지 **"그게 우리 가게인가"**가 아니다.

| 신호 | 상태 |
|---|---|
| 이름 등급 | ✗ 도달한 4건이 전부 최하위 등급, `완전일치`였던 `몽쁘띠`는 오답 |
| 후보 1건 | ✗ `봉궁순대국`·`몽쁘띠` 둘 다 1건인데 오답 |
| 주소 | 비즈노 응답에 없음. 웹검색 근거에 우연히 딸려 올 때만 |

그래서 **`19.0%`는 도달률(recall)이지 정확도(precision)가 아니다** — "정답이 후보 안에
있었다"이지 "골라냈다"가 아니다. 자동 반영을 하지 않고 담당자가 `source_url`을 여는 이유다.

## 확정 — 그라운딩을 지키고 structured output을 포기한다

**둘을 동시에 가질 방법이 없다.** 그라운딩을 켜면 스키마 강제가 400으로 막힌다
(`controlled generation is not supported with Search tool`). Gemini 플랫폼의 구조적
제약이라 정식 API로 옮겨도 같다. 카테캠 프록시는 OpenAI 호환 `/v1`만 노출해 그라운딩을
태울 구멍 자체가 없다. 따라오는 대가 둘 — **응답 형식이 보장되지 않고**(방어는 `_coerce_json`
+ 재시도, 실패는 누락이지 오염이 아니다), **팀원이 돌릴 수 없다**(개인 GCP ADC에 묶인다).

## 하지 말 것

- **`Store.사업자등록번호`를 폴백 결과로 자동 덮어쓰기.** 틀린 번호가 들어가면 이후 국세청
  조회가 계속 다른 가게를 가리키는데 **예외도 안 나고 값도 정상으로 보인다**
- **LLM self-report confidence를 임계값 분기에 사용.** 멘토 결정사항
- **structured output을 위해 그라운딩을 끄는 것.** 위 확정 참고
- **검색 엔진 교체만으로 정확도를 올리려는 시도.** 엔진이 아니라 호출 구조가 문제였다

## 결정이 필요한 사항

- **비즈노에서 주소를 받을 수 있는가** ← 가장 중요. 지금 쓰는 `fapi`는 주소를 안 준다(실측).
  티어 문제인지 엔드포인트 문제인지 확인하지 못했다. **이게 동일성 판정을 좌우한다**
- **폴백 산출물의 저장 위치** — `Store`에 제안값·근거·확인상태 컬럼이 없다. 백엔드 협의 필요
- **원본 선한영향력가게 목록** — 5번에 필요하다
- **Vertex 경로 유지 여부** — 개인 GCP ADC에 묶여 팀원이 못 돌린다.
  필요하면 IAM(`roles/aiplatform.user`) 초대 방식이고 과금은 프로젝트 소유자 부담
