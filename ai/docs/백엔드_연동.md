# 백엔드 연동 — 조사 흐름과 요청할 것

PROMPT-88 · 갱신 2026-10-06 (PROMPT-116)

AI 와 백엔드·프론트가 주고받는 구간만 다룬다. 조사 로직은 [`2차_조사.md`](2차_조사.md).
**아래 모양은 AI 쪽 제안이고 백엔드와 아직 합의하지 않았다.**

> **2026-10-06 (PROMPT-116) — AI 쪽은 붙일 수 있는 상태가 됐다.**
> 조사기가 서버에 꽂혔고(이전에는 무조건 503), AI 서비스가 `docker-compose.yml` 에 들어갔고,
> 백엔드 호출에 `X-API-KEY` 를 붙인다. **남은 것은 백엔드가 `POST /investigations` 를 부르는 것뿐**
> (PROMPT-106). 아래 "백엔드가 할 일" 1~5 는 그대로 유효하다.

## 연결 방식 — 백엔드가 골라서 한 곳씩 맡긴다

```
[매일 새벽] 백엔드 배치: 국세청 조회 → store_nts_check 저장                     (1차 조사, 있음)

[담당자가 가게 선택 → "조사 시작하기"]
프론트 → 백엔드  POST /api/jobs {storeIds}                                   (없음)
백엔드: Job 생성, 선택된 가게 중 번호 없음·틀림(dataProblem)만 빼고 → 번호 채우기 쪽으로
백엔드 → AI      POST /investigations [가게 1곳]   ← 가게마다, 백그라운드         (AI 쪽 있음, 호출 없음)
AI:  국세청과 상태 다름(statusMismatch) → 웹검색 없이 1차 근거로 수정안             (예정)
     나머지                              → 2차 조사(웹검색·카카오맵)로 수정안        (PROMPT-88)
AI → 백엔드      StoreFinding (응답, 수정안에 한글 라벨)
백엔드: Task · Signal 저장, Job.completedCount += 1                            (없음)
프론트 → 백엔드  GET /api/jobs/{jobId} · /latest                              (프론트만 있음)
```

**AI 가 `GET /api/stores/nts-checks` 로 가져가는 방식을 쓰지 않는 이유** — 담당자 선택, 1차 결과, Job·Task 저장이
모두 백엔드에 있다. AI 가 가져가면 선택된 가게를 표현할 방법이 없고, 거르기 규칙이 AI 로 넘어오고, 결과를
다시 백엔드에 보낼 저장 API 가 따로 필요하다. 백엔드가 맡기면 AI 는 **상태 없이 가게 하나를 조사해 돌려주기만**
한다. 에이전트다운 판단(검색이 빗나가면 다시 찾기)은 가게 하나를 조사하는 안쪽에 둔다.

`nts-checks`(PR #32) 는 버리지 않는다 — 백엔드가 선택된 가게의 1차 결과를 읽는 쿼리로 쓴다. AI 에 있던
`GET /investigation-targets`(국세청 불일치 목록을 대신 불러 주던 초기 연결 확인용)는 이 방향이라 뺐다.

**수정안은 AI 가 만든다.** 1차(국세청)로 잡힌 변화도 백엔드가 AI 에 보내면, AI 가 웹검색 없이 1차 결과
(`statusComparison`·`ntsStatus`·`ntsClosedAt`)로 수정안과 근거를 만든다. 예: 우리 OPEN · 국세청 폐업 →
`{"status": "CLOSED"}`, 근거 "국세청: 2026-08-01 폐업". 그래서 백엔드는 번호 문제만 빼고 선택된 가게를 전부 보내면
된다. (이 갈래는 아직 없다 — 지금 AI 는 모든 행을 2차 조사로 처리한다.)

## 요청·응답 — `POST /investigations`

**요청**: `nts-checks` 응답의 `content` 행을 **그대로** 배열에 담는다(1~100건, 권장은 1건). 모르는 칸은 버린다.

| 칸 | AI 가 쓰는 곳 |
|---|---|
| `storeId` | 결과를 가게와 잇는 열쇠 |
| `name`, `addressRoad` | 검색어·비교 대상 |
| `phone`, `internalStatus` | 웹에서 본 값과 비교할 DB 값 |
| `lat`, `lng` | 카카오맵 검색 중심(없으면 주소를 좌표로) |

**응답**: `{ results: [StoreFinding], requested, succeeded }` — 결과 수는 항상 요청 수와 같다(실패한 가게도 `failure` 를
채워 돌려준다).

**`StoreFinding` 은 백엔드 스키마 그대로다** — 백엔드는 바꾸지 않고 칸에 넣기만 하면 된다.

```json
{
  "storeId": 44,
  "classification": "PRIORITY_CHECK",
  "proposedChanges": { "phone": "053-964-0022" },
  "signals": [
    { "signalType": "SIGNAL_HIGH", "confidence": null, "field": "phone",
      "evidenceText": "전화번호: 전화번호 053-964-0022 (출처 2곳)", "evidenceUrl": "https://…" }
  ],
  "failure": null
}
```

| 응답 | 백엔드 칸 |
|---|---|
| `classification`, `proposedChanges` | `Task.classification`, `Task.proposedChanges` |
| `signals[]` 의 `signalType`·`confidence`·`evidenceText`·`evidenceUrl` | `Signal` 한 행의 같은 이름 칸 |
| `signals[].field` | `signal.field` — **PROMPT-104(#67)로 컬럼이 생겼다.** 다만 `nullable = false` 이고, 상수 이름이 AI 값과 다르다(`ADDRESS_ROAD` ↔ `"addressRoad"`). 백엔드가 받을 때 매핑한다 |
| `failure` | Task 를 만들지 않고 `Job.errorMessage` 에 가게 이름과 `message` 를 적는다(실패한 가게는 판정이 없고 `Task.classification` 은 NOT NULL) |

- `classification` 은 `PRIORITY_CHECK`(변화 있음) · `NO_CHANGE` 둘뿐이다. `ADDITIONAL_CHECK` 는 백엔드가 정한다
- `signals` 는 **잡힌 변화 하나가 한 행**이다(백엔드 `Signal` = 이상 징후 하나 + 근거 한 쌍). 변화가 없으면 빈 목록.
  `signalType` 은 항상 `SIGNAL_HIGH`
- **`confidence` 는 항상 null** 이다. 모델 확신도를 쓰지 않기로 했다(멘토 결정) — 백엔드 칸을 nullable 로 바꿔야 한다(아래)
- 백엔드에 칸이 없는 값은 응답에 넣지 않는다. 출처 도메인 수와 "지도와 어긋남" 표시는 `evidenceText` 문구에 들어간다.
  카카오맵 `placeUrl`(약관상 저장 가능한 유일한 값)은 AI 안에서만 쓰고 응답에서 뺐다 — 칸을 두면 다시 넣는다
- 오류: 빈 목록·100건 초과는 **422**, AI 서버에 `GOOGLE_CLOUD_PROJECT` 가 없으면 **503**

**가게별 실패** — `failure` 가 null 이면 성공, 아니면 `{ "code", "message" }` 다. 실패한 가게는 `classification` 이 null 이고
수정안·Signal 이 비어 있다. `message` 는 화면에 그대로 보여도 되는 고정 문장이고, 원래 예외 문장은 AI 서버 로그에만 남는다.

```json
"failure": { "code": "RATE_LIMITED", "message": "AI 요청 한도를 넘어 조사하지 못했습니다" }
```

| `code` | 뜻 | 다시 조사 |
|---|---|---|
| `RATE_LIMITED` | Vertex 요청 한도(429). AI 가 5초·15초 기다려도 계속됐다 | 잠시 뒤 하면 된다 |
| `TIMEOUT` | LLM 응답이 60초를 넘겼다 | 하면 될 수 있다 |
| `BAD_RESPONSE` | 2번 불러도 모델 응답을 쓸 수 없었다(형식 이탈·출처 없음) | 하면 될 수 있다 |
| `UNAVAILABLE` | AI 조사 기능을 쓸 수 없다(자격증명 등). 처리 도중 이렇게 되면 남은 가게가 모두 이 코드 | 운영 조치 후 |
| `ERROR` | 그 밖의 예외 | 같을 수 있다 |

**"웹에서 아무것도 못 찾음"은 실패가 아니다** — 조사는 끝났으므로 `NO_CHANGE` + Signal 0개로 나간다. 다시 해도 결과가 같다.
백엔드→AI 연결 실패·타임아웃처럼 AI 가 응답을 못 준 경우는 백엔드가 직접 실패로 기록한다.
- **동기 호출**이다 — 가게 한 곳에 5~40초. 여러 곳을 묶으면 응답이 오지 않는다

## 백엔드가 할 일

1. **조사 시작 API** — `POST /api/jobs {storeIds}` → `202 {jobId}` 를 바로 돌려주고 조사는 뒤에서 한다.
   선택된 가게 중 번호 없음·틀림(`dataProblem`)만 빼고 AI 에 보낸다. 국세청 불일치 가게도 보낸다(수정안은 AI 가 만든다)
2. **AI 호출** — 가게 하나씩 `POST {AI_BASE_URL}/investigations`. **동시 1~2곳**(넘으면 Vertex 429), **타임아웃 60~90초**.
   `@Async` + 작은 스레드 풀로 시작하고, 재시작에도 이어가야 하면 대기 상태를 DB 에 두고 `@Scheduled` 로 집는다
3. **결과 저장** — 가게마다 트랜잭션 하나

   | 응답 | 저장 |
   |---|---|
   | `classification` | `Task.classification`. **`NO_CHANGE` 이고 `lastCheckedAt` 이 90일 넘었으면 `ADDITIONAL_CHECK`** |
   | `proposedChanges` | `Task.proposedChanges` (jsonb 그대로) |
   | `signals[]` | `Signal` 한 행씩 (같은 이름 칸에 그대로) |
   | `failure` | Task 를 만들지 않는다. `Job.errorMessage` 에 한 줄씩 덧붙인다(예: `예시분식: AI 요청 한도를 넘어 조사하지 못했습니다`). `completedCount` 는 성공·실패 모두 올린다. 일부만 실패하면 Job 은 `DONE` |
   | AI 503 · 연결 실패 · 타임아웃 | 남은 가게를 멈추고 Job `FAILED` + `errorMessage` |

   **실패는 컬럼을 늘리지 않고 Job 으로 보여 준다.** 화면은 `targetCount` 와 Task 수를 비교해 "10곳 중 2곳 조사 실패"를 띄우고
   `errorMessage` 로 어느 가게가 왜 실패했는지 보여 준다. 다시 조사는 실패한 가게만 골라 새 Job 으로 돌린다. 실패는 드물다(실험
   37곳 중 2곳, 모두 429). 실패가 잦거나 가게별 재조사 화면이 필요해지면 그때 `Task` 에 실패 상태를 둔다
   (`classification` nullable + `failureReason`)

4. **결과 조회 API** — `GET /api/jobs/{jobId}`, `GET /api/jobs/latest`(프론트가 이미 부른다, 아래)
5. **엔티티**

   | 대상 | 변경 |
   |---|---|
   | `signal.confidence` (NOT NULL) | **nullable 로 바꿔 달라.** AI 는 모델 확신도를 주지 않고(멘토 결정) 항상 null 을 보낸다 — 출처 수(정수)는 0.0~1.0 범위 검사에 걸려 대신 넣을 수도 없다. `ddl-auto: update` 는 기존 컬럼의 NOT NULL 을 풀지 않으므로 이미 테이블이 있는 DB 에는 `ALTER TABLE signal ALTER COLUMN confidence DROP NOT NULL;` 을 직접 실행해야 한다 |
   | `signal.field` 컬럼 추가 (varchar, NOT NULL) | **이 Signal 이 어느 수정안 항목의 근거인지.** 값은 `task.proposed_changes` 의 키와 같은 `status`·`phone`·`addressRoad`·`name`. 없으면 수정안이 둘 이상일 때 Signal 과 짝지을 방법이 없다(`jsonb` 는 키 순서를 보존하지 않아 순서로도 못 맞춘다). 새 컬럼은 `ddl-auto` 가 추가하지만, NOT NULL 이라 `signal` 에 행이 이미 있으면 추가가 실패한다 |
   | (선택) `Task` 에 `placeUrl` 칸 | 두면 AI 가 카카오맵 장소 링크를 다시 응답에 넣는다 |
   | (선택) 조사 대상에 `lastCheckedAt` | AI 가 담당자 확인일보다 오래된 웹 글을 판정에서 빼는 데 쓴다(실험 중) |
   | `SignalType` | AI 는 `SIGNAL_HIGH` 만 쓴다. 1차(국세청) Signal 에 무엇을 쓸지와 함께 정리 |
   | `NtsCheckFilter` | `STATUS_MISMATCH` 주석 "AI 조사 대상"은 옛 설계 — "1차에서 우선확인"으로 |
   | `TaskClassification` | 주석 "산출 방법은 아직 정해지지 않았다" → 위 분류 규칙으로 |

담당자 승인은 이미 있는 `PATCH /api/stores/{id}`(값 반영) + `POST /api/stores/{id}/confirm`(확인일 갱신)으로 한다.

## 프론트와 맞출 것

프론트(`frontend/src/services/analysis.ts`)가 기대하는 결과 모양:

```ts
JobResultResponse = { jobId, finishedAt, tasks: TaskResponse[] }
TaskResponse = { taskId, storeId, storeName, storeAddress, classification,
                 evidences: [{ description, sourceLabel, sourceUrl }],
                 proposedChanges: [{ field: "가게 상태", description: "'휴업' 갱신" }] }
```

- `evidences` — AI 는 근거를 `signals` 에 담는다. 백엔드가 Signal 행을 이 모양으로 풀어 준다
- `proposedChanges` — 지금 AI 는 `{"phone": "053-…"}`(필드명·원본 값)를 준다. 수정안 생성을 AI 가 맡으므로
  **한글 라벨(`field`·`description`)도 AI 가 붙이는 쪽**으로 한다(예정). 원본 값은 담당자가 승인할 때 `Store` 를
  고치는 데 필요하니 함께 준다
- "조사 시작하기"(`frontend/src/hooks/store.ts` 의 `startSurvey`)는 지금 모달만 닫는다 — `POST /api/jobs` 를 부르고
  받은 `jobId` 로 결과 화면에 이동하게 바꾼다

## AI 쪽 할 일

- **국세청 불일치 행의 수정안** — `statusMismatch` 행은 웹검색 없이 1차 결과로 수정안·근거를 만든다(PROMPT-88 또는 별도 티켓)
- **수정안 한글 라벨** — `proposedChanges` 에 프론트가 그대로 그릴 `field`·`description` 을 함께 준다
- ~~백엔드 호출에 `X-API-KEY` 를 보내지 않는다~~ **(2026-10-06 완료)** `INTERNAL_API_KEY` 가 있으면 붙인다.
  키가 없으면 헤더를 **아예 안 붙인다** — 빈 값을 보내면 백엔드가 "틀린 키"로 보고 401 을 내서
  미설정과 키 오류를 구분할 수 없다
- ~~AI 서비스가 `docker-compose.yml` 에 없다~~ **(2026-10-06 완료)** `ai` 서비스로 들어갔다.
  **포트를 바깥으로 열지 않는다** — 백엔드만 부르면 되고, 열면 공개 주소에서 아무나 조사를 돌릴 수 있다
  (Vertex·카카오 쿼터가 걸린 호출이다)
- **AI 서버(`POST /investigations`)는 들어오는 요청 인증이 없다** — 지금은 포트를 안 열어 막고 있지만,
  열어야 할 일이 생기면 키 검사를 붙여야 한다. 남은 구멍이다
- **국세청 불일치 행의 수정안** 과 **수정안 한글 라벨** 은 그대로 남아 있다(위 참고)

## 타입이 어긋나지 않게 — 계약 테스트

`src/backend_client/models.py`·`src/investigation/models.py` 의 enum 은 백엔드 Java 를 손으로 옮긴 것이다. 이 팀은
같은 문제로 두 번 데였다(5주차 가게 상태가 화면에서 빈 칸, 6주차 `TASK_HIGH` ↔ `PRIORITY_CHECK`).

`tests/backend_client/test_contract.py` 가 **백엔드 Java 파일을 직접 읽어 enum 값을 대조한다** — `StoreStatus`,
`StatusComparison`, `NtsLookupResult`, `BusinessState`, `NtsCheckFilter`, `TaskClassification`, `SignalType`.

`ChangeField` 는 **상수 이름이 일부러 달라서**(백엔드 `ADDRESS_ROAD` ↔ AI `"addressRoad"`) 이름 대조를 못 한다.
대신 **짝이 맞는지**를 본다 — 양쪽에 항목이 하나만 늘어도 깨진다. 그리고 AI 가 보내는 값이 실제로
`StoreUpdateRequest` 의 필드명인지도 본다. 여기가 어긋나면 담당자가 수정안을 승인해도
`PATCH /api/stores/{id}` 에 실을 칸을 못 찾는다.
백엔드가 값을 바꾸면 AI 테스트가 깨진다. **칸 이름도 대조한다**(2026-10-06 추가). AI 가 **실제로 직렬화해 보내는** 칸이 백엔드
`Signal`·`Task` 엔티티에 자리가 있는지 본다 — 스키마가 아니라 직렬화 결과를 보는 이유는
`observed`·`sourceCount` 처럼 `exclude=True` 로 응답에서 빠지는 칸이 있어서다.
AI 가 칸을 더해도, 백엔드가 칸 이름을 바꿔도 깨진다(둘 다 일부러 어긋내 확인했다).

DTO 가 아직 없어 엔티티를 본다. 백엔드가 응답 DTO 를 만들면 그쪽으로 옮기는 게 낫다.
`nts-checks` 응답 필드 17개는 PR #32 브랜치의 실제 백엔드에 붙여 이름·타입이 맞는 걸 확인했다(2026-09-23).

## 조사 구현 고르기 — `INVESTIGATOR`

`get_investigator()` 가 환경변수로 구현을 고른다. 이전에는 무엇을 하든 `UnavailableInvestigator`
였고, 그래서 **백엔드가 불러도 무조건 503** 이었다.

| 값 | 꽂히는 것 | 쓰는 때 |
|---|---|---|
| `web` | `WebInvestigator` (Vertex + 카카오맵) | 실제 조사 |
| `mock` | `MockInvestigator` | **연동 흐름만** 확인할 때 — 외부 호출이 없어 빠르고 결정적이다 |
| `off` | `UnavailableInvestigator` | 붙이기 전 상태를 일부러 유지할 때 |
| (없음) | `GOOGLE_CLOUD_PROJECT` 가 있으면 `web`, 없으면 `off` | 기본 |

`web` 인데 자격증명·의존성이 빠져 있으면 **500 으로 죽지 않고 `off` 로 떨어진다.** 못 하는 것을
못 한다고 답하는 쪽이 낫다.

지금 무엇이 꽂혀 있는지는 `GET /health` 가 알려 준다.

```
$ curl localhost:8000/health
{"status":"ok","investigator":"MockInvestigator"}
```

503 이 날 때 "자격증명이 없어서"인지 "코드가 안 꽂혀서"인지를 배포 환경에서 확인할 길이 이것뿐이다.

## 실행

```bash
# ai/ 에서
uv sync
cp .env.example .env          # BACKEND_BASE_URL, GOOGLE_CLOUD_PROJECT, KAKAO_REST_API_KEY
uv run uvicorn src.server.main:app --reload --port 8000

curl localhost:8000/health              # AI 프로세스만
curl localhost:8000/backend-health      # 백엔드에 닿는지
```

`BACKEND_BASE_URL` 기본값은 `http://localhost:8080`, docker compose 에서는 `http://backend:8080`.
