# 에러 처리 가이드

> **Front / Back 공용 문서입니다.** 에러 응답은 두 파트가 함께 지키는 계약이라
> 한 곳에만 둡니다. 프론트는 "프론트가 읽는 법"까지만 보면 됩니다.

우리 API 는 실패를 **RFC 9457(Problem Details for HTTP APIs)** 형식으로 돌려줍니다.
Spring Framework 6 이 표준으로 지원하는 형식이고, 프레임워크가 던지는 예외까지 자동으로 같은 모양이 됩니다.

> 예외를 던지는 방법(`ErrorCode` + `CustomException`)은 [백엔드_코딩_컨벤션_가이드.md](../backend/docs/백엔드_코딩_컨벤션_가이드.md) 참고.

---

## 응답 형태

```json
{
  "type":     "https://kakaotechcampus-4.github.io/ktc4-kyungpook-6/errors/invalid-request",
  "title":    "요청 값이 올바르지 않습니다",
  "status":   400,
  "instance": "/api/stores/1",
  "errors":   [{ "field": "name", "message": "가게명은 1~200자여야 합니다" }]
}
```

| 필드 | 누가 채우나 | 설명 |
|---|---|---|
| `type` | 우리 | **에러 종류의 유일한 식별자.** [RFC 9457 §3.1.1](https://www.rfc-editor.org/rfc/rfc9457.txt) 이 이걸 "primary identifier"로 쓰라고 못박는다. 지금 응답에 실리는 URI는 문서가 아직 없어도 된다(비역참조 허용) — 아래 [값 목록](#현재-나가는-type-값) 참고 |
| `title` | 우리 | **한글.** 에러 종류의 이름. 같은 종류면 항상 같은 문구다 |
| `status` | Spring | HTTP 상태코드 |
| `detail` | (지금은 없음) | **이번 건에 대한 구체적인 설명.** `decorate()`가 모든 경로에서 무조건 비워서, 지금 코드에서는 **항상** 키 자체가 사라진다(있을 수도 있다는 뜻이 아니다). `title`과 헷갈리지 말 것 — `title`은 종류 이름, `detail`은 이번 건 설명. CustomException이 구체 정보를 실어야 할 날이 오면 그때 값이 생긴다 |
| `instance` | Spring | 요청 경로. 자동으로 채워진다 |
| `errors` | 우리 | 필드별 검증 오류. **요청 본문 검증에 실패했을 때만** 실린다 |

`code` 필드는 없다. 에러 종류를 구분하는 건 **`type` 하나**다.

응답 `Content-Type` 은 `application/json` 이 아니라 **`application/problem+json`** 이다.

## 프론트가 읽는 법

1. **화면에 보여줄 문구는 `title`** 을 씁니다. 한글로 나옵니다.
2. **분기는 `type`** 으로 합니다. `status` 만으로는 400 안에서 원인을 구분할 수 없고,
   `type`이 URI 형태라 길지만 스펙에 값 목록이 enum으로 박혀 있어 상수로 뽑아 쓰면 됩니다.
   ```ts
   import type { components } from "./api";
   type ErrorType = components["schemas"]["ErrorResponse"]["type"];
   // "https://.../errors/invalid-request" | "https://.../errors/not-found" | ... | undefined
   ```
   > 스펙에 `required` 목록이 없어서 `ErrorResponse`의 모든 필드가 `optional`로 생성됩니다
   > (`type?: ...`). `undefined` 케이스를 같이 처리해야 합니다 — 실무에서는 대개 발생하지 않지만
   > 타입 체커는 그 경우도 요구합니다.
3. **`detail` 은 지금 코드에서는 항상 없습니다.** 있을 수도 있다는 뜻이 아니라, `decorate()`가
   모든 경로에서 무조건 비웁니다. 화면 로직에서 `detail` 유무를 분기 조건으로 쓰지 마세요 —
   지금은 절대 오지 않습니다. 나중에 CustomException이 구체 정보를 싣게 되면 이 문서를 갱신합니다.
4. **필드별 에러 표시는 `errors`** 를 씁니다.
   - 없을 수도 있습니다(본문 검증 실패가 아닌 경우 필드 자체가 안 옵니다)
   - **한 필드에 여러 개가 올 수 있습니다.** 예: `name` 이 빈 문자열이면 `@Size` 와 `@Pattern` 이
     둘 다 걸려 `name` 항목이 두 번 옵니다. 순서도 보장되지 않습니다
   - ⚠️ **쿼리 파라미터·경로변수 검증 실패에는 `errors` 가 실리지 않습니다.**
     `GET /api/stores?page=-1` 은 `{"type":"...invalid-request","title":"요청 값이 올바르지 않습니다"}` 만 옵니다 —
     어느 파라미터가 왜 틀렸는지 응답으로는 알 수 없습니다(서버 로그에는 남습니다).
     필드 단위 오류 표시는 **요청 본문** 검증에만 가능합니다
5. 타입은 손으로 적지 말고 스펙에서 생성하세요. 생성되는 타입 이름은 **`ErrorResponse`**, 필드별 오류는 **`FieldError`** 입니다.
   ```bash
   npx openapi-typescript http://localhost:8080/v3/api-docs -o src/types/api.d.ts
   ```
   `type` 필드는 스펙에 실제 나올 수 있는 URI 전체가 enum으로 박혀 있어, 생성된 타입에서
   문자열 리터럴 유니온으로 좁혀져 나옵니다 — 값 집합을 놓칠 일이 없습니다.

### 현재 나가는 `type` 값

| `type` (베이스: `https://kakaotechcampus-4.github.io/ktc4-kyungpook-6/errors/`) | HTTP | `title` | `errors` | 언제 |
|---|---|---|---|---|
| `invalid-request` | 400 | 요청 값이 올바르지 않습니다 | 본문 검증 실패일 때만 | 요청이 잘못된 대부분의 경우 (본문 검증 실패, 깨진 JSON, 잘못된 enum, 쿼리·경로 파라미터 오류) |
| `store-not-found` | 404 | 요청한 가게를 찾을 수 없습니다 | 없음 | 가게 수정·확인 API 에서 `storeId` 에 해당하는 가게가 없음 |
| `not-found` | 404 | 요청한 경로를 찾을 수 없습니다 | 없음 | 없는 경로 |
| `method-not-allowed` | 405 | 지원하지 않는 요청 방식입니다 | 없음 | 지원하지 않는 HTTP 메서드 |
| `unsupported-media-type` | 415 | 지원하지 않는 형식입니다 | 없음 | `Content-Type` 이 잘못됨 |
| `internal-error` | 500 | 서버 오류가 발생했습니다 | 없음 | 서버에서 예상 못 한 예외 |
| `bizno-api-error` | 502 | 비즈노 API 호출에 실패했습니다 | 없음 | 외부 API(비즈노) 호출 실패. **지금은 HTTP 응답으로 나가지 않음** — 아래 참고 |
| `nts-api-error` | 502 | 국세청 API 호출에 실패했습니다 | 없음 | 외부 API(국세청) 호출 실패. **지금은 HTTP 응답으로 나가지 않음** — 아래 참고 |

`store-not-found` 와 `not-found` 는 **둘 다 404** 입니다. "가게가 없음"과 "경로가 없음"은 `status` 로는
구분되지 않으니 `type` 으로 분기하세요.

`bizno-api-error` / `nts-api-error` 는 지금 어떤 API 도 응답으로 돌려주지 않습니다. 비즈노·국세청을
부르는 곳이 국세청 배치(`NtsCheckScheduler`) 하나뿐이고, 배치가 이 예외를 안에서 잡아 로그로만 남기기
때문입니다. 다만 Swagger 스펙의 `type` 목록은 `ErrorCode` 전체를 자동으로 싣기 때문에 **생성된 타입에는
이 값이 보입니다.** 외부 API 를 직접 부르는 API 가 생기면 그때부터 실제로 나갑니다.

⚠️ **`invalid-request` 는 지금 여러 원인을 한데 묶고 있습니다.** 클라이언트 입력 문제뿐 아니라
엔티티 불변식 위반·외부 API 인자 검증 실패도 같은 종류로 나갈 수 있습니다.
"이 종류면 이 화면" 같은 세밀한 분기를 붙이기 전에 백엔드와 한 번 확인하세요.

### 유형별 응답 예시

본문 모양은 모든 유형이 같습니다. 유형마다 달라지는 건 위 표의 `type`·`status`·`title`·`errors` 뿐이라,
표의 한 행이 곧 그 유형의 응답입니다. 본문 검증 실패 예시는 맨 위 [응답 형태](#응답-형태)에 있고,
여기엔 모양이 다른 두 가지만 적습니다. (실서버 응답 그대로)

**가게가 없을 때** — `PATCH /api/stores/99999`

```json
{
  "type": "https://kakaotechcampus-4.github.io/ktc4-kyungpook-6/errors/store-not-found",
  "title": "요청한 가게를 찾을 수 없습니다",
  "status": 404,
  "instance": "/api/stores/99999"
}
```

**쿼리 파라미터가 잘못됐을 때** — `GET /api/stores?page=-1`

```json
{
  "type": "https://kakaotechcampus-4.github.io/ktc4-kyungpook-6/errors/invalid-request",
  "title": "요청 값이 올바르지 않습니다",
  "status": 400,
  "instance": "/api/stores"
}
```

같은 `invalid-request` 라도 본문 검증 실패와 달리 **`errors` 가 없습니다.** 어느 파라미터가 틀렸는지는
응답으로 알 수 없습니다(위 [프론트가 읽는 법](#프론트가-읽는-법) 4번 참고).

## 백엔드가 새 에러를 추가하는 법

`ErrorCode` 에 항목을 추가하고 `CustomException` 으로 던집니다. 그게 전부입니다.

```java
// ErrorCode.java — RFC 9457 §4 가 problem type 문서에 요구하는 세 가지(type URI/title/status)를 그대로 담는다
STORE_NOT_FOUND(HttpStatus.NOT_FOUND, "요청한 가게를 찾을 수 없습니다"),

// 서비스 어디선가
throw new CustomException(ErrorCode.STORE_NOT_FOUND);
```

`type` URI는 `ErrorCode.getType()` 이 enum 이름을 케밥케이스로 바꿔 자동으로 만듭니다.
`GlobalExceptionHandler` 는 건드리지 않습니다 — **비즈니스 예외(`CustomException`)일 때만입니다.**
`type`·`title` 이 자동으로 채워집니다. 프레임워크 예외(404/405/415/5xx)에 새 상태코드를 대응시키려면
`GlobalExceptionHandler.errorCodeFor()` 를 고쳐야 합니다 — 아래 [핸들러를 고칠 때 주의할 것](#️-핸들러를-고칠-때-주의할-것) 참고.

**사용자에게 보이는 한글 문구는 `ErrorCode.title` 에만 둡니다.** 핸들러 안에 문구를 적지 마세요 —
두 군데로 흩어지면 나중에 어디를 고쳐야 할지 알 수 없게 됩니다.

### `ErrorCode` 를 도메인별로 쪼갤 시점

**개수로 정하지 않습니다.** *"다른 도메인 담당자와 같은 파일에서 상수를 추가하다 충돌이 반복될 때"* 가 신호입니다.
그때 공통 인터페이스를 뽑는 리팩터링은 기계적이라 지금 미리 할 이유가 없습니다.

## ⚠️ 핸들러를 고칠 때 주의할 것

### `@ExceptionHandler` 를 함부로 추가하면 앱이 안 뜹니다

`GlobalExceptionHandler` 는 `ResponseEntityExceptionHandler`(이하 REEH)를 상속합니다.
REEH 는 Spring MVC 내장 예외 **20종**을 이미 `@ExceptionHandler` 로 잡고 있어서,
그중 하나를 우리가 또 선언하면 **기동 시점에** 이렇게 죽습니다.

```
IllegalStateException: Ambiguous @ExceptionHandler method mapped for
[ExceptionHandler{exceptionType=...HandlerMethodValidationException, mediaType=*/*}]
```

컴파일은 통과하고 **런타임 기동 실패**로만 드러납니다.
`BackendApplicationContextTest` 가 이걸 잡아주니 반드시 같이 돌리세요.

**그 20종을 다르게 처리하고 싶으면** `@ExceptionHandler` 를 새로 만들지 말고
REEH 의 `handleXxx` 메서드를 **`@Override`** 하세요. 단 두 가지를 조심해야 합니다.

- **`body` 파라미터가 `null` 로 들어옵니다.** REEH 의 `handleXxx` 19개 중 14개가 `body=null` 을 넘깁니다.
  `(ProblemDetail) body` 로 바로 캐스팅하면 그 14개 경로가 깨집니다.
  `super.handleXxx(...)` 를 먼저 호출해 완성된 `ResponseEntity` 를 받은 뒤 그 본문을 확인하세요.
- **반환값이 `null` 일 수 있습니다.** 응답이 이미 커밋된 경우입니다. 반드시 체크하세요.

### `type` 을 채웠다고 `title` 이 자동으로 고쳐지지 않습니다

Spring 의 `ProblemDetail.getTitle()` 은 `title` 이 `null` 이면 상태코드의 **영어** reason phrase로
폴백합니다. 이 폴백은 `type` 값과 완전히 무관합니다 — `setType()` 만 하고 `setTitle()` 을 빠뜨리면
`type` 은 우리 URI인데 `title` 은 영어인, 표준상 가장 어색한 상태가 됩니다.
**`decorate()` 는 항상 `setType()` 과 `setTitle()` 을 함께 호출해야 합니다.**
`GlobalExceptionHandlerTest.titleIsNeverTheDefaultStatusPhrase` 가 이 회귀를 잡습니다.

### 전역 예외 처리기는 `GlobalExceptionHandler` **하나만** 둡니다

`@RestControllerAdvice` 를 하나 더 만들면 기동은 되지만 **우선순위가 꼬여 규격이 조용히 우회됩니다.**
(`@Order` 가 더 높은 advice 가 같은 예외를 잡으면 그쪽 응답이 나갑니다 — 실측 확인)
새 예외를 추가할 때는 advice 를 만들지 말고 `ErrorCode` 에 항목을 더하세요.

### 로그를 지우지 마세요

REEH 를 상속하는 순간 Spring 이 자동으로 남기던 WARN 로그가 사라집니다(실측 확인: 7줄 → 1줄).
`handleExceptionInternal` 의 `log.warn` 이 그 자리를 대신하고 있습니다.
**응답 `title` 은 고정 문구로 나가므로, 원본 예외 정보는 로그에만 남습니다.** 지우면 추적이 불가능해집니다.

## 통일 범위

**DispatcherServlet 안에서 발생하는 예외**까지입니다.

서블릿 필터 단계에서 나는 것은 REEH 가 보지 못하고, **지금도** 스프링 기본 형태로 나갑니다.

```json
{ "timestamp": "...", "status": 500, "error": "Internal Server Error", "path": "/boom" }
```

`type`·`title` 이 없으므로 프론트는 **이 필드들이 없는 응답도 처리할 수 있어야 합니다.**
지금은 필터가 없어서 실제로 마주칠 일이 없지만, **Spring Security 를 도입하면 401/403 이 이 경로**로
나갑니다(`AuthenticationEntryPoint`·`AccessDeniedHandler` 로 별도 처리해야 합니다).

## Swagger 문서화는 자동으로 따라오지 않습니다

핸들러는 `@RestControllerAdvice` 로 한 번에 적용되지만, **OpenAPI 스펙에 에러 응답이 뜨는 것은
컨트롤러마다 손으로 붙여야** 합니다.

```java
@ApiResponse(responseCode = "404", description = "가게를 찾을 수 없는 경우",
        content = @Content(mediaType = "application/problem+json",
                schema = @Schema(implementation = ApiProblemDetail.class)))
```

> `ApiProblemDetail` 은 `ProblemDetail` 에 `errors` 를 정식 필드로 더한 클래스다.
> `errors` 없이 순수 `ProblemDetail` 로 두면 스펙에 `additionalProperties` 로만 찍혀서
> 프론트가 타입을 생성해도 구조를 알 수 없다.
>
> `type` 필드의 enum 목록은 애노테이션이 아니라 `ErrorTypeSchemaCustomizer` 가 기동 시점에
> `ErrorCode.values()` 를 읽어 채운다 — `@Schema(allowableValues=...)` 는 컴파일 타임 상수만
> 받아서 enum 값을 직접 참조할 수 없기 때문이다. `ErrorCode` 에 항목을 추가하면 이 목록도
> 자동으로 갱신된다 — 손으로 나열한 목록과 동기화가 안 맞을 위험이 없다.
