# 배포 환경에서 작업하는 방법

PROMPT-150 · 작성 2026-10-13 · 2차 점검 반영 2026-10-16 (PROMPT-155)

**배포본을 고쳐 가며 일하는 고리**를 적어 둔 문서입니다. 화면이 실제로 도는지는 로컬에서만 보면
알 수 없고, 배포 환경은 바깥에서 닿는 범위가 좁아서 "무엇을 어떻게 확인할 수 있는지"를 모르면
한 바퀴를 돌리지 못합니다. 여기 적힌 수치는 전부 **실제로 재 본 값**입니다(2026-10-13 과
2026-10-16).

> 2차(PROMPT-150 의 뒷부분)에서 이 고리를 그대로 돌릴 수 있도록 적었습니다. 틀린 게 보이면
> 그 자리에서 고치고 PR 에 적어 주세요.

---

## 1. 배포 환경이 무엇으로 이뤄져 있나 (dev)

| | |
|---|---|
| 화면 | `https://goodradar.mojan.kr/` |
| API | `https://goodradar-api.mojan.kr/` (Swagger UI `/swagger-ui/index.html`, 스펙 `/v3/api-docs`) |
| 올라가는 것 | `docker-compose.yml` + `docker-compose.dev.yml` 을 병합해 띄우는 **postgres · backend · frontend · ai** |
| 돌리는 기계 | GitHub Actions **self-hosted 러너**(`Dev Enviroment Server`, Linux). 팀 자체 서버입니다 |

운영(prod)은 AWS 쪽이고 **별개**입니다. dev 가 된다고 prod 도 된다는 뜻이 아닙니다(PROMPT-117).

## 2. 한 바퀴 — 고쳐서 배포하고 확인하기

```
개인 브랜치 → develop PR 머지
        ↓  (자동, 22~50초)
.github/workflows/deploy-dev.yml  →  scripts/deploy.sh dev up -d --build
        ↓
배포본에서 확인 → 고칠 것 발견 → 다시 브랜치
```

### 2-1. 머지하면 무엇이 도는가

`deploy-dev.yml` 은 **`develop` 에 push 될 때만** 돕니다(`workflow_dispatch` 가 없어 손으로 돌릴 수
없습니다). 하는 일은 체크아웃 → `scripts/deploy.sh dev up -d --build --remove-orphans` → dangling 이미지 정리.

- **`clean: false` 를 지우지 마세요.** 서버 `.env` 가 러너 작업 폴더(레포 안)에 있어서, 정리되면
  시크릿 없이 컨테이너가 조용히 뜹니다. 값이 비어도 compose 가 멈추지 않기 때문에 **티가 안 납니다.**
- `concurrency: cancel-in-progress` 라 연달아 머지하면 앞 배포가 취소됩니다.

### 2-2. 배포가 됐는지 확인

```bash
gh run list --workflow deploy-dev.yml --limit 5
```

실측 소요: **22 · 24 · 25 · 37 · 50초** (최근 5회). 머지하고 1분 안에 올라온다고 보면 됩니다.

### 2-3. 내 코드가 올라갔는지 확인

배포본이 실제로 어느 코드인지는 **API 표면으로** 확인합니다. 커밋 해시를 알려 주는 엔드포인트는 없습니다.

```bash
curl -s https://goodradar-api.mojan.kr/v3/api-docs | python3 -c "
import sys,json
p=json.load(sys.stdin)['paths']
n=sum(1 for k in p for m in p[k] if m in ('get','post','put','patch','delete'))
print('엔드포인트', n, '개')
print('내가 더한 경로 있나:', '/api/admin/stores/imports' in p)
"
```

## 3. 바깥에서 어디까지 닿나 — 실측

| 대상 | 결과 |
|---|---|
| 80 · 443 | 열림 |
| 5432 (Postgres 표준) | **막힘** |
| 22 (SSH) | **막힘** |
| Postgres | 인프라가 연 **비표준 포트**로 닿습니다. 포트 번호는 공개 저장소에 적지 않습니다 — 팀 채널에서 받으세요 |
| AI 서버 8000 | **닿지 않습니다** (2026-10-16 실측 · 0.018초에 연결 거부). compose 는 여는 설정인데 실제로는 막혀 있습니다 |

그래서 **밖에서 쓸 수 있는 진입점은 셋뿐**입니다.

1. **HTTP API** — Swagger 로 전부 보입니다
2. **DB 읽기** — 아래 3-2
3. **GitHub Actions 로그** — 배포가 실패했을 때의 유일한 단서

### 3-0. DB 는 왜 열어 두고, AI 는 왜 열지 않나

**원칙은 닫는 것입니다.** DB 를 열어 둔 것은 서버에 들어가지 않고도 자료를 들여다볼 수 있어야
해서입니다(SSH 가 막혀 있습니다). 10주차 멘토 리뷰에서 *"지금 팀 상황에서는 외부 접근이 가능하게
두는 것이 좋을 것 같습니다"* 라는 답을 받아 그대로 둡니다.

**prod 는 닫혀 있습니다.** `docker-compose.yml`(base)은 backend·frontend 만 포트를 열고, postgres·ai 는
`docker-compose.dev.yml` 에서만 엽니다.

현업에서는 dev DB 라도 바깥에 노출하지 않고 **서버 인그레스 통제나 QueryPie 같은 도구**를 쓴다고 합니다.
서버에 들어갈 길이 생기면 닫는 쪽이 맞습니다.

**AI 는 열지 않습니다.** `POST /investigations` 는 **Vertex 과금이 걸린 호출**이라 DB 와 성격이 다릅니다.
읽어도 돈이 들지 않는 DB 와 달리, 한 번 부를 때마다 비용이 나갑니다. 조사는 백엔드가 내부망
(`http://ai:8000`)으로 부르니 **바깥 포트가 닫혀 있어도 기능은 전부 돕니다.**

`docker-compose.dev.yml` 은 `0.0.0.0:${AI_PORT:-8000}:8000` 으로 여는 설정인데 **바깥에서는 닿지
않습니다.** 서버 방화벽이 막는 것인지, ai 컨테이너가 떠 있지 않은 것인지는 서버에 들어가야 갈립니다.
`INTERNAL_API_KEY` 는 `${INTERNAL_API_KEY:?}` 로 필수라 키 없이 부를 수는 없습니다.

### 3-3. 배포본에서 AI 조사가 한 달째 죽어 있었습니다 (2026-09-18 ~ 10-16)

화면에는 "실패" 만 떠서 아무도 몰랐습니다. **키 하나가 빠진 게 아니라 겹이 넷이었습니다.**

| | dev (개인서버) | prod (AWS) |
|---|---|---|
| 지금 상태 | ✅ **16초에 5/5** | ❌ 아직 — 아래 "prod" 절 |

아래는 그 넷을 찾은 과정입니다. 같은 벽에 또 막히면 순서대로 보세요.

**배포본에서 직접 재 봤습니다.** 가공 자료 8곳을 넣고 5곳을 조사시킨 결과입니다.

```
POST /api/jobs           → {"jobId":1,"targetCount":5,"excluded":[]}
GET  /api/jobs/1         → status FAILED · completedCount 0 · tasks 0개
                            errorMessage "서버 오류로 조사를 멈췄습니다"
걸린 시간                  1초
```

**1초**가 핵심입니다. 조사는 가게당 수십 초가 걸리는 일인데, AI 를 부르자마자 503 이 돌아와서
한 곳도 시작하지 못하고 끝납니다. 같은 자료를 **같은 compose** 로 로컬에 띄워 돌리면
**8/8 성공(110초)** 입니다 — 차이는 자격증명 하나뿐입니다.

화면에서는 조사가 실패했다고만 보이고, 왜 실패했는지는 밖에서 알 수 없습니다.

`docker compose config` 로 ai 컨테이너가 받는 값을 뽑아 보면 이렇습니다.

```
GOOGLE_CLOUD_PROJECT = ''     INVESTIGATOR = ''     KAKAO_REST_API_KEY = ''
```

`ai/src/server/main.py:130` 이 앞의 둘이 비면 `UnavailableInvestigator` 를 돌려줘 **항상 503** 입니다.
세 겹으로 조용합니다.

| | |
|---|---|
| `.env.example`·`.env.development.example` | `GOOGLE_CLOUD_PROJECT` 가 **없습니다** — 서버에 넣어야 한다는 안내 자체가 없습니다 |
| base compose | `${GOOGLE_CLOUD_PROJECT:-}` 로 **빈 값을 허용**합니다. 없어도 배포는 success 입니다 |
| AI 코드 | 없으면 503. 화면은 뜨고 조사만 조용히 실패합니다 |

**키를 넣어도 그것만으로는 안 됩니다.** `web_research.py:351` 이 `genai.Client(vertexai=True, …)` 라
프로젝트 ID 말고 **자격증명**을 따로 요구하는데,

```
GOOGLE_APPLICATION_CREDENTIALS    없음
ai 컨테이너 volumes               없음 (backend·postgres 만 있습니다)
```

자격증명이 컨테이너로 들어갈 길이 compose 에 없습니다. dev 는 GCE 가 아니라 **팀 자체 서버**라
메타데이터로 받는 ADC 도 안 됩니다. `ai/.env.example:12-13` 이 *"API 키 없이 ADC로 인증한다 — 먼저
`gcloud auth application-default login` 필요. 이 경로는 실행하는 사람의 구글 계정/GCP 결제 계정에
묶인다"* 고 적어 둔 그대로입니다.

**그래서 이렇게 붙였습니다** (2026-10-16).

```
GitHub Secrets (GCP_SA_KEY)
   ↓  deploy-dev.yml 이 배포 때 ~/.ktc4/vertex.json 으로 씁니다 (레포 밖, 디렉터리 700 · 파일 644)
VERTEX_KEY_PATH
   ↓  compose 가 컨테이너 안 /run/secrets/vertex.json 으로 읽기 전용 마운트
GOOGLE_APPLICATION_CREDENTIALS=/run/secrets/vertex.json
```

🔴 **키 파일은 644 여야 합니다.** ai 컨테이너가 이 파일을 직접 마운트해 읽는데, 그 안에서는
`adduser --system app`(`ai/Dockerfile:27`)이 만든 사용자로 돕니다. 600 으로 써 두면 컨테이너가
못 읽어 조사가 `[Errno 13] Permission denied: '/run/secrets/vertex.json'` 로 실패합니다
(2026-10-16 에 실제로 그랬습니다). 호스트 쪽 보호는 **디렉터리 700** 이 합니다.

**서버 `.env` 를 고치지 않아도 됩니다.** compose 는 셸 환경변수를 `--env-file` 보다 먼저 읽어서,
워크플로 step 의 `env:` 로 넘긴 값이 이깁니다. SSH 가 막혀 있어도 저장소 admin 권한만으로 붙습니다.

### ⚠️ 브라우저가 읽는 주소는 따로 넣어야 합니다

`PUBLIC_BACKEND_URL` 은 **빌드할 때 프론트 번들에 박히는 값**입니다. 비우면 옛 키
(`BACKEND_BASE_URL` — AI 가 백엔드를 부르는 **내부** 주소)로 떨어지는데, 그 값은 서버마다
내부용으로 맞춰져 있어서 **브라우저가 자기 PC 를 부르게 됩니다.**

2026-10-16 에 실제로 그 상태였습니다.

```
dev  번들에 http://localhost:8015 이 박혀 있어 화면에서 로그인이 되지 않았다
     (API 자체는 정상 — POST /api/auth/login 200)
prod 번들에 http://localhost:8080 이 박혀 있었다(재배포로 고침)
```

| 환경 | 넣는 곳 | 값 |
|---|---|---|
| dev | 저장소 **Variables** `PUBLIC_BACKEND_URL` | `https://goodradar-api.mojan.kr` |
| prod | **운영 서버 `.env`** 의 `PUBLIC_BACKEND_URL` | 운영 백엔드 공개 주소 |

dev 는 **서버 `.env` 를 고치지 않아도 됩니다**(저장소 Variables 가 이깁니다). prod 는 반대로
**서버 `.env` 가 정답입니다**(아래). 어느 쪽이든 값이 바뀌면 **다시 배포해야** 번들에 박힙니다.

### 넣어야 하는 시크릿·변수

| 이름 | 종류 | 없으면 |
|---|---|---|
| `GCP_SA_KEY` | Secret | 조사가 503 (화면은 정상) |
| `GCP_PROJECT_ID` | Secret | 같음 |
| `KAKAO_REST_API_KEY` | Secret | 지도 확인 없이 웹검색만 |
| `NAVER_CLIENT_ID`·`NAVER_CLIENT_SECRET` | Secret | 네이버 대조 불가 |
| `AGENT_API_KEY` | Secret | 판단 모델을 프록시로 못 씀(Vertex 로 떨어짐) |
| `AI_NAVER_LOCAL_ENABLED`·`AI_KAKAO_COMPARE_ENABLED`·`AI_AGENT_ENABLED`·`AI_AGENT_MODEL` | Variable | 전부 꺼짐(지금과 같은 동작) |

스위치를 Secret 이 아니라 Variable 로 둔 이유는, **켜졌는지 눈으로 보이는 편이 낫기** 때문입니다.

### 붙은 뒤에 확인하는 법

`deploy-dev.yml` 은 **develop 에 push 될 때** 돌아서, 머지되기 전에는 시험할 수 없습니다.
머지된 다음 이 순서로 확인합니다.

```bash
# 1. 배포가 키를 찾았는가 — 로그에 서비스 계정 주소가 찍힙니다
gh run list --workflow=deploy-dev.yml --limit 1
gh run view <id> --log | grep "서비스 계정"

# 2. 한 바퀴 — 조사가 FAILED 를 벗어나는가
TOKEN=<관리자 토큰> scripts/integration-test.sh _local/작업/배포환경_점검/시연용_가공자료.json
```

고쳐졌으면 **5곳 성공 · 수십 초**가 나옵니다. 1초에 FAILED 면 키가 여전히 안 들어간 것입니다
(`GCP_SA_KEY` 가 비었거나, JSON 이 깨졌거나).

### 🔴 자격증명을 다 고쳐도 49ms 에 죽었습니다 — DB CHECK 제약

이게 진짜 벽이었습니다. 자격증명·주소를 전부 고친 뒤에도 조사가 **49ms** 에 실패했습니다.
1차 결과(Task)를 저장하는 자리에서 DB 가 거절하고 있었습니다.

`Task.classification` 의 CHECK 제약이 **초안 시절 이름**(`TASK_HIGH`·`TASK_LOW`·`TASK_NONE`)만
허용한 채 남아 있었습니다. 코드는 멘토 리뷰(PR #25)로 `PRIORITY_CHECK`·`ADDITIONAL_CHECK`·
`NO_CHANGE` 로 바뀌었는데, 배포본 DB 만 옛 제약을 들고 있었던 것입니다.

🚨 **`ddl-auto: update` 는 CHECK 제약도, NOT NULL 도 고치지 않습니다.** 표와 칸은 더해 주지만
제약은 처음 만들 때 그대로 둡니다. 그래서 **로컬은 되고 배포본만 안 되는** 상태가 조용히 쌓입니다
(로컬은 DB 를 자주 새로 만들어서 티가 안 납니다).

### ✅ 이건 Flyway 로 막았습니다 (`PROMPT-159`)

`ddl-auto` 를 **`validate`** 로 바꿨습니다. 스키마를 건드리지 않고 엔티티와 맞는지만 보고,
어긋나면 **기동이 멈춥니다.** 조용히 어긋난 채 도는 일이 없어집니다.

스키마는 이제 **`backend/src/main/resources/db/migration/` 의 SQL** 이 바꿉니다.

```
V1__baseline_schema.sql            Flyway 를 들이기 전 스키마 그대로 (고치지 않습니다)
V2__sync_constraints_with_code.sql 이미 돌던 DB 의 CHECK·NOT NULL 을 코드에 맞춥니다
```

**이미 돌고 있는 DB 는 V1 을 실행하지 않습니다.** `baseline-on-migrate` 가 켜져 있어 Flyway 가
"V1 까지는 끝난 것"으로 도장만 찍고 V2 부터 돌립니다. 빈 DB(로컬·CI)는 V1 부터 그냥 돕니다.

> **엔티티를 고쳤으면 마이그레이션 파일도 같이 씁니다.** 안 쓰면 `validate` 가 기동을 멈춥니다 —
> 그게 이 설정의 목적입니다. 파일 이름은 `V<다음번호>__<무엇을_하는지>.sql` 입니다.

**한 번 배포된 마이그레이션 파일은 고치지 않습니다.** 내용이 바뀌면 Flyway 체크섬이 어긋나
기동이 멈춥니다. 고칠 일이 생기면 다음 번호로 새 파일을 만듭니다.

#### 배포 로그에 이 경고가 뜨면

```
WARN  옛 값이 남아 있어 아직 검증하지 못했습니다: task.task_classification_check
      — 자료를 정리한 뒤 ALTER TABLE task VALIDATE CONSTRAINT task_classification_check 를 돌리세요
```

**배포는 멈추지 않습니다.** CHECK 제약을 `NOT VALID` 로 걸기 때문입니다 — 그냥 걸면 Postgres 가
이미 들어 있는 행까지 검사해서, 옛 값이 한 줄이라도 있으면 마이그레이션이 실패하고 백엔드가
아예 뜨지 않습니다. 기동할 때 자동으로 도는 것이라 그 실패는 곧 서비스 중단입니다.

`NOT VALID` 라도 **새로 들어오는 행은 제대로 막습니다.** 고치려던 것이 "앞으로 저장되는 값이
거절당하는 일" 이므로 이것으로 충분합니다. 경고에 적힌 표의 옛 자료를 정리한 뒤 그 `VALIDATE`
명령을 한 번 돌리면 깨끗해집니다.

### prod(AWS)는 서버 `.env` 가 정답입니다

dev 와 반대입니다. **운영 값은 EC2 에 직접 접속해 `.env` 를 고치는 정책**입니다(`#119` 리뷰에서
정했습니다 — 값이 두 곳에 있으면 어긋나고, 어긋났을 때 어느 쪽이 참인지 알 수 없습니다).

```
운영 서버  /home/ubuntu/ktc4-kyungpook-6/.env   ← 사람이 직접 고친다 (백업 .env.bak.<날짜>)
           ~/.ktc4/vertex.json (디렉터리 700 · 파일 644)
   ↓
compose 가 --env-file 로 읽고, /run/secrets/vertex.json 으로 ro 마운트 (dev 와 같은 자리)
```

🚨 **`docker-compose.yml`(base)의 `environment:` 에 적힌 키만 컨테이너로 갑니다.** `.env` 에
넣어도 거기 없으면 안 들어갑니다 — prod 관리자 로그인이 `401` 이었던 이유가 이것입니다.

> 2026-10-16 까지는 SSM 파라미터 스토어(`/ktc4/prod/*`)에서 받아 `scripts/prod-remote-deploy.sh`
> 가 넘기는 구조였습니다. 위 정책에 맞춰 **파라미터 10개를 `.env` 로 옮기고 전부 삭제했고,
> 그 스크립트도 걷어냈습니다.** `deploy-main.yml` 은 `scripts/deploy.sh` 를 직접 부릅니다.

**SSM 으로 무엇을 하든 값을 명령에 싣지 마세요.** `send-command` 의 파라미터는 명령 기록
(SSM 콘솔 Command history · CloudTrail · Actions 로그)에 **그대로 남습니다.** 지금 배포 명령에는
`git fetch`·`deploy.sh` 만 실려 있습니다.

### 운영 서버에서 명령이 도는 조건 (2026-10-16 실측)

| | |
|---|---|
| 실행 사용자 | **root** |
| `HOME` | **설정되어 있지 않습니다.** `~` 도 확장되지 않습니다 |
| aws CLI | **없습니다** |
| python3 · bash · mktemp | 있습니다 |
| `/home/ubuntu` | `ubuntu:ubuntu 750` · root 쓰기 가능 |

🚨 **`$HOME` 을 쓰는 스크립트는 `set -u` 와 겹쳐 그 줄에서 죽습니다** — 자격증명이 안 붙는
정도가 아니라 **배포 전체가 실패합니다.** 서버에서 돌 스크립트는 경로를 고정하세요.

aws CLI 가 없으므로 스크립트는 없을 때 `docker run --rm --network host amazon/aws-cli` 로
부릅니다. `--network host` 가 필요한 이유는 인스턴스 메타데이터의 `HttpPutResponseHopLimit` 이
**1** 이어서, 브리지 네트워크 컨테이너는 자격증명을 받지 못하기 때문입니다.

키가 없으면 스크립트가 **그대로 넘어갑니다** — 지금처럼 조사만 503 이고 배포는 멈추지 않습니다.

⚠️ **스위치를 켜기 전에 고칠 것이 있습니다.** `ai/src/investigation/classify.py:84` 의
`_REGION_BEFORE_BRANCH` 가 `"대구왕갈비본점" → "왕갈비본점"` 으로 자르고, 그 열쇠를
`map_lookup.same_store()` 가 써서 **같은 구 안의 다른 가게** 주소·전화를 관측으로 끌어옵니다.
`AI_KAKAO_COMPARE_ENABLED` / `AI_NAVER_LOCAL_ENABLED` 를 켜는 순간 열리는 경로입니다.

**컨테이너 로그(`docker compose logs`)는 서버에 들어갈 수 있는 사람만 봅니다.** 밖에서 디버깅할 때는
HTTP 응답(RFC 9457 `title`)과 DB 상태로만 좁혀야 한다는 뜻입니다. 백엔드가 왜 그렇게 답했는지
로그로 확인해야 하면 **인프라 담당자에게 로그를 요청**하세요.

### 3-1. 관리자 토큰 받기

관리자 비밀번호는 **사람이 입력합니다.** 파일·커밋·티켓·채팅에 적지 않습니다.

```bash
read -s -p '관리자 비밀번호: ' PW; echo
TOKEN=$(curl -s -X POST https://goodradar-api.mojan.kr/api/auth/login \
  -H 'Content-Type: application/json' \
  -d "{\"email\":\"<관리자 이메일>\",\"password\":\"$PW\"}" \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["accessToken"])')
unset PW
curl -s -H "Authorization: Bearer $TOKEN" https://goodradar-api.mojan.kr/api/auth/me
```

> 관리자 계정은 기동할 때 `ADMIN_EMAIL`·`ADMIN_PASSWORD` 로 **한 번만** 만들어집니다. 이미 있으면
> 비밀번호를 갱신하지 않으므로, `.env` 를 나중에 바꿨다면 DB 쪽은 옛 값 그대로입니다.

### 3-2. DB 읽기

비밀번호를 명령줄·셸 기록에 남기지 않도록 `~/.pgpass` 를 씁니다(파일 권한 600).

```bash
echo '<호스트>:<포트>:ktc4:<계정>:<비밀번호>' >> ~/.pgpass && chmod 600 ~/.pgpass
psql -h <호스트> -p <포트> -U <계정> -d ktc4
```

**읽기만 하세요.** 자료를 넣을 때 DB 에 직접 `INSERT` 하면 정규화가 적용되지 않아 중복 판정·국세청
대조·점주 후보 찾기가 조용히 망가집니다(`backend/docs/데이터_정규화_가이드.md`). 넣는 길은 4번입니다.

⚠️ **연결이 암호화되지 않습니다**(서버가 `SSLRequest` 를 거절합니다 · `pg_stat_ssl.ssl = f`).
비밀번호와 조회 내용이 평문으로 지나갑니다. 개인정보가 든 표를 밖에서 조회하기 전에
접속 IP 제한이나 SSH 터널을 먼저 정하세요.

## 4. 배포 환경에 자료 넣기

`POST /api/admin/stores/imports` (관리자 전용). 같은 요청을 두 번 보내도 가게가 두 배가 되지 않고,
이미 있는 가게는 덮어쓰지 않습니다. `ntsCheck` 를 함께 보내면 국세청 확인 기록까지 만들어져
조사 화면에서 바로 쓸 수 있습니다.

```bash
curl -X POST "$API/api/admin/stores/imports" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  --data-binary @import.json
```

🔴 **실데이터(제3자 상호·주소·전화번호·사업자등록번호)는 권한 검사가 켜진 뒤에 넣습니다.**
스위치가 꺼져 있으면 `GET /api/stores` 가 토큰 없이 열려 있어 그대로 공개됩니다.

### 넣은 것을 되돌리기

잘못 넣은 가게나 한 바퀴 돌려 보려고 넣은 가공 자료는 **지울 수 있습니다**(PROMPT-157).

```bash
# 한 곳
curl -X DELETE "$API/api/admin/stores/12" -H "Authorization: Bearer $TOKEN"

# 여러 곳 (한 번에 100건까지)
curl -X POST "$API/api/admin/stores/deletions" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"storeIds":[12,13,14]}'
```

딸린 기록(국세청 확인·상태 변경 이력·메뉴·영업시간·조사 결과·확인 기록·신호·가게 변경 기록·점주
연결)을 함께 지웁니다. 조사(`job`) 자체는 남습니다.

**실제 활동이 남은 가게는 409 로 거절합니다.** 다만 둘은 `force` 로 넘길 수 있습니다 —
관리자가 그 리스크를 알고 지운다는 표시입니다.

| 거절 | `force` | 왜 |
|---|---|---|
| 점주가 연결돼 있음 | ✅ 넘김 | 점주 앱에서 그 가게가 사라집니다 |
| 조사가 돌고 있음 | ✅ 넘김 | 돌고 있는 조사의 대상이 없어집니다 |
| 방문(체크인) 기록이 있음 | ❌ | 아동이 다녀간 기록인데 **보관할 자리가 아직 없습니다** |

조사는 **가게 단위가 아니라 조사 단위로** 막습니다. 조사 결과(`task`)는 가게 한 곳이 끝날 때마다
생기므로, "이 가게가 지금 조사에 들어 있나" 를 물을 표가 없습니다 — 아직 차례가 안 온 가게는 어디에도
없어서, 가게로 물으면 이미 끝난 가게만 걸립니다. 그래서 끝나지 않은 조사가 하나라도 있으면 그동안은
삭제를 받지 않습니다(조사는 한 번에 하나만 돌고, 보통 분 단위로 끝납니다).

`force` 로 넘겨 조사 중에 지우면, 그 가게 차례가 올 때 **그 가게만 결과 없이 빠지고** 조사는 끝까지
갑니다. 요청한 가게 수와 결과 수가 그만큼 어긋납니다.

```bash
curl -X DELETE "$API/api/admin/stores/12?force=true" -H "Authorization: Bearer $TOKEN"
```

이름·주소가 틀린 정도라면 지우지 말고 `PATCH /api/stores/{storeId}` 로 고치세요. 지우면 그 가게의
조사 이력까지 사라집니다.

## 6. 로컬에서 먼저 재현하기

### 6-0. compose 로 배포와 같은 구성을 띄우기

배포본과 **같은 compose** 로 띄우면 환경변수가 제대로 전달되는지까지 같이 확인됩니다.

```bash
cp .env.example .env     # GOOGLE_CLOUD_PROJECT · VERTEX_KEY_PATH · 관리자 계정을 채운다
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build
```

- 관리자 계정은 `.env` 의 `ADMIN_EMAIL`·`ADMIN_PASSWORD` 로 **기동할 때 새로 만들어집니다.**
  로컬 전용 값을 쓰세요 — 배포 비밀번호를 여기 적지 않습니다
- `docker compose config` 로 **컨테이너가 실제로 받는 값**을 먼저 확인할 수 있습니다.
  환경변수가 compose 에 안 적혀 있으면 `.env` 에 적어도 들어가지 않습니다

배포 고리는 **머지를 거쳐야** 돌아서, 고칠 때마다 쓰기에는 느립니다. 화면·API 문제는 로컬에
같은 구성을 띄워 먼저 잡고 올리는 쪽이 빠릅니다.

```bash
# DB (도커가 있으면 compose, 없으면 로컬 Postgres 에 빈 DB 하나)
createdb ktc4_local

# 백엔드 — 권한 검사를 켠 채로 띄워야 배포와 같은 조건이 된다
DB_URL=jdbc:postgresql://localhost:5432/ktc4_local DB_USERNAME=... DB_PASSWORD=... \
JWT_SECRET=... ADMIN_EMAIL=admin@localhost.test ADMIN_PASSWORD=... \
AI_BASE_URL=http://localhost:8000 INTERNAL_API_KEY=... \
gradle bootRun            # backend/

# AI — 외부 호출 없이 연동 흐름만 볼 때
INVESTIGATOR=mock uv run uvicorn src.server.main:app --port 8000    # ai/

# AI — 실제 조사까지 돌려 볼 때. Vertex 는 서비스 계정 JSON 이 필요하다
GOOGLE_APPLICATION_CREDENTIALS=/경로/vertex.json GOOGLE_CLOUD_PROJECT=... \
uv run uvicorn src.server.main:app --port 8000

# 프론트
BACKEND_SWAGGER_URL=http://localhost:8080/v3/api-docs npm run api:generate && npm run dev   # frontend/
```

- **권한 검사를 끄고 확인하지 마세요.** 배포본과 조건이 달라져서, 로컬에서 되던 게 배포에서 401 로 막힙니다.
- 프론트 생성 코드(`frontend/src/api/generated`)는 커밋하지 않습니다. 없으면 `npm run api:generate` 로 만듭니다.

## 7. 하지 않는 것

- DB 비밀번호·관리자 비밀번호·API 키를 **파일·커밋·티켓·PR 에 적지 않습니다.** 사람끼리 직접 전달합니다
- **DB 에 직접 INSERT 하지 않습니다** (3-2 참고)
- 권한 검사가 꺼진 동안 **실데이터를 올리지 않습니다**
- 배포가 깨졌을 때 **서버에서 손으로 고치고 끝내지 않습니다** — 다음 배포에서 되돌아갑니다.
  고친 내용은 반드시 저장소(compose·스크립트)에 반영합니다
- 두 가지를 섞지 마세요. **구성**(compose·워크플로·스크립트)은 저장소가 정답이고,
  **운영 값**(prod `.env`)은 서버가 정답입니다. 값을 저장소에 적거나, 구성을 서버에만 고치면
  둘이 어긋납니다
