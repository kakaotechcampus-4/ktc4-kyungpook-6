## 그때 상황

최종 제출 하루 전, 발표 이틀 전이었습니다. 발표는 공개 정보 다음에 기능 두 가지를 하나씩 공개하는 구성이었고, 시연은 확인 전화만 라이브로 하고 조사 기능은 영상으로 보여 줄 계획이었습니다. 멘토님 앞에서 발표를 처음부터 끝까지 하고, 실제로 가게에 전화를 거는 시연도 했습니다.

## 나온 이야기

- 발표를 들은 지 30초 안에 무엇을 하는 서비스인지 알 수 있어야 한다. 기능을 하나씩 늦게 공개하는 구성은 기다리는 시간이 길다.
- 듣는 사람이 겪어 보지 않은 문제라면, 담당자가 명단을 보고 전화했는데 틀린 번호인 장면처럼 상황극으로 시작하는 방법이 있다.
- 주제가 AI 에이전트인 만큼 조사보다 전화에 집중한다. 전화 시연을 보면 사람들은 전화에 관심이 쏠린다.
- 라이브 시연이 실패할 때를 대비해 녹화 영상을 준비한다. 청중에게 바뀐 정보를 받아 그 자리에서 전화를 걸고, 통화 전사와 수정 카드가 관리자 화면에 바로 뜨는 모습을 보여 주면 좋다.
- "점주가 엉뚱한 답을 하면 어떻게 하나요?"라는 질문이 나올 것이다. 테스트 결과가 의도와 달랐던 경우와 그 이유, 조치를 전화 쪽 중심으로 정리해 둔다.
- 고도화 방향으로, 정해진 값을 확인하는 질문을 넘어 "바뀐 정보가 있나요?"라는 열린 질문에 대한 답을 정보 항목으로 나눠 담는 구조를 생각해 볼 수 있다.
- README 하나에 소개, 문제와 해결, 시스템 아키텍처, 기능, 기술 스택, 로컬 실행, 시연 영상을 모은다. 기술 멘토링 기록은 주차별로 정리해 저장소에 넣는다.

시연 중 음성 인식이 한 번 흐리게 들어갔는데, 에이전트가 저장하지 않고 다시 물어 확인했습니다.

## 정한 방향

- 발표는 문제 장면으로 시작하고, 기능을 늦게 공개하는 구간을 줄입니다.
- 발표와 시연의 중심을 확인 전화에 둡니다.
- 예상하지 못한 답의 처리와 의도와 달랐던 테스트 결과를 문서로 정리합니다.
- README를 다시 쓰고, 기술 멘토링 기록을 저장소에 남깁니다.
