## Branch

#### main

```
최종 브랜치
```

#### develop

```
개발 메인 브랜치
```

- 개인 티켓 작업 후 develop 브랜치로 PR 진행
- **같은 파트 팀원**이 검토 후 머지
  (Front↔Front, Back↔Back, AI↔AI)

</td>
<td width="34%" valign="top">

```
PROMPT-{티켓번호}-{파트}-{설명}
```

- **Jira에서 자동 생성하여 사용!!**
  직접 만들 필요 없음!

</tr>
</table>

#### 작업 태그

| Tag | 용도 |
|---|---|
| `init` | 프로젝트/모듈 최초 생성 |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `add` | 새 파일(이미지, 문서 등) 추가 |
| `design` | 디자인 추가/수정 |
| `docs` | 문서(README, `docs/` 등) 수정 |
| `chore` | 빌드 설정, 의존성, Docker 등 |
| `style` | 코드 포매팅, 들여쓰기 등 |
| `refactor` | 리팩토링 |
| `test` | 테스트 코드 추가/수정 |
| `rename` | 파일/폴더 이름 변경 |
| `remove` | 파일/폴더 삭제 |

</td>
<td width="50%" valign="top">

#### 커밋 메시지 형식

```
<작업 태그>(파트): 작업 내용
```

- 작업 태그, 파트 모두 **영어 소문자** (`front`/`back`/`ai`)
- 작업 내용은 한글로 간결히.

**예시**

```
feat(back): 매장 목록 조회 API 추가
fix(back): 사업자등록번호 검증 로직 버그 수정
test(back): StoreService 단위 테스트 추가
```

- ⭐️**한 커밋 = 의미 있는 변경 하나.** 
- `git add .`로 비빔밥 커밋 하지 않기!
- 관련 있는 파일들만 골라서(`git add <file>`) 커밋.

</td>
</tr>
</table>

## Pull Request

<table>
<tr>
<td width="50%" valign="top">

#### 개인 PR (`개인 작업 브랜치 → develop`)

- **리뷰어**: 같은 파트 팀원 <- Reviewers에 추가!!
- `.github/pull_request_template.md`에 있는 필요 내용들을 간단히 작성
- **상세 구현 내용은 Notion에 기록**
- 팀원 피드백 반영 완료되면 **코멘트로 완료 표시**

</td>
<td width="50%" valign="top">

#### 종합 PR (`develop → main`)

- **PM이** 그 주 `develop`에 머지된 내용을 종합해서 main에 PR
- PR 내용은 템플릿에 따라 작성
- **base가 `main`인지 확인!!**
- 멘토님께 특히 봐주셨으면 하는 부분은 **Notion에 미리 적어두기**
- 멘토님이 팀에서 언급하지 않은 부분을 지적하면, **해당 파트 리더가 책임지고 반영**

</td>
</tr>
</table>

#### 파트 간 API 계약 — 백엔드가 먼저 공개합니다

**순서를 고정합니다.**

```
① 백엔드가 스펙을 먼저 공개한다   구현 없이 경로·요청·응답만. 501 을 돌려주는 PR 로 올려도 된다
② 프론트가 그 스펙으로 목업을 만든다   화면 작업이 백엔드 구현을 기다리지 않는다
③ 백엔드 구현이 뒤따른다
```

**왜 이 순서인가** — `[Back] 가게 정보 수정 API 스펙 선구현`(PR #31)에서 이렇게 했고 어긋남이
없었습니다. 반대로 프론트가 없는 API 를 **자기가 가정한 이름으로 먼저 붙인 경우**에는, 나중에
백엔드가 다른 이름으로 만들어 화면·타입·테스트를 다시 고쳐야 하는 상황이 생겼습니다
(조사 결과 조회 API — 문서·백엔드·프론트가 세 갈래).

- **경로·필드명·enum 은 기획 문서에 적지 않습니다.** 그 층위의 기준은 **Swagger 와 코드**입니다.
  기획 문서는 "왜 만드는가"와 "무엇을 만드는가"(화면 흐름·판정 규칙)까지만 담습니다
- 기획 문서에는 대신 **주고받을 데이터와 그 데이터가 어떻게 가공되는지**를 적습니다
- 스펙이 바뀌면 **바꾼 파트가 그 자리에서 공유**합니다. 문서를 나중에 몰아 고치면 갈라집니다

#### PR 제목

```
[파트] 제목
```

**예시**: `[Back] 컨벤션 문서화`
