# 확인 전화

가게에 **전화를 걸어 점주에게 직접 물어보는** 기능입니다. 조사가 찾아낸 값이 맞는지, 또는 등록된
값이 그대로인지를 확인합니다. 전화를 걸고 받아 오는 일은 **전화 API 서버**가 하고, 관리자 서비스는
요청을 넣고 결과를 읽습니다.

> 이 문서는 `PROMPT-165` 에서 썼습니다. 전화 API 서버 쪽은 심준성님(`MOJAN3543`) 이,
> 관리자 서비스 연결(백엔드·프론트)은 이 문서가 다룹니다.

---

## 1. 언제 전화가 걸리나

**조사 판정이 정합니다.** 두 경우만 걸고, 그 밖에는 걸지 않습니다.

| 판정 | 화면 | 전화 | 무엇을 묻나 |
|---|---|---|---|
| `PRIORITY_CHECK` | 우선확인 | ✅ **변화가 잡혀서** | 조사가 찾아낸 값이 맞는지 항목마다 (`VALUE_CONFIRMATION`) |
| `ADDITIONAL_CHECK` | 추가확인 | ✅ **90일 넘게 확인하지 않아서** | 등록된 값이 그대로인지 한 질문으로 (`CHANGE_DETECTION`) |
| `NO_CHANGE` | 변화없음 | ❌ | 물을 것이 없습니다 |
| 판정 없음(조사 실패) | 조사하지 못함 | ❌ | 무엇을 물어야 할지 모르는 상태입니다 |

90일 기준은 `docs/도메인_용어집.md` 의 "추가확인 판정 기준" 과 같은 값입니다 — 전화가 그 기준을
따로 갖지 않습니다.

여기에 더해 **담당자가 이미 확인을 끝낸 카드에는 걸지 않습니다.** 답이 나온 뒤에 가게로 전화가
가면 민폐입니다. 가게 전화번호가 없거나, 하이픈·공백·괄호를 지운 뒤 숫자가 7~15자리가 아니면
전화 API 가 받지 않으므로 우리 쪽에서 먼저 막습니다(그러면 `502` 가 아니라 `409` 로 보입니다).

### 전화 한 통은 담당자 확인을 대신하지 않습니다

이름이 비슷한 두 기록이 있고, 뜻이 다릅니다.

| | 무엇인가 | 누가 만드나 |
|---|---|---|
| `VerificationCall` (확인 전화) | 전화를 걸어 점주에게 물은 기록 | 자동 |
| `Verification` (확인 기록) | 담당자가 가게를 확인했다고 남긴 기록 | 사람 |

전화가 끝나도 **가게 확인일(`Store.lastCheckedAt`)은 올라가지 않고** 확인 기록도 생기지 않습니다.
점주의 답을 읽고 판단하는 일은 담당자가 합니다 — 수정안 반영(`apply`)이 확인일을 올리지 않는 것과
같은 이유입니다.

## 2. 무엇을 어떻게 묻나

전화 API 는 질문 배열의 **순서대로** 통화를 진행하고, 통화는 중간에 끊길 수 있습니다. 그래서
**영업 여부를 가장 먼저** 묻습니다 — 이 서비스가 있는 이유가 "폐업한 가게에 아이가 헛걸음하는 것"
을 없애는 것이므로, 한 가지만 듣고 끊긴다면 그 한 가지는 영업 여부여야 합니다.

| 우리 항목 | 전화 API 키 | 통화에서 부르는 이름 | 값 |
|---|---|---|---|
| `status` | `open` | 영업 여부 | **JSON 불리언** |
| `name` | `storeName` | 상호명 | 문자열 |
| `addressRoad` | `storeLocation` | 매장 위치 | 문자열 |
| `phone` | `phoneNumber` | 전화번호 | 문자열 |

### ⚠️ 영업 상태만 규칙이 다릅니다

우리는 영업 상태를 `OPEN`·`SUSPENDED`·`CLOSED` 세 값으로 갖지만, 전화로 "상태가 `CLOSED` 맞습니까"
를 물을 수는 없습니다. 그래서 전화에는 **"지금도 영업하십니까" 한 가지만** 묻고, 답은
`true`/`false` 로 옵니다.

```
휴업 → 폐업 으로 바뀐다는 수정안은 전화로 묻지 않습니다
  둘 다 "영업하지 않음" 이라 전화로 가를 수 없습니다 — 담당자가 정합니다

상태가 미확인(UNKNOWN)인 가게도 영업 여부를 묻지 않습니다
  모르는 것을 "영업하지 않는다" 로 바꿔 물으면 점주가 "아니요" 라고 답하고,
  그 답이 "영업 중" 으로 기록됩니다
```

**재확인 전화에서는 전화번호를 묻지 않습니다.** 그 번호로 전화가 연결됐다는 것이 이미 답입니다.
변화가 잡혀 조사가 다른 번호를 제안한 경우에만 묻습니다 — 그때는 옛 번호로 걸어 새 번호를 확인합니다.

## 3. 대기열은 우리가 만들지 않습니다

전화 API 가 요청을 받아 대기열에 넣고 차례대로 발신합니다. **한 번에 여러 건을 넣으면 됩니다** —
화면이 한 통씩 기다리며 다음을 넣지 않습니다.

```
담당자가 "전화 대상 N곳에 한 번에 전화 걸기" 를 누른다
   ↓
POST /api/jobs/{jobId}/calls      대상마다 전화 API 에 요청을 넣는다 (건별 트랜잭션)
   ↓
전화 API 가 대기열에 넣고 차례대로 발신한다            ← 순서·동시 통화 수는 전화 API 가 정한다
   ↓
CallStatusPoller 가 10초마다 끝나지 않은 전화를 읽어 DB 에 반영한다
   ↓
화면이 조사 결과를 다시 조회하면 카드마다 call 이 채워져 있다
```

### 왜 폴러가 따로 있나

전화 API 는 요청을 접수하고 바로 답합니다(`202 Accepted`). 통화 결과는 우리가 물어봐야 합니다.
담당자 화면은 조사 결과를 되풀이해 조회하는데, **그 조회가 외부 호출을 하면 가게 수만큼 전화 API 를
부르게 됩니다.** 그래서 받아 오는 일은 폴러가 하고 화면 조회는 DB 만 읽습니다.

폴러는 **한 차례에 보는 수에 상한**(`call.poll-batch-size`)을 두고 오래된 것부터 읽습니다. 상한이
없으면 전화 API 가 느려진 날 한 바퀴가 끝나지 않아 다음 차례가 계속 밀립니다.

### 영영 끝나지 않는 전화는 닫습니다

전화 API 문서에 통화 제한 시간이 없어 **우리가 정합니다**(`call.max-wait-minutes`, 기본 15분).
닫지 않으면 폴러가 그 전화를 끝없이 다시 읽고, 담당자 화면에도 "전화 확인 중" 이 영영 남습니다.

## 4. API

| | |
|---|---|
| `POST /api/tasks/{taskId}/call` | 한 건. `202` + 전화 기록 |
| `POST /api/jobs/{jobId}/calls` | 그 조사의 전화 대상 전부. `202` + 대상 수·요청 수·건너뛴 수 |
| `GET /api/jobs/{jobId}` | 조사 결과. 카드마다 `call` 이 붙어 옵니다 |

둘 다 관리자 전용입니다(`/api/tasks/**`·`/api/jobs/**` 가 이미 `hasRole("ADMIN")`).

거절하는 경우:

| 상태 | type | 언제 |
|---|---|---|
| `409` | `call-target-not-eligible` | 판정이 대상이 아님 · 이미 확인한 카드 · 번호 없음·모양 안 맞음 · 물을 질문이 안 만들어짐 |
| `409` | `call-already-requested` | 걸어 둔 전화가 있음. **실패한 전화는 다시 걸 수 있습니다** |
| `503` | `call-not-available` | 전화 API 주소·키를 아직 넣지 않았습니다 |
| `502` | `call-api-error` | 전화 API 가 거절했거나 닿지 않았습니다 |

한 번에 걸기는 한 건의 실패로 멈추지 않습니다 — 그 건만 `skipped` 로 세고 넘어갑니다. 어느 결과가
빠졌는지는 결과를 다시 조회해 `call` 이 비어 있는 것으로 압니다.

## 5. 넣어야 하는 값

| 이름 | 없으면 |
|---|---|
| `VERIFICATION_API_BASE_URL` | 전화 기능만 꺼집니다 — 걸려고 할 때 `503`. 앱은 뜨고 나머지는 그대로 돕니다 |
| `VERIFICATION_API_KEY` | 같습니다. 둘 중 하나만 있어도 꺼진 것으로 봅니다 |

🚨 **키는 사람끼리 직접 전달합니다.** 파일·커밋·티켓·PR 에 적지 않습니다. 이 저장소는 public 입니다.

- **dev** — 저장소 Secrets 에 넣고 `deploy-dev.yml` 이 넘깁니다
- **prod** — 운영 서버 `.env` 를 직접 고칩니다(`docs/배포환경에서_작업하는_방법.md` 의
  "prod(AWS)는 서버 `.env` 가 정답입니다")

`docker-compose.yml`(base)의 `environment:` 에 두 키가 이미 들어 있습니다 — `.env` 에만 넣으면
컨테이너로 가지 않습니다.

조정할 수 있는 값(기본값으로 둬도 됩니다): `CALL_POLL_INTERVAL_MS`(10000) ·
`CALL_POLL_BATCH_SIZE`(20) · `CALL_MAX_WAIT_MINUTES`(15).

## 6. 아직 확인하지 못한 것

- 🟡 **영업 여부를 참·거짓으로 묻는 질문이 통화에서 어떻게 들리는지** 들어보지 못했습니다.
  전화 API 명세가 불리언을 받는다고 적고 있어 그 모양으로 보내지만, `open`/`영업 여부` 라는 이름으로
  실제 통화가 자연스럽게 흘러가는지는 **심준성님과 함께 한 통 걸어 봐야** 압니다
- 🟡 **`failureReason` 코드 목록**이 명세에 없습니다. 그래서 받은 코드를 번역하지 않고 화면에
  그대로 보여 줍니다 — 모르는 코드를 삼키면 원인이 사라집니다
- 🔴 **받은 API 키가 거절됩니다(401).** 2026-11-04 에 주소와 키를 받아 붙였는데, 전화를 걸지 않는
  조회로 확인해 보니 키가 먹지 않습니다. 키를 다시 받아야 합니다 — 그때까지 전화 버튼은 `503` 입니다

> ✅ **요청·응답 형식은 실제 서버와 맞는 것을 확인했습니다.** 전화 API 가 `/openapi.json` 을 공개하고
> 있어 우리 클라이언트와 하나씩 대조했습니다(`target` 세 칸, 두 질문 방식의 칸 구성, `currentValue`·
> `expectedValue`·`value` 가 문자열이거나 불리언인 것, `status` 네 값). 주소와 키는 `_local/설정/` 에
> 둡니다 — 이 저장소는 public 이라 여기 적지 않습니다.

## 7. 하지 않는 것

- **전화 결과로 가게 정보를 자동으로 고치지 않습니다.** 점주가 전화로 말한 값이 그대로 반영되면,
  잘못 들은 한마디가 가게 정보가 됩니다. 답은 담당자가 읽고 "직접 수정하기" 로 반영합니다
- **우리 쪽에 대기열을 만들지 않습니다.** 전화 API 가 갖고 있습니다
- **실패한 전화를 자동으로 다시 걸지 않습니다.** 다시 걸지는 담당자가 정합니다 — 안 받는 가게에
  서버가 알아서 되풀이해 걸면 민폐입니다
