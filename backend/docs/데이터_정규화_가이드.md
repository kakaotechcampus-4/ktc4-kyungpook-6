# 데이터 정규화 가이드

가게 이름·주소·사업자등록번호를 **비교 가능한 형태로 정리하는 규칙**을 정리한 문서입니다.
규칙은 매칭 결과를 보며 계속 조정될 예정이라, 바꿀 때는 이 문서도 함께 고쳐주세요.

---

### 1. 왜 정규화하나?

같은 가게라도 데이터마다 표기가 다릅니다.

```
㈜예시분식(샘플점)
(주) 예시분식 샘플점
예시분식 샘플점
```

사람 눈엔 같은 가게지만 컴퓨터는 전부 다른 값으로 봅니다. 그래서 **정해진 규칙으로 밀어서 같은 값으로 만든 뒤** 비교합니다.

| 용도 | 설명 |
| :--- | :--- |
| **중복 판별** | 같은 가게가 두 번 등록되는 것 방지 |
| **외부 데이터 매칭** | 국세청 등 외부 데이터와 우리 가게를 짝지음 |
| **검색** | `예시분식` 으로 검색해도 `㈜예시분식` 이 나오게 함 |

#### 원본과 정규화 값은 따로 저장합니다

| 컬럼 | 예시 | 용도 |
| :--- | :--- | :--- |
| `name` | `㈜예시분식(샘플점)` | **화면에 보여주는 원본** |
| `name_normalized` | `예시분식샘플점` | **비교·검색용** |

정규화 값은 사람이 읽기 불편해서 화면에 쓰지 않고, API 응답(`StoreResponse`)에서도 제외합니다.

---

### 2. 어디서 정규화하나?

**서비스 계층에서 정규화 클래스를 호출합니다.** (멘토 리뷰 Q4 반영)

| 위치 | 판단 | 이유 |
| :--- | :--- | :--- |
| **서비스** | ✅ | 정규화는 "데이터 가공"이라 아키텍처 문서상 서비스 역할. 규칙이 바뀌었을 때 전체 재계산도 서비스에서 자연스러움 |
| 엔티티 `@PrePersist` | ❌ | `save()` 할 때만 동작해서 **벌크 수정·직접 SQL 에서는 건너뜀**. "막고 있다고 착각하는 구멍"이 생김 |
| DB 제약 | 🟡 보조 | `NOT NULL` 은 "비어 있지 않음"만 보장하고 정규화 여부는 못 봄. 빈 값 사고 방지용으로만 유지 |

> ⚠️ **SQL 로 데이터를 직접 넣으면 정규화가 적용되지 않습니다.** 적재 경로(CSV 적재 등)에서 반드시 정규화 클래스를 거쳐 저장하세요.
> 이미 들어간 데이터를 고쳐야 하면 **일회성 보정 코드로 실행한 뒤 바로 삭제**합니다. 상시 재정규화 기능은 두지 않습니다. (멘토님 리뷰 반영)

### 3. 사업자등록번호 — `BizNoNormalizer`

국세청 API 는 **하이픈 없는 숫자 10자리**만 받습니다.

| 규칙 | 설명 |
| :--- | :--- |
| 전각 숫자 변환 | `１２３` → `123` |
| 숫자만 남김 | 하이픈·공백·점 등 모두 제거 |
| 유효성 검사 | 정리 후 **숫자 10자리**여야 유효 (`isValid`) |

| 원본 | 결과 | 유효 |
| :--- | :--- | :--- |
| `123-45-67890` | `1234567890` | ✅ |
| ` 123 45 67890 ` | `1234567890` | ✅ |
| `12345-67890` | `1234567890` | ✅ |
| `１２３-４５-６７８９０` | `1234567890` | ✅ |
| `123456789` | `123456789` | ❌ 9자리 |
| `null` / 빈 값 / `---` | `""` | ❌ |

#### 저장 방식

- **`bizNo` 컬럼에는 정규화한 값(숫자만)을 저장합니다.** 이름·주소와 달리 사업자번호는 정답 모양이 하나라 원본 컬럼을 따로 두지 않습니다.
  - 모양이 통일돼야 DB 에서 같은 사업자를 찾거나(`DISTINCT`, 검색) 중복을 확인할 수 있습니다.
  - 화면에 `123-45-67890` 처럼 보여줘야 하면 **보여줄 때** 하이픈을 붙입니다.
- 타입은 **`String` 을 유지합니다.** 숫자 타입으로 바꾸면 `0123456789` 의 앞자리 0 이 사라집니다.
- 정규화 후 10자리가 아닌 번호도 **숫자만 남긴 채 저장**되고, 조회할 때 `isValid` 로 걸러집니다. (적재 시 처리 방식은 CSV 적재 작업에서 결정)
- SQL 로 직접 넣은 데이터는 정규화가 안 돼 있을 수 있어, **조회할 때도 `normalize` → `isValid` 를 거칩니다.**

#### 기타

- 사업자번호 **검증번호(마지막 자리 계산) 체크는 하지 않습니다.** 형식만 봅니다.
- 유효하지 않은 번호는 국세청을 호출하지 않고 걸러서 **일일 호출 한도를 아낍니다.**

### 4. 가게 이름 — `StoreNormalizer.normalizeName`

#### 적용 순서 (순서가 중요합니다)

| 순서 | 규칙 | 예시 |
| :--- | :--- | :--- |
| 1 | 전각 문자 → 일반 문자 | `ＳＡＭＰＬＥ` → `SAMPLE` |
| 2 | **법인 표기 제거** | `㈜` `(주)` `주식회사` / `(유)` `유한회사` / `㈔` `(사)` `사단법인` / `(재)` `재단법인` — 괄호 안팎과 글자 사이 공백도 허용 (`( 주 )`, `사단 법인`) |
| 3 | 영문 소문자 | `SAMPLE` → `sample` |
| 4 | **한글·영문·숫자만 남김** | 공백·괄호·특수문자 제거 |

> **2번이 4번보다 먼저여야 합니다.** 괄호를 먼저 지우면 `(주)예시분식` 이 `주예시분식` 이 되어 법인 표기가 남습니다.
>
> **법인 표기에 공백을 허용하는 이유:** `주식 회사 예시분식` 을 못 지우면 4번에서 공백이 빠져 `주식회사예시분식` 이 되고, 한 번 더 정규화하면 `예시분식` 이 되어 **결과가 흔들립니다.** 정규화한 값을 다시 정규화해도 같아야 합니다.

#### 예시

| 원본 | 결과 |
| :--- | :--- |
| `㈜예시분식` | `예시분식` |
| `(주)예시분식` | `예시분식` |
| `주식회사 예시분식` | `예시분식` |
| `주식 회사 예시분식` | `예시분식` |
| `(사)예시단체` / `㈔예시단체` | `예시단체` |
| `사단법인 예시단체` | `예시단체` |
| `(재)예시단체` / `재단법인 예시단체` | `예시단체` |
| `예시분식 주식회사` | `예시분식` |
| `유한회사 예시분식` | `예시분식` |
| `예시분식 (샘플점)` | `예시분식샘플점` |
| `샘플카페[본점]` | `샘플카페본점` |
| `SAMPLE CAFE` | `samplecafe` |
| `ＳＡＭＰＬＥ　카페` | `sample카페` |
| `null` | `""` |

### 5. 주소 — `StoreNormalizer.normalizeAddress`

| 순서 | 규칙 | 설명 |
| :--- | :--- | :--- |
| 1 | 전각 문자 → 일반 문자 | `８０` → `80`, `－` → `-` |
| 2 | 보이지 않는 문자 제거 | zero-width space·joiner(U+200B~U+200D), BOM(U+FEFF). 웹 복사·엑셀 CSV 에서 섞여 들어옴 |
| 3 | 대시 문자 → 하이픈 | `‐` `‑` `‒` `–` `—` `−` (U+2010~U+2014, U+2212) → `-`. 워드·한글 프로그램이 자동으로 바꿔 넣음 |
| 4 | **공백 제거** | 스페이스·탭·줄바꿈 |

| 원본 | 결과 |
| :--- | :--- |
| `가상특별시 예시구 샘플로 123` | `가상특별시예시구샘플로123` |
| `가상특별시 예시구 샘플로 ８０` | `가상특별시예시구샘플로80` |
| `가상특별시 예시구 샘플로 80-1` | `가상특별시예시구샘플로80-1` |
| `가상특별시 예시구 샘플로 80–1` (en dash) | `가상특별시예시구샘플로80-1` |

> **하이픈은 지우지 않습니다.** 지우면 `샘플로 80-1` 과 `샘플로 801` 이 같은 주소가 됩니다.

### 6. 1차 버전에서 하지 않는 것

| 하지 않는 것 | 이유 |
| :--- | :--- |
| 지점명 떼기 (`예시분식샘플점` → `예시분식`) | 같은 체인의 **다른 지점이 한 가게로 합쳐질** 위험 |
| 시·도 표기 통일 (`대구광역시` ↔ `대구`) | 표기 목록 관리가 필요해 규칙이 커짐 |
| 한자·일본어 등 보존 | 드문 경우라 제외 (정규화 시 지워짐) |
| 사업자번호 검증번호 계산 | 규칙 오류 시 멀쩡한 번호를 거를 위험 |
| 한쪽 괄호만 있는 법인 표기 (`주)예시분식`) | 원래 이름이 `주)` 로 시작하는 경우를 망가뜨릴 수 있음. 실제 데이터를 보고 결정 |

#### 알려진 부작용

| 원본 | 결과 | 비고 |
| :--- | :--- | :--- |
| `B&B 카페` | `bb카페` | `&` 가 사라짐 |
| `카페 1+1` | `카페11` | `+` 가 사라짐 |

매칭에 문제가 없어 1차 버전에서는 허용합니다.

### 7. 국세청 API 와의 관계

국세청 사업자 상태조회 응답에는 **가게 이름·주소가 없습니다.** 그래서 국세청과는 **사업자등록번호로만** 대조하고,
이름·주소 정규화 값은 **중복 판별·AI 조사 전달·다른 외부 데이터 매칭**에 사용합니다.

#### 역할 분담

| 단계 | 담당 코드 | 하는 일 |
| :--- | :--- | :--- |
| 호출 | `BusinessLookupService` / `NtsApiClient` (PROMPT-48) | 국세청 API 호출, JSON 파싱까지. **원본 문자열 그대로** 돌려줌 |
| 해석 | `domain/business/dto/BusinessStatus` | `b_stt_cd` → `BusinessState`, `end_dt` → 폐업일 |
| 사용 | `StoreService.checkWithNts` | 번호 정규화·검증 → 조회 → 가게 정보와 나란히 담아 AI 조사 자료 생성 |

#### 조회할 때 지키는 것

| 규칙 | 이유 |
| :--- | :--- |
| **정규화 후 10자리인 번호만** 조회 | 형식이 틀린 번호는 물어봐도 소용이 없어 호출 한도만 쓴다 |
| **중복 번호는 한 번만** 조회 | 사업자 하나로 매장 여러 개를 운영할 수 있다 |
| 응답은 **순서가 아니라 `b_no` 로** 짝지음 | 응답이 한 건만 밀려도 엉뚱한 가게에 붙는다 |
| 상태 판단은 **`b_stt_cd` 로만** | 폐업자여도 `tax_type` 은 "일반과세자" 로 온다 |
| 값이 이상하면 **예외 → 그 건만 `UNCONFIRMED`** | 틀린 상태를 AI 에 넘기는 것보다 "확인 안 됨" 이 안전하다 |

#### AI 에 넘기는 비교 결과 (멘토님 리뷰 반영)

**답이 하나로 정해지는 비교는 코드가, 답이 갈리는 해석은 AI 가** 맡습니다.

| 필드 | 값 | 뜻 |
| :--- | :--- | :--- |
| `ntsLookup` | `CONFIRMED` | 국세청 상태를 확인함 |
| | `UNCONFIRMED` | 조회했지만 응답이 없거나 해석 실패 → **다시 조회하면 확인될 수 있음** |
| | `NO_BIZ_NO` | 번호가 없거나 형식이 틀려 조회 안 함 → **데이터를 고쳐야 함** |
| `statusComparison` | `MATCH` | 우리 상태와 국세청 상태가 같음 |
| | `OPEN_BUT_CLOSED` 등 | 어떻게 다른지 (`우리상태_BUT_국세청상태`) |
| | `NTS_NOT_REGISTERED` | 국세청에 없는 번호 |
| | `NOT_COMPARABLE` | 우리 상태가 `UNKNOWN` 이거나 국세청 상태를 확인 못함 |
| `statusMismatch` | `true` / `false` | 두 상태가 다른가. `MATCH`·`NOT_COMPARABLE` 이면 `false` |

`statusMismatch` 가 `true` 인 가게만 AI 조사에 넘기면 호출을 줄일 수 있습니다. 두 값은 `StoreCheckResponse.of()` 에서 함께 계산해 서로 어긋나지 않습니다.

### 8. 규칙을 바꿀 때

1. **테스트의 기대값을 먼저 수정** (`StoreNormalizerTest`, `BizNoNormalizerTest`)
2. 정규화 클래스 수정 → 테스트 통과 확인
3. **이 문서의 규칙·예시 갱신**
4. **기존 데이터 보정** — 규칙이 바뀌면 이미 저장된 값과 새 값이 달라집니다. 필요하면 일회성 보정 코드로 다시 계산한 뒤 코드는 삭제합니다

> 보정 전까지는 옛 규칙 값과 새 규칙 값이 섞여 있는 게 정상입니다. 정규화 값은 "항상 맞아야 하는 값"이 아니라 **계산해서 저장해둔 값**이기 때문입니다.
