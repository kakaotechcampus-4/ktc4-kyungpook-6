# 도메인 기반 아키텍처 가이드

우리 프로젝트 백엔드에서 **Layered Architecture**(기능별 분류) 대신, **Domain-Driven Architecture**(비즈니스 단위 분류) 느낌으로 채택하여 진행해볼까 합니다.

"내 코드를 어디에, 어떻게 작성해야 하는가?" 확인 가이드

---

### 1. 왜 도메인 아키텍처?

* **Layered (기본형)**: `controller`, `service` 폴더에 모든 도메인의 파일이 섞여 있어 프로젝트가 커지면 탐색 힘듦
* **Domain (우리 방식)**: `store`(가게), `business`(사업자등록번호) 등 비즈니스 단위로 폴더를 나누기. 가게 관련 코드는 `store` 폴더에. **응집도가 높고 유지보수 편함.**


---

### 2. 폴더 구조와 역할

모든 비즈니스 로직은 `src/main/java/.../domain/` 아래에 위치하기.

#### **📂 domain/{해당 도메인 이름}/**
각 도메인은 자신만의 '성'을 가집니다. 아래 5개 계층을 기본으로 합니다.

| 폴더 (Package) | 역할 | 비유 |
| :--- | :--- | :--- |
| **controller** | 클라이언트의 요청을 받고 응답을 보냄 | **카운터 직원** |
| **service** | 비즈니스 로직 수행 (데이터 가공, 외부 API 호출 등) | **주방 요리사** |
| **entity** | 실제 DB 테이블과 매핑되는 클래스 | **식재료** |
| **repository** | DB에 접근하여 데이터를 저장/조회 (JPA) | **냉장고/창고** |
| **dto** | 계층 간 데이터 이동 시 사용 (Request, Response) | **포장 용기** |

#### **📂 global/**
특정 도메인이 아닌, 프로젝트 전체에서 공통으로 쓰는 기술 설정.
- `config`: Swagger, Redis, Security 설정 등
- `error`: 전역 예외 처리 (`GlobalExceptionHandler`, `ErrorCode`, `CustomException`) — 패턴은 `백엔드_코딩_컨밴션_가이드.md` 참고
- `util`: 날짜 변환, API 호출 헬퍼 등 공통 도구

---

### 3. 코드 작성 규칙

#### **1: 도메인 횡단 주의**
- `store` 도메인이 `business` 도메인의 데이터를 직접 수정하지 마세요.
- 다른 도메인의 정보가 필요하다면, 해당 도메인의 **Service**를 호출하여 소통하는 것을 권장.

#### **2: Entity 그대로 말고 DTO 사용**
- **Entity**는 DB와 직접 연결된 민감한 객체.
- API 응답을 보낼 때는 반드시 `dto` 폴더에 있는 **Response 객체**로 변환해서 내보내기.

#### **3: 스웨거 태그 달기**
- 컨트롤러 상단에 `@Tag(name = "도메인명")`달아주기. 그래야 스웨거 문서에서도 아키텍처처럼 묶임.
